# Components

## How the components get built

**The components are `FujiList`, the list view; `FujiTree`, the tree view; and `FujiBar`, the toolbar.** The list and the tree are the views every file manager has beside its icons. A menu is a toolbar too, one with text and no icons where every item leads to a submenu, so fuji's menus are `FujiBar` rather than a component of their own.

**The research behind them** is a survey of existing components, and a table of the keyboard and mouse interactions compiled from Apple, Microsoft, VS Code and the ARIA guide.

**Incrementally, with `pnpm local` running.** Build a small piece, look at it in the running program, then the next piece, so the work never gets over its skis. Simple all the way through: simple code is shorter, and it tends to run faster.

**One list on every platform, informed by Explorer and Finder, and its own thing.** Each choice, in how the list looks and in how it behaves, starts from what Windows Explorer and Finder do, because those are what a user already knows. Then fuji makes the choice itself, for a list that is simple, familiar and clean and the same on Windows, the Mac and Linux, and the comment on each choice names who it follows, such as a type-ahead timeout taken from Chromium or a focus rectangle taken from Windows. Where Explorer and Finder disagree, or another program does it better, fuji takes one answer and every platform gets it. The alternative is copying Explorer exactly on Windows and Finder exactly on the Mac. That is a list per platform, with code and selectors for each and a lot of back and forth between machines; an imperfect match reads as wrong to a user who knows the real thing, so every miss would be suspect; few users would benefit; and on Linux there is no one file manager to copy. A list built from both and copying neither becomes fuji's own. For the look, the choice is Swing's, one look consistent across platforms, without Swing's result: the list and the tree are made of web and do not try to match the native controls pixel for pixel, and they look good by using the system's own typography correctly and keeping their appearance flat and simple.

**An exception would customize the list to the platform it runs on, where matching the platform is what makes the list right there.** One is made today: the highlight colors, a selection and a menu's row under the pointer, take each platform's own look, as The highlight colors below describes. Each is the Mac's or everyone else's, two looks and no third: what is not the Mac takes Windows', and fuji does not style for Linux alone, the user's choice on 2026-11-21. The bar's ground was another, the title bar's color on Windows, until 2026-11-20, when everything took one face. A new case is weighed by whether matching the platform there is what makes the list read as the machine's rather than a web page's. Command on the Mac doing what Control does elsewhere is not an exception: it is the same behavior under the platform's own key, as in every cross-platform program, since a Control-click on the Mac is a right click.

**The feel: nothing a desktop user reaches for is missing.** The components have to be complete and robust enough that a native desktop user never finds them limited or incomplete. The failure is a web list that is clearly a web page and not Finder or Explorer, which is fine, but skips the ordinary second-order interactions that make a list feel like a list: control-click to toggle one item in the selection, shift-click to extend it, the arrow keys moving a keyboard focus that is separate from the selection, a name typed to jump to it. A user who sees such a list, thinks "this is like my file manager," tries one of those, and meets nothing, decides the whole thing is incomplete and worse than what they already have. Google Drive's file list is the kind of list meant, and its own shortcuts page documents a focus that moves under Ctrl with the arrows, as fuji's list moves its focus under the command key. Fuji's list and tree pass the test.

**Showcases and innovations.** Some features are in the art but rare, and fuji's list and tree showcase them. Others are interactions fuji's list adds beyond what Finder and Explorer do, which are built after the rest of the list, and then written up in the article on fuji's design choices or in the List and Tree article on the site. Each such item below says which it is.

**Shipping on npm.** Whether the components ship on npm as `@zootella/components` is still to answer.


## The order of work

**The suggested order of work**, each step seen running before the next: the full text of a cut-off cell shown in place; the list scrolling while a selecting drag is past its edge; and the bar last, with the menu as its first use.


## FujiList

**The full text of a cut-off cell, in place.** When the pointer rests on the text of a cell that is cut off, the whole text shows exactly over it, in the same face at the same place, so it seems simply to carry on past the edge while the rest of the row stays where it was; a right-aligned value grows to the left, its right edge on the column's. Windows calls this an in-place tooltip, "used to display text strings for objects that have been clipped," with text "identical to the complete label text, and normally is the same size and font," placed to overlay the label, shown after the tooltip delay, by default "the user's double click time and is typically about one-half second," and gone on a click or when the pointer leaves ([in-place tooltips](https://learn.microsoft.com/en-us/windows/win32/controls/implement-in-place-tooltips), [tooltip controls](https://learn.microsoft.com/en-us/windows/win32/controls/tooltip-controls)); the list view does it with `LVS_EX_LABELTIP` ([extended list-view styles](https://learn.microsoft.com/en-us/windows/win32/controls/extended-list-view-styles)). AppKit calls it an expansion tooltip: when the mouse "is hovered over the text," "the full contents will be shown in a special floating tool tip view," off by default on a control and recommended for a table's text fields, `allowsExpansionToolTips` in the macOS SDK's `NSControl.h`. Open: the delay, Windows' half second or at once, once Finder and Explorer are watched on their machines; and the look, the row's own background, so the text reads as carrying on, or a tooltip's border and shadow.

**Scrolling at the edge at a speed a person can steer, an innovation.** While a drag selects past the list's edge, the list scrolls faster the further past the edge the pointer goes, smoothly, so a user can creep a row at a time or race to the end and everything between. Explorer's does not: its scrolling jumps from too slow to the whole list at once, with nothing in between, and no file manager is known to get this right. What others do, read 2026-10-29: GTK 4's list views scroll while the pointer is within 30 pixels inside the edge, faster the deeper it goes into that margin (`SCROLL_EDGE_SIZE` in `gtklistbase.c`); Qt scrolls within 16 pixels of the viewport's edge, its [`autoScrollMargin`](https://doc.qt.io/qt-6/qabstractitemview.html); VS Code scrolls only for drag and drop, in a 35-pixel zone at up to 14 pixels a frame. A write-up on Windows 11 says that past Explorer's top or bottom edge "a small overshoot scrolls more slowly than a large one" ([Geek Rewind](https://geekrewind.com/select-multiple-files-with-a-selection-rectangle-in-windows-11/)), which differs from what the user sees and is checked on the Windows box.

**No ellipsis, an innovation.** The list cuts off text too long for its column and draws a line on the edge beside that row, where other lists draw an ellipsis. An ellipsis takes a lot of width right where space is tight, and it makes the reader stop and wait, as though a speaker were about to go on, which pulls attention away from the list.

**Shading the sorted column.** Explorer fills the column the list is sorted by with a very light gray that is still noticeable, and Finder does not. What fuji's list does is open, a choice for one list on every platform.

**No candy stripes.** Finder shades alternate rows a little apart down the whole list, and fuji's list does not, since the stripes read as old computer paper.

**The highlight colors, each platform's own look.** The user's choice on 2026-11-19, which replaced one accent on every platform. The Mac's strong blue shows only on the Mac, the same in light and dark; Windows' pale blue shows only on Windows and Linux; and in dark, Windows and Linux have no color at all in a selection or a menu. Every value comes from a platform, its grays set on the ladder. On the Mac, a selected row with the keyboard and a menu's row under the pointer are filled solid in the accent, `#0064e1`, the Mac's own selection blue, with white words; it was the user's to change, `accent.color` in `fuji.toml`, until that setting was removed on 2026-11-19, since a user's color could not follow Windows' pale look without a tint worked out from it. On Windows and Linux a selected row with the keyboard is Explorer's pale blue, `#cce8ff`, in light, and `gray-600`, `#525252`, in dark, two notches darker than Windows 11's own `#626262` so the text reads on it, and without the light cyan line Windows draws around it, each with the text's own color; a menu's row under the pointer is white in light and black in dark, across the menu with a gray line around it, so a menu there has no blue in it. A selected row without the keyboard is a quiet gray, `select-quiet`, the Mac's own on every platform, since Explorer's light one is not to be told from it and its dark one is too faint to read. The row the keyboard is on has a solid line around it, black in light and white in dark, as Windows 11 draws its own, in place of the dotted rectangle it had before. MockMenu, the right-click menu, still lights its rows in the accent everywhere, until it becomes one of FujiBar's menus. `pnpm color`'s Accent Colors tab shows all four, the Mac and Windows each in light and dark, as A, B, C and D. The stylesheet's essay says why the platforms' own colors were set aside in October and why they came back. Windows 11 added a border around selected items in a 2024 update ([Eleven Forum](https://elevenforum.com/t/the-blue-outline-in-file-explorer-suddenly-started-appearing.35226)). The desktops' sources below are kept for the List and Tree article. What the desktops' own sources say, read 2026-10-28: GNOME's libadwaita, on Debian, Fedora and under Ubuntu's theme, fills a selected row in a view with the accent mixed 25 percent over the view's background and leaves the text its usual color ([_views.scss](https://raw.githubusercontent.com/GNOME/libadwaita/main/src/stylesheet/widgets/_views.scss), [_colors.scss](https://raw.githubusercontent.com/GNOME/libadwaita/main/src/stylesheet/_colors.scss)), with the blue accent `#3584e4` over `#ffffff` in light and `#1d1d20` in dark ([css-variables.md](https://raw.githubusercontent.com/GNOME/libadwaita/main/doc/css-variables.md)). KDE's Breeze selects in `#3daee9` in both light and dark, with white text and no separate color for an inactive list ([BreezeLight.colors](https://invent.kde.org/plasma/breeze/-/raw/master/colors/BreezeLight.colors), [BreezeDark.colors](https://invent.kde.org/plasma/breeze/-/raw/master/colors/BreezeDark.colors)). Mint-Y's source selects in its accent, `#35A854`, with white text in both ([_colors.scss](https://raw.githubusercontent.com/linuxmint/mint-themes/master/src/Mint-Y/gtk-3.0/sass/_colors.scss)), though Mint 22.2 made the accent the user's choice. Ubuntu's Yaru selects in orange, hex not found.

**Each column's sort breaks its own ties.** When a header sorts the list, rows that tie, files of the same size or the same date, need an order among themselves. The sort a column plugs in brings its tie-breaker with it, so the same click always gives the same order, however the user arrived. For instance, Size and Date may break ties by name, in fuji's name sort and in the direction the column is sorted: a list sorted by Size from largest down holds its tied files in reverse name order, and reversing a sort turns the whole list over, ties included. The spreadsheet's way, a stable sort of the order already on screen that makes the column sorted before the second key, is the one Microsoft documents for Explorer's list view, and it suits a table a person is studying, where the sorts they clicked through are layers they built. In a file listing the order of earlier clicks is usually an accident, so tied files would land in an order nobody chose, which changes with how the user got there.

**Rename in place, and rename with the arrow keys, a showcase.** The list renames a file where its name is, and how a rename begins is open: a key, F2 in Explorer and Return in Finder; a click on the name of a row that is already selected, which both file managers take as a rename after a pause; and the timeouts that tell that click apart from the start of a double-click and from a drag. Under the list's rule for selecting and carrying, where every part of a row does the same thing, that click would be anywhere on a selected row rather than on its name. The keys and the pauses are from memory, and are checked on each machine as the rename is built. Two ideas are transplanted from XYplorer and attributed to it: while renaming a file, the up and down arrows move the rename to the file above or below, and the I-beam cursor keeps its column as it goes, so the whole listing behaves like a text editor. Brilliant, and copied. Before the article names XYplorer for it, its own documentation is checked for what it does and what it calls it.

**Space on a folder goes into it.** Once the list shows a folder's subfolders beside its files, space with the keyboard on a subfolder opens it, rather than toggling it into the selection as space does on a file. Neither file manager does this, from memory: Explorer opens a folder with Enter and space only selects, and Finder's space is Quick Look.

**Update when the pointer is away.** Chrome's tab strip set the standard: close a tab and the rest could all widen, and they do not until the mouse leaves the strip, so the next click lands where the last one did. A control whose contents move under the pointer turns every click into a chase after a herd of targets, and the experience is awful. So when rows are flowing into a sorted list, say a list sorted by Name with the pointer resting over a patch of A names while more names arrive in bursts over seconds, the rows under the pointer hold still. The list shows that it is stale with a mark beside the sort column's header, an asterisk on the sort, essentially. When the pointer moves away, to that header or anywhere else, the list is free to update, the new rows take their places, and the mark goes.

**Media details in the margin, a showcase.** It is a section of the List and Tree article in its own right. A file manager's grid has Name, Date, Size and Type, and no place for the one more thing a media file knows about itself: an image's dimensions, a song's or a video's runtime, a video's bitrate. Windows answered with a gazillion more columns and a way to customize each folder's view, and that design is a disaster from end to end. The user does not know how to get there. Arriving, they find fifty columns they have never heard of and not the one they need. They add one, and the columns no longer fit the display. When the view is finally right it belongs to that one folder, not to the folder beside it holding the same kinds of files, and the moment they move the files out, the work is useless. It is so high-maintenance that nobody did it. Fuji knows that solution and kept inventing to avoid it, and the article says so, loudly. `FujiList` notes a file's one useful extra detail in the whitespace of a wide column, pinned to the right margin, and the details are hand-picked rather than everything a file could carry, the few fundamentals media files share: runtime for audio and video, dimensions for images and video.

**Sizes, said the way the user picks, a showcase.** Still open: Kilo follows Explorer from memory, and is checked against it on the Windows box; a way that matches Finder's joins the choices, since Finder and Explorer do not agree on what a kilobyte is, also from memory; and a palette could code the unit like the metals of credit cards, where platinum outranks gold: KB blue, MB silver, GB gold, TB platinum, or something near it.


## Selecting and carrying in FujiList, an innovation

**A press on a row that is not selected selects, and a press on a row that is selected carries.** Dragged from an unselected row, anywhere in it, a press selects the rows it passes over; dragged from a selected row, it carries the whole selection, to a subfolder, to the tree, or out of the window once the list drags files. So a file is dragged by selecting it first, a click and then a drag. `_listSmear` and `_listCarry` in `list.js` are the code.

**Why: every part of a row does the same thing.** Finder and Explorer drag an unselected file pressed on its name or icon, and select from the space beside it. Where a name ends cannot be seen, so the place that drags grows and shrinks with each name's length: a long name is almost all drag and a short one almost all select, and a folder of short names behaves differently from a folder of long ones. Here the one thing that decides is what the user can see, whether the row is highlighted.

**How it differs from Finder and Explorer, slightly.** Like both, a press on a selected row drags the selection. Like Finder's list from beside a name, and Explorer's rectangle from blank space, a press elsewhere selects, but here from anywhere in the row; what each does is from memory, and checked on each machine as the article is written. Unlike both, an unselected file cannot be dragged in one motion. The difference fails safe: a user who presses a name expecting to move the file gets a highlighted run, nothing moves, and the next drag carries it. The opposite slip, a drag meant to select that drops files into the folder beside them, is the costly one, and this rule cannot make it.

**The pointer while carrying is the closed hand for now, a spike.** It is CSS's `grabbing`, which every engine draws in its own way, and it does for trying the carry. What it becomes is open: pointers fuji authors and brings along, drawn to look good beside the system's own on Windows and the Mac, or the plain pointer with something floating beside it, like a count of the files being carried.


## FujiTree

**The tree stands on a panel.** A tree beside the content is Zed's panel.background, One Light's #ebebec and One Dark's #2f343e, which joins the palette when the tree paints it, with its tint taken out as every gray's is, #ebebeb and #343434, and a name for its job.


## FujiTree's keys beyond the arrows

**Type-ahead.** Typing the start of a folder's name moves the selection to the next folder on screen whose name starts with it, as the list's `_listFind` does.

**`*` opens every folder at the selected folder's level.** The ARIA tree pattern lists it as optional; Windows shows all subfolders with Num Lock and the asterisk; Finder's Option-click on a triangle opens every folder within.


## The tree's right-click menu

**A right click on a folder in the tree opens a menu for that folder**, as a right click in the list opens one for what it selects.


## Dragging between fuji, the list and the tree

**A drag goes into and out of fuji, between the list and the tree, and within one list or one tree.** The happy path is a user selecting files in the list and dropping them on a folder, in the list or in the tree.

**Dragging out of the tree is open**, until what Explorer does there is checked on the Windows box.


## Remembering which folders were open

**The tree keeps which folders the user opened**, since Apple's guidelines ask that expansion choices be retained and Microsoft's that they persist, so `fuji.toml` is where they go.


## Spacing and sizes

**The tree's behaviors that `tree.js` says are from memory are checked on the Windows box** against the classic Win32 tree.

**A text size setting, later, picks the row height and the icon size from a short table of whole numbers.** On Windows it follows Windows' own text size setting, which fuji does not obey yet; on the Mac it is an option of its own or none. No combination the table offers may collide or look bad.


## Publishing updates to the list and the tree

**Rows arrive gradually, the way search results fill in, and the structure underneath changes**, as when something else changes a drive the tree is showing, or a torrent's files fill in as they download in a sister project that shows them in the same components.

**App code says exactly what changed, and nothing compares the whole.** `listAdd` takes a batch of rows and places each in the current sort and filter; `listChange` takes a fresh record, which finds its row by its identity and takes that row's place, moving it if the sort says so; `listRemove` takes identities alone, since a deletion often carries nothing else. The tree's own versions do the same under a parent named by its identity. Each call costs the rows it names and their places in the order.

**A folder the app has not read yet still shows its twistie.** Its record says it has folders inside, `branch` beside the `children` it does not have yet; opening it fires `onOpen`, and the app reads the disk and hands the folders over with the tree's add.

**A batch costs one sort.** Fuji's sorts are comparators, so a row finds its place by binary search, and a burst of rows lands in one pass rather than a sort per row.

**A record crosses a boundary as a fresh object**, from Rust, from a watcher, from another peer, which is why a row is found by the identity it carries rather than by being the same object the list was handed.


## The light table's menu

**The light table is headed toward having no context menu, and its menu has not been taken out yet.** A menu shows which row is under the pointer by lighting it, and in fuji's fullscreen on the Mac the page hears none of the pointer's moves, so the highlight cannot follow and the menu looks broken; the fullscreen essay in `window.rs` says why. Today a right click on the light table still opens its menu, from `onMenu` in `DiamondTable.vue`.

## FujiBar

**Microsoft's trail, and its high points.** Microsoft's habit, per version of Windows and per version of Office, was to make the next version look different so people would see value in it, and the result over the years was a meandering and worsening design. The bar copies the high points that stand out from that trail.

**One face.** The bars, a menu a bar opens, the list, the tree and the sheet all stand on one color, `face` in `style.css`: `#fcfcfc` in light and `#222222`, `gray-825`, in dark, the same on every platform. The user's choice on 2026-11-20, so no part of a window is a slightly different white or black from the part beside it, and the list and the sheet, which are to become interchangeable and mixed in some views, are already on one ground. In light it is the white the web engine on Windows paints a scrollbar's track in, measured that day on Windows 11, which replaced Zed's `#fafafa` under the content and the pure white of the bars and menus. In dark it is a step from Finder's list, `#212121`, and nine steps lighter than File Explorer's, `#191919`; it replaced Zed's `#2c2c2c`, nineteen from Explorer's, which the user saw as charcoal beside both. One Dark has no darker ground to give, so in dark the face follows the platforms. The two file managers are eight steps apart, so one gray cannot sit within a step or two of both, and for part of 2026-11-21 the face was each platform's own, `gray-825` on the Mac and `gray-875` elsewhere. The user put it back to one the same day, on seeing the two dark faces together on the color page and not being able to tell them apart: seven steps near black, in panes that do not touch, could not be seen, so the rule bought nothing. Only the face moved: the other dark grays were each set for their distance from `#2c2c2c` and still are, and whether they follow it down is open. Measured on the Mac mini on 2026-11-20, in sRGB, for what stands around the face there: Finder's list, toolbar and title bar are `#ffffff` in light and its sidebar `#ebebeb` to `#efefef`, moving with the wallpaper; in dark its sidebar is `#282828` to `#2b2b2b`. The title bar macOS draws over fuji is `#ffffff` in light, over fuji's `#fcfcfc` bar, and `#282828` in dark, six steps above fuji's bar. A toolbar in Zed is editor.background too, the same as the content it sits over, divided from it by Zed's border and not by a change of color. Until then the bars took the title bar's color on Windows, white and black, as Windows 10's own programs do, and a menu's face was pure white and pure black for a day; Windows 11's title bar is a material tinted by the wallpaper, `#ecf6f9` when measured, and cannot be matched, so fuji leaves it alone. The palette called it `background`, Zed's word, until 2026-11-21, and the bars and menus reached it by names of their own, `--bar-ground` and `menu-face`, from when they could differ from the content; now each names `face`. On Windows and Linux a menu's row under the pointer stays pure white in light and pure black in dark, a little purer than the menu around it, told from it by its gray edge.

**The lines stay Zed's.** Every line fuji draws, under a bar, between the tree and the list, under the list's header, is `border`, `#c9c9c9` in light. Windows 11's own window edge was measured as a candidate to copy and set aside: it is a translucent line over the window's shadow, and read from `#999999` to `#bbbbbb` around one window in one screenshot.

**A scrollbar's colors are fuji's, its shape the engine's.** The track is transparent, so it shows the face, and the thumb is `scrollbar` in `style.css`, the engine's own grays on Windows set on the ladder, `gray-450` in light and `gray-400` in dark. `scrollbar-color` sets those two and nothing else: the arrows take the thumb's color, and under the pointer Windows' engine darkens the thumb to seven tenths of it, where the Mac's does not change it at all and has no arrows, in light as its own does, and in dark where its own brightens, which was accepted so the track would be fuji's and not move when the engine's does. `style.css`'s essay has the measurements. On the Mac the engine takes the thumb's color too, and a transparent track leaves nothing there, seen in fuji on 2026-11-20 and again in screenshots the next day; Finder draws a track of its own and fuji has none on any platform. Not seen on Linux.

**Square, while it is built.** Every edge in the bar is square, which is simpler and more exact to work against, and corners are easy to round at the end; the list and the tree keep their rounded selections.

**The Internet Explorer 3 coolbar, from the mid-1990s.** Its buttons were flat until the pointer floated over one, and then an outline appeared around the button. The user could click the moment the border appeared, without even looking for the pointer, because the border said where the pointer was. That is the hover behavior for `FujiBar`'s buttons: flat at rest, outlined under the pointer, and really, really usable.

**The menus of Microsoft's software around 2003**, Visual Studio 2003 or Office 2003, for their appearance. Click a menu title and the title does not move. A card that is the menu, with its title still at the top, shaped like a skyscraper with a house on top, is set forward, drawn with a simple one-pixel outline, and casts a light shadow on everything behind it. The shape tells the user at once where they are and what they can choose next, and it looks really good. The user's screenshots of Windows Explorer and Office 2003, on Windows XP in its classic look, were measured, and they inform the bar's arrangement, weight, size and capability rather than being copied as fixed rules; `FujiBar.vue` says what it took from them and where it departs, as the open title keeping the bar's color rather than darkening.

**Heights are said as L plus css pixels.** L is the line height the UI font comes out at, and the rest is measured in css pixels: the menubar's row is L + 10, and a toolbar's row of big buttons L + 40.

**A big button is square or wider, never narrow.** Most buttons share one aspect ratio, and a button with a long label gets wider, which is rare.

**The command under the pointer lifts.** Beside its outline, its drawing moves up and to the left and casts a sharp shadow down onto a plane, as in the screenshots, so the user sees Cut or Folders or Undo or Delete lifted, ready to strike.

**Open in the bars.** Each of these was raised while the bars were built and none is decided.

- **Menu row height.** The rows come out at fractions of a pixel, L + 10 being about 25.96 with Segoe UI at 12, since L is the font's own. Claude suggested pinning them to whole multiples of 4, 24 for the menubar, as `style.css` does the list's rows.
- **Keys.** Menus take no keys yet: no Escape, no arrows, no Alt or F10, no underlined letters. The shell's own bare keys, h, g, v, t and u, still act while a menu is open, and an Escape while the list has the keyboard goes to the list and not the menu, so the keys need a decision in the shell. `fuji-bar-dsl.md`'s Access keys and Menu engineering sections hold the research.
- **Not there yet.** Shortcuts beside a menu's rows, whose syntax is still to come; submenus opening from a menu's row; split buttons; a menu that would run past the window's right edge; and buttons with a drawing and no words.
- **MockMenu.** It still draws the right-click menus on the sheet, the light table and the bench's list. Claude suggested moving them to FujiBar's `menu` kind, opened from code as `barShow` in `fuji-bar-dsl.md` sketches, and then removing MockMenu.
- **A menubar off the Mac.** `menu.md` says the main window gets a toolbar on every platform, not a menu. The bench shows a menubar on every platform while the bars are designed, and leaves it out on the Mac at the end. Whether Windows and Linux get a menubar in the real window, and whether it takes Alt, was asked and not answered.
- **Faded at rest**, seen in the screenshots and not asked for. Office 2003 draws its icons lighter at rest, outlines `#4d4d4d` and not black, as if 30 percent toward white, and at full strength only under the pointer.
- **Dropped on the press**, the same. A lifted command could drop back without its shadow as it is pressed, so the strike shows.
- **Screenshots not yet looked at.** The user's green guides, Windows Explorer and Office 2003 on Windows XP in its classic look, are on the Windows 10 box in `C:\Documents\with-claude\fuji-bar-guides`, a folder the user has opened to Claude. Four other pictures there, a Chrome menu, a glass menu, a Windows 10 menu and list, and balloons, have not been looked at.


## A key and a menu item send the same word

**The text that defines the bars declares each item's shortcut, and FujiBar turns the key into the item's word**, so a key and a menu item arrive at one onCommand identically, and a shortcut is written once, beside the item it chooses. The item on the light table's menu that closes the window would carry Esc, and pressing Esc would send that item's word just as choosing the item does. Until then a key and an item each have wiring of their own that ends at the same function, so no behavior is written twice, only the routes to it.

**A context menu declares shortcuts it does not show.** Apple and Microsoft both say a context menu shows no keyboard shortcuts, so the text can give an item its key while the menu on screen shows only the item's name.


## Icons

**FujiBar starts with Lucide, by name.** The text that defines the bars names each icon by its Lucide name. A bundler cannot see which names a string holds, so fuji keeps a roster of the icons in use, imported by name, and only those reach the build.

**Still to be seen on Windows.** Whether the icons draw sharp at 125 and 175 percent, where their square starts half a backing pixel off the grid and the code relies on WebView2 snapping plain layout to whole pixels; and that they draw as sharp in dark as in light.

**Color in light, monochrome in dark.** In light the bar's drawings take a few colors, and in dark every drawing is in the text's own color, so the user picks the look by picking light or dark: dark for fuji calm around the pictures, as Lightroom is, and light for a colorful file manager, as Windows Explorer is. The user's choice, 2026-11-19, which replaced a plan for fuji to choose by what it showed, a colorful toolbar while no thumbnails were on screen and a monochrome one while they were; this way nothing switches as the view changes, and the palette needs colors for light alone. Lucide is just a shape, unlike icon libraries with white sheets of paper, blue ink and manila folders, and that is liked: fuji should be more like the Mac, whose toolbar is not a circus, and less like Windows, where Microsoft assumes there is no color in the user's document and brings the fun itself. So in light some color on the drawings makes them expressive and shows their grouping: Delete red, Undo green, Back, Forward and Up blue, Folders manila yellow.

**The drawings' palette, off the shelf or made.** Crayons in a box: distinct colors that work mixed together in any combination, not five shades of one color, with at least two distinct colors of each named color, like three kinds of orange, a pumpkin, an amber and a sunflower. First described as calm classroom tones, neither too saturated nor too muted, and on 2026-11-19, after seeing 82 palettes, as bright colors, strong, numerous, distinct, classroom fun. Eventually a whole family, several of each of red, orange, yellow, green, blue, purple and brown, not the same number of each, for light alone, since dark is monochrome. The box is for doing the choosing once: any few crayons taken out and drawn beside each other are seen and told apart, though not every pair in the box need be, and after that coloring a drawing is picking the second blue crayon.

**A box, not a grid.** Most palettes are a grid, a few hues times a ladder of lightness, and the ladder is the part fuji has least use for. What it wants is the flat set, where each color was chosen against the others, as Catppuccin's Latte was, only larger. The hope was to inherit one whole from a team that spent years on it, and nothing is chosen: after a survey of interface palettes, chart palettes and editor themes, and a second of crayons, toys, transit maps, pixel artists' palettes and the icon palettes of old systems, the user found no obvious choice, some too small, some too light, some too sparse. So the few colors fuji takes may come from one box or several, or the box may be fuji's own, built from their parts. `pnpm color` shows the work: the color page's Button Color tab draws every palette whole, with who made it and what for, and FujiBar's own toolbar and the edit menu in its colors, and its Crayon Boxes tab picks a sample box from each by measurement, in light.

**What the two surveys found.** A grid is not a box: most palettes are a few hues times a ladder, where nobody checked one hue's step against its neighbor's. One row across a wide grid is a box, and the grids that hold every hue to one contrast, Carbon, Spectrum and Primer, make the worst ones, since along a row only hue is left to tell two crayons apart. The first survey, interface palettes, chart palettes and editor themes, was the wrong water, each sober, small or pastel on purpose. The second came closer. Crayola is the right spirit, with the most browns, and a third of it is too pale for a thin line on white. Google Calendar's 24 was made for a small mark on white picked from a row of others. Pixel artists' palettes are ramps for shading, half darks and pales, with bright middles; Famicube and Resurrect 64 gave the fullest boxes, and Resurrect's the most even. KDE's Oxygen is the richest palette written down for icons, under a license that forbids commercial use. Windows XP's icon colors are the bar's own era, and are seven blues with no purple, pink or teal. And every old guideline for small icons paired its palette with an outline, black on the Mac, black below and right on Windows, a darker shade of the fill later; Lucide's drawings are a line and nothing else, which is much of why every palette looks weaker on the bar than in its swatches. `desktop/color/upstream.js` holds the 82 palettes, each with who made it, its license and where its values were read, and `crayon.js` beside it picks each sample box. The seven research reports behind them are in the transcript of the session of 2026-11-19 and nowhere else; they also hold values the color page does not draw, Apple's colors for dark, all of Fluent's ramps, Gmail's grid, and the old guidelines' own words on outlines.

**Open in the palette.** Nothing is chosen.

- **The box.** Claude suggested giving up on a finished box and building fuji's own on the color page from the best parts, starting from Resurrect 64's or Famicube's box for brightness and spread, borrowing browns from Crayola or Oxygen, and checking each addition by the same measurements. Not answered.
- **Line or fill.** Under each sample box are four rows, the drawings as lines at 24 and 16 css pixels and then again with a quarter of the crayon's color filled inside, a trial. Claude suggested settling how a drawing carries color, a fill or a darker outline, before choosing crayons, since it changes which ones are strong enough. Not answered, and a fill across an open shape like an arrow's head has not been looked at closely.
- **The picking rule.** `crayon.js` holds every pair in a box at least 0.09 apart in OKLab, stricter than the user asked. Its limits, a floor of 1.6 to 1 against the face, the gap from the text's color, the least chroma, the lean toward strong colors and a box of at most 24, are Claude's and have not been reviewed, and the hue ranges that name a crayon's family are rough. It passes over a palette's best known red for a neighbor a hair farther from everything else, so every box is a first pass for a person to change.
- **Too light.** The floor lets in crayons under the 3 to 1 the accessibility guidelines ask of a drawing, so a box can have a yellow, and marks them pale. Whether fuji draws anything that pale is not decided.
- **Names and licenses.** Crayola's, LEGO's and Transport for London's names are trademarks, fine on the color page and not as fuji's own names for colors; pixel artists' colors have no names, only places in a list. ## Fuji's own icons

**Fuji draws an icon of its own where the system's cannot say what fuji means, and where the system gives none.** Folders told apart by what they hold come first, an empty folder above all, which Finder on macOS 27 seems to mark already with a sheet of paper inside a folder that holds something, seen by the user and not found written up anywhere. A fallback is another: where the system gives nothing, which is every kind on linux today, an extension Windows refuses as one no file could have, and any failure, the square shows cyan until fuji's fallback takes its place. A made-up extension and a file with no extension already get the system's generic document on the Mac and on Windows, which copper's tests check.

- **Where they live.** Fuji's own icons are assets bundled with the page, so none crosses into the Rust. The cache gives each the same number and css rule a system icon gets, with the rule pointing at the asset's url rather than at a png copper made, and the list and the tree see no difference.
- **PNG at 16, 32 and 64 pixels square, for the designer.** 16 is exact at 100 percent, the default on Windows and most linux and on a Mac's 1x monitor, and 32 at 200 percent, every Retina Mac and Windows and linux at 2x. Between them, at 125, 150 and 175 percent, the engine shrinks the 32, and above 200 it shrinks the 64, which covers every scale up to 400 percent where a 48 would have to be stretched; CSS's `image-set()` names the three and lets the engine pick for the display. The 16 and the 32 are the ones to tune by hand, where a pixel off shows, and the 64 comes straight down from a master at 256, the large size the system folders a design might start from carry on both the Mac and Windows. Larger sizes join the three only if fuji draws icons larger than a row's. PNG rather than SVG for that tuning, which an SVG drawn by the engine at 16 and at 20 loses.
- **Light and dark.** The system's icons are the same in both, measured on the Mac mini, and fuji's would either be drawn to sit on both backgrounds or come in two, which the rules would switch with the theme.
- **Telling folders apart** takes knowing what each holds, which the list and the tree learn from the disk as the app reads it, so that icon follows the app's record rather than the system's kind.
- **Where the artwork comes from** is the question in Color where fuji is a file manager: drawn for fuji, or a set under a license the GPL can carry.

## System icons on Linux

**Fuji asks no system for icons on linux yet, so every row there keeps the cyan square.** What the desktops offer, from memory and not yet checked on the Linux machine:

- **Standard names.** The freedesktop Icon Naming Specification names `folder`, `text-x-generic` for a plain file, and `image-x-generic`, `video-x-generic` and `audio-x-generic`, the counterparts of the Mac's generic kinds and Windows' stock icons, and the major themes draw them.
- **Per type.** The shared MIME database maps an extension to a type like `application/pdf`, whose icon name is `application-pdf`, and names a generic icon like `image-x-generic` for a theme without the specific one. GIO, already in copper, does the mapping.
- **The lookup.** GTK's icon theme finds a name in the desktop's chosen theme, Adwaita on GNOME and Yaru on Ubuntu, Breeze on KDE, Mint-Y on Cinnamon, and Raspberry Pi OS's own, falling back through the theme's parents to hicolor. It belongs on GTK's main thread, where the Mac's and Windows' calls run on the blocking pool.
- **The flatpak** sees its runtime's icon themes rather than the host's, so without the matching theme installed for flatpaks it may draw Adwaita's icons on a KDE desktop. The deb and the rpm see the host's.
- **Minimal setups,** a window manager with no full theme, fall back to hicolor, which may hold no file type icons, and there fuji's own fallback icon draws instead.
- **Coverage differs by theme,** Adwaita having dropped many of its old full-color icons in recent releases, so how each theme looks at 16 pixels is to be seen on each desktop.
