# Security

<!-- draft of 2026-10-15: the history, which the half on how Fuji is built will follow. Every link was fetched on 2026-10-15 by the research behind this page; each claim marked verify still needs checking against its source before the page is published -->

For twenty years the most serious attacks on personal computers and phones have arrived inside ordinary files, a JPEG, a song, a font, a GIF, and gone to work the moment a program read them to be helpful: to draw a thumbnail, index a folder or preview a message, before anyone chose to open anything. Each of those attacks worked through a few facts about how a computer runs a program, and each defense that held was built from the same facts. Fuji reads files by the thousand to show them, so its design starts from this history.

## What a decoder does

A file is a row of bytes, and a format is an agreement about what they mean. A decoder is the program that keeps its side of the agreement: it reads the bytes in order and does what they say. Much of what they say is numbers about the rest of the file: this picture is 640 pixels wide, this block of compressed data is 4,096 bytes long, the next table starts 12,000 bytes further on. The decoder cannot know those numbers are true until it has acted on them, and whoever made the file wrote every one.

Most decoders are written in C or C++, chosen for speed and because they run anywhere, and those languages do exactly what the code says, including the wrong thing. If a decoder sets aside room for 640 pixels and a later number in the file makes it copy 700, the extra bytes are written into whatever memory comes next. That memory belongs to something else: other data, the note of where the program goes when the current function returns, or the address of a function it is about to call. Microsoft's security bulletins call this a buffer overrun. The file's author chose the extra bytes, and when they land on an address the program is about to use, the file has chosen what the program does next. Languages that check every access to memory, Rust, Swift and Java among them, cannot make this particular mistake; a program written in one stops instead.

A decoder also decides for itself what kind of file it is reading, and it decides from the bytes rather than the name. Most formats begin with a signature: a JPEG starts with the two bytes `FF D8`, and a PNG with eight bytes that spell out `PNG` among them, as [the PNG specification](https://www.w3.org/TR/png-3/) lays out. <!-- verify: fetch the PNG specification and link its signature section --> Programs that read pictures look at those first bytes, so a picture renamed `.txt` still opens as a picture, which is a convenience for anyone whose files have lost their names. It also means a name protects no one. Microsoft answered the question of whether blocking a dangerous extension would help in [its bulletin of January 2006](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2006/ms06-001):

> The Graphics Rendering Engine does not determine file types by the file name extensions that they use. Therefore, if an attacker alters the file name extension of a WMF file, the Graphics Rendering Engine could still render the file in a way that could exploit the vulnerability.

## Looking was enough, 2004 to 2011

In September 2004 Microsoft fixed a buffer overrun in GDI+, the code that Windows XP, Office, Internet Explorer and the .NET Framework all used to draw JPEG pictures ([MS04-028](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2004/ms04-028)). The bulletin's list of ways in ran from a web page to an email shown in the preview pane, a picture inside an Office document, and a folder on a network share previewed in Windows Explorer. It also said, "There is no way for an attacker to force a user to open a malicious file," which was how security was still described in 2004: a person had to open something. The list above it showed that opening had stopped being something only a person did. A mail client previewed, a file manager drew thumbnails, and each read a stranger's file on behalf of someone who never chose it.

The Windows Metafile came next. A WMF is a recording of drawing commands from 16-bit Windows, replayed to draw the picture, and one of its records, `SETABORTPROC`, handed Windows a function to call while a print job spooled, the job [the `SetAbortProc` call](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-setabortproc) does for a program that prints. In a file from a stranger, the function was whatever the stranger supplied. <!-- verify: the exploit's mechanism, that the record's function pointed into the file's own data --> It was being exploited before any fix existed, and Microsoft's fix of January 5, 2006, [MS06-001](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2006/ms06-001), repaired no bounds check: it removed support for the record from WMF images. Google Desktop Search, which read a computer's files to index them, reached the bug without anyone opening anything, and the Windows Search team [cited it a year later](https://brandonlive.com/2007/06/20/faq-why-does-wds-windows-vista-use-so-many-processes/) as the reason their own indexer reads files differently, which the next section comes to.

Looking at a folder stayed enough for years. In 2010 Windows ran code when it displayed the icon of a crafted shortcut ([MS10-046](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2010/ms10-046)), and Stuxnet, the worm built to damage industrial centrifuges, spread through it on USB drives, infecting machines [according to CISA](https://www.cisa.gov/news-events/ics-advisories/icsa-10-201-01c) "after users open a USB drive with a file manager capable of displaying icons." <!-- verify: a source for Stuxnet's target, the centrifuges, or drop the clause --> In 2011 it was a thumbnail ([MS11-006](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2011/ms11-006)).

## Walls and fuzzers, 2007 to 2016

The first answer was to stop trusting the code that reads. Every program on a computer runs as a process, and the operating system decides what each process may touch: which files, the network, other programs. A decoder that runs inside a program has everything that program has. A decoder moved into a process of its own, with almost nothing allowed, can still be fooled, but the code that fools it inherits almost nothing. Windows Search was built this way in Windows Vista: its filters run in a separate process with reduced privileges that ["cannot even read the filesystem"](https://brandonlive.com/2007/06/20/faq-why-does-wds-windows-vista-use-so-many-processes/), handed each file's contents by the indexer. Google built Chrome around the same idea and described [its sandbox](https://blog.chromium.org/2008/10/new-approach-to-browser-security-google.html) in October 2008: the code that reads web pages and their pictures runs in processes that cannot reach the rest of the machine. <!-- verify: the 2008 post's body, which did not load; Chromium's sandbox design document says the same --> And Explorer moved thumbnail drawing out of its own process into a helper, because, as [Raymond Chen put it in 2009](https://devblogs.microsoft.com/oldnewthing/20090212-00/?p=19173), "Explorer has learned not to trust thumbnail extractors." The name for this is a sandbox, and its rule has since been written down by Chromium as [the Rule of 2](https://chromium.googlesource.com/chromium/src/+/main/docs/security/rule-of-2.md): of untrustworthy input, code in an unsafe language, and a process with high privilege, a program may combine any two and never all three.

The second answer was to find the bugs before anyone else did, by machine. [Fuzz testing](https://google.github.io/oss-fuzz/) feeds a decoder millions of files made by changing real ones a little at a time, and watches for a crash; the fuzzers in use today also watch which parts of the decoder each file reaches, and keep the files that reach somewhere new, so they work their way into code nobody thought to test. In January 2014 Google reported [1,120 fixes](https://security.googleblog.com/2014/01/ffmpeg-and-thousand-fixes.html) in FFmpeg, the free library that reads and decodes hundreds of audio and video formats, from its own fuzzing, and advised people to "refrain from using either of the two projects to process untrusted media files", meaning FFmpeg and Libav, a fork of it. <!-- verify: the context of the "refrain" sentence in Google's post --> In December 2016 Google opened [OSS-Fuzz](https://google.github.io/oss-fuzz/), started in response to Heartbleed, which fuzzes open-source projects around the clock; by August 2023 it had helped fix "over 10,000 vulnerabilities and 36,000 bugs across 1,000 projects." FFmpeg's own history holds more than three thousand fixes that cite an OSS-Fuzz test case. A number like that says two things at once: the project is examined more closely than almost any other code that reads media, and that close examination keeps finding more.

## No click at all, 2015 to 2017

In July 2015 Joshua Drake of Zimperium showed that Android's media library, Stagefright, could be taken over by a video sent in a text message ([Zimperium](https://www.zimperium.com/blog/experts-found-a-unicorn-in-the-heart-of-android/), [CERT](https://kb.cert.org/vuls/id/924951)). Android's messaging app fetched an MMS attachment and handed it to Stagefright as it arrived, to show a preview, so "the worst of which requires no user-interaction," on an estimated 950 million devices. Google's response, in Android 7, split the media server into separate processes with no camera, microphone or network, because ["media parsers do not require access to most of the privileged permissions held by mediaserver"](https://android-developers.googleblog.com/2016/05/hardening-media-stack.html), and later moved the software decoders into a process of their own after counting that about [80% of 2018's critical and high media bugs](https://security.googleblog.com/2019/05/queue-hardening-enhancements.html) were in them.

In November and December 2016 Chris Evans did the same to Linux desktops with music from old game consoles. A crafted NES music file took over Ubuntu ["without the user opening the exploit file -- they only have to navigate to the folder"](https://scarybeastsecurity.blogspot.com/2016/11/0day-exploit-compromising-linux-desktop.html), because the file manager's thumbnailer read it, and he named it `.mp3`, since the media framework "will ignore a file's suffix and use file format auto detection." A web page could drop a file into the Downloads folder, where Fedora's search indexer, Tracker, [read it on its own](https://scarybeastsecurity.blogspot.com/2016/11/0day-poc-risky-design-decisions-in.html), and a SNES music file named `.flac` [took over Fedora 25](https://scarybeastsecurity.blogspot.com/2016/12/redux-compromising-linux-using-snes.html) the same way. His conclusion was that "Code that automatically indexes or thumbnails media files really needs to be sandboxed in this day and age," and GNOME did it: Tracker's extractor got a sandbox [within weeks](https://download.gnome.org/sources/tracker/1.11/tracker-1.11.2.changes), and every thumbnailer ran in one from [GNOME 3.26 in 2017](https://www.hadess.net/2017/07/security-for-security-gods-sandboxing.html), with no network and nothing of the file system but the one file. Tracker's extractor also learned to give each file [five seconds](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract.c), and to write down which file it was reading before it began, so a file that crashed or stalled it is [never read again](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract-decorator.c).

Some formats point at other files, and that turned out to be a door of its own. A playlist lists the files it plays, and a video streamed over the web is a playlist of short segments. In January 2016 Maxim Andreev showed that a playlist hidden in a file "with any extension: avi/mov" could make FFmpeg read a file from the same computer and send its first line to a web server, ["when file manager tries to generate thumbnail"](https://seclists.org/oss-sec/2016/q1/85), and in 2017 Emil Lerner and Pavel Cheremushkin made an AVI read a local file and draw it into the video's own picture ([their proof of concept](https://github.com/neex/ffmpeg-avi-m3u-xbin)). FFmpeg answered with lists of what a file may reach, and its fix admitted that leaks remained possible ["from files and symlinks ending in common multimedia extensions."](https://github.com/FFmpeg/FFmpeg/commit/189ff4219) The same year Check Point took over VLC, Kodi, Popcorn Time and Stremio, about 200 million installs between them, through [subtitle files](https://research.checkpoint.com/2017/hacked-in-translation/), the small text files that ride along with a film.

## Around the wall, 2020 to 2023

In March 2020 Microsoft warned of a bug in how Windows read a kind of font, reachable by looking at a document in Explorer's preview pane, and added that on Windows 10 an attack ["could only result in code execution within an AppContainer sandbox context"](https://api.msrc.microsoft.com/sug/v2.0/en-US/vulnerability?$filter=cveNumber%20eq%20%27ADV200006%27), so it advised Windows 10 users not to bother with the workarounds. That is a sandbox doing its job: the bug was the same, and what it could reach was not.

Apple built one for the iPhone's messages. iOS 14 moved almost all the reading of untrusted data in iMessage into BlastDoor, a [tightly sandboxed service written in Swift](https://projectzero.google/2021/01/a-look-at-imessage-in-ios-14.html), a memory-safe language, and slowed its restarts too. That needs a word about how attackers work around a modern operating system. Computers now load each program at a randomly chosen place in memory every time it starts, so an attacker who can overwrite an address does not know what address to write; one way through is to guess, crash, and guess again. BlastDoor's supervisor doubles the wait before restarting it after each crash, up to about twenty minutes, so guessing takes years.

Attackers went around the wall instead. In March 2021 Citizen Lab examined the phone of a Saudi activist infected with NSO Group's Pegasus spyware, and in [September they reported](https://citizenlab.ca/2021/09/forcedentry-nso-group-imessage-zero-click-exploit-captured-in-the-wild/) what they had found in its backup: thirty-one files named `.gif`, twenty-seven of them 748-byte Photoshop files and four of them PDFs. Apple fixed the bug the day Citizen Lab published. Google's Project Zero [took the exploit apart](https://projectzero.google/2021/12/a-deep-dive-into-nso-zero-click.html) in December. iMessage handed any attachment ending in `.gif` to a service outside BlastDoor, which passed it to ImageIO, Apple's picture library, and ImageIO chose among "over 20 image codecs" by the contents, "completely ignoring the file extension." It found a PDF, and inside it a JBIG2 stream: "a domain specific image codec designed to compress images where pixels can only be black or white." JBIG2 can refine a region of the picture by combining bits with AND, OR, XOR and XNOR, and those four operations are enough to compute anything. Once a bug in the decoder let the file write past its buffer, "over 70,000 segment commands defining logical bit operations" built "a small computer architecture with features such as registers" and "a full 64-bit adder and comparator," inside a picture decoder, and that small computer ran the rest of the attack. Project Zero called it "one of the most technically sophisticated exploits we've ever seen." Apple narrowed what that service accepts and moved GIFs into BlastDoor.

Two years later Citizen Lab caught another one, [BLASTPASS](https://citizenlab.ca/2023/09/blastpass-nso-group-iphone-zero-click-zero-day-exploit-captured-in-the-wild/), in pictures inside PassKit attachments, the passes of Apple Wallet, and Chrome fixed a bug in the WebP picture library, reported by Apple and Citizen Lab, for which ["an exploit for CVE-2023-4863 exists in the wild"](https://chromereleases.googleblog.com/2023/09/stable-channel-update-for-desktop_11.html). <!-- verify: that BLASTPASS and CVE-2023-4863 are the same libwebp bug --> Fonts kept their place on the list as well: FreeType, the library that draws text on Android, Linux and much else, had one bug used in a [Chrome exploit chain in 2020](https://www.cve.org/CVERecord?id=CVE-2020-15999) and another in 2025 that ["may have been exploited in the wild"](https://www.facebook.com/security/advisories/cve-2025-27363), with ["limited, targeted exploitation"](https://source.android.com/docs/security/bulletin/2025-05-01) on Android.

## Bugs found by machines, 2025 and 2026

Fuzzers now have company. In 2025 Google's Big Sleep, an AI system built to find vulnerabilities, was credited in a dozen of FFmpeg's fixes, among them a heap overflow in its reader for [OpenEXR](https://www.cve.org/CVERecord?id=CVE-2025-59733), the format of film effects houses, and a use-after-free write in its decoder for [SANM](https://www.cve.org/CVERecord?id=CVE-2025-59734), the video format of LucasArts games of the 1990s. FFmpeg's developers answered in public that the SANM bug touched "the first 10-20 frames of Rebel Assault 2," and called such reports ["CVE slop"](https://itsfoss.com/news/ffmpeg-google-fiasco/); <!-- verify: FFmpeg's own posts, which the research read only as reported by It's FOSS and The New Stack --> FFmpeg's [security page](https://ffmpeg.org/security.html) now says "Automated submissions are not accepted." The bug was real, a write to memory already freed, and any program built with every decoder carries the SANM decoder whether or not anyone owns a copy of Rebel Assault 2.

In June 2026 JFrog published [PixelSmash](https://jfrog.com/blog/pixelsmash-critical-ffmpeg-vulnerability-turns-media-files-into-weapons/), an out-of-bounds write in FFmpeg's decoder for MagicYUV, a format for recording video without loss, and tried it on the programs that scan media collections. It ran attacker code through the library scan of Jellyfin, a home media server, with the memory randomization described above turned off, and crashed it reliably with randomization on. It corrupted another server's memory, Emby's, and the process exited as if nothing had happened. And it did nothing to Plex, whose FFmpeg is built "with decoders disabled" and "a minimal allow-list." The bug was fixed in FFmpeg 8.1.2.

These attacks are rare, and the record says how rare. The United States' Cybersecurity and Infrastructure Security Agency keeps a [catalog of vulnerabilities known to be exploited](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json), 1,746 entries in October 2026, and it lists no bug in FFmpeg; the research behind this page found no public report of one used in the wild. The attacks above that did happen in the wild were aimed at particular people, an activist's phone among them. A collection of downloads holds far more files that are simply broken, truncated by a dropped connection or damaged by a dying disk, than files built to attack anything, and a program that reads collections meets the broken ones every day.

## What twenty years show

A name decides nothing. Every decoder in this history chose what to run from the bytes, and every attack that mattered used a name that looked harmless.

The attacks land on software that reads files to be helpful: a preview pane, a thumbnailer, an indexer, a message that shows its attachment as it arrives. Nobody chose those files, so nobody was there to hesitate.

Decoders written in C and C++ have bugs, and fuzzers and now AI systems find them by the thousand. A library examined this closely has its bugs found and fixed in public, one release after another; a library nobody examines keeps whatever bugs it has, known only to whoever finds them first.

Walls work. A decoder in a sandbox can still be fooled, but the code that fools it reaches only what the sandbox allows, as Windows 10's font sandbox showed, and the systems that read untrusted files at scale, Windows Search, Android's media server, GNOME's indexer and Apple's BlastDoor, all put the reading in a separate process with almost nothing allowed. And attackers go around walls: FORCEDENTRY reached the one decoder left outside.

A crash is a signal, and its absence is not. A fooled decoder can exit cleanly, as Emby's did, so a program that reads untrusted files cannot judge them by whether its reader survived. And a file that once crashed or stalled the reader is remembered and not read again, which keeps a scan moving and denies an attacker a second try.

No wall is perfect. GNOME's thumbnail sandbox had [a hole of its own](https://cveawg.mitre.org/api/cve/CVE-2019-11460), no sandbox stops a bug in the operating system's kernel, and the best defenses raise the cost of an attack from one bug to several; none makes it impossible. That is the ground Fuji is built on.
