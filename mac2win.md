# To the Windows box: the recipe is Python now, the library has a ledger, and the video moves

Written on the Mac mini, 2026-10-15. Read this, then talk to the user before changing anything; a letter starts a conversation rather than settling one. The recipe landed on the Mac and in the Linux containers that day; the one thing only this machine can answer about it is in the second section. The audio panel's video, which moved on the Mac the day after, comes next, a section added on 2026-10-16 is the icon Explorer shows on the videos and sounds fuji now registers, the one added on 2026-10-17 is transparency: two steps in WIC that may lose it, and what should show through a transparent picture, the one added on 2026-10-20 is ergo: an install to run first, and three pieces of the build that only this machine compiles or runs, and the last, added on 2026-10-21, is the video window: what it does, the roads in it that have never run here, and how far Windows lets a window be dragged past the edges of the screen.

## What changed since you last built the library

`desktop/libmpv/build.sh` is gone and `desktop/libmpv/build.py` is the recipe, the same twelve packages with the same flags in the same order, ported line for line; on the Mac and in both containers the Python recipe produced the same library bytes as the shell one except for one thing, the shell spelled the prefix path as `desktop/libmpv/../src-tauri` and Python resolves it, and mpv and FFmpeg write that path into the binary, so every library's hash moved once. Yours will too, from `a6d92d7b…`, and that is expected. The command is `pnpm library` now, in desktop as before, and `libmpv.js` starts the recipe with `/usr/bin/python3` under MSYS2's login shell instead of bash, and installs one more MSYS2 package, `python`, the first time.

Each package is built under a stamp that chains the one before it, so a change anywhere rebuilds everything after it, and on your first run every stamp is new, so the whole twenty minutes runs once. Beside the dll the recipe writes `libmpv.json`, the record: the library's hash and size, the moment, the recipe's own hash, the compilers, and every source with its hash. And it appends the same record as an entry to `library-win.txt` at the repository root, the ledger, which git tracks; `library-mac.txt`, `library-amd.txt` and `library-arm.txt` beside it already hold today's entries from the Mac and the containers, and yours is the one empty one. `pnpm hash` refuses a library whose record does not name the checked-out recipe, a library in `binaries` that is not the one its record describes, an installer older than the library's record, and a library with no entry in its ledger, so the order on your machine is `pnpm library`, `pnpm installer`, `pnpm hash`, `pnpm upload`, then a commit that carries the sidecar and the ledger.

## The one question for this machine

Which Python runs the recipe. MSYS2 carries two: the native one meson brings into the ucrt64 environment, which spells a path as `C:\Users`, and MSYS2's own in its POSIX layer, `/usr/bin/python3`, which spells it `/c/Users` and converts arguments for the native programs it starts, the way bash did. The twelve projects' configure scripts want the POSIX form, so `libmpv.js` names `/usr/bin/python3`, and the recipe takes its own location from `Path(__file__).resolve()`, so every path it hands to configure, meson and cmake is in that form. That is reasoned from MSYS2's documentation and not run, and the first `pnpm library` here is the test. If a configure script or meson refuses a path, the recipe's `environment` block and its `run` helper are where a path is spelled, and `cygpath` is on hand in MSYS2 to convert in either direction; a fix goes there, with a comment saying why, where the next reader of the recipe will find it.

## What to look at when it runs

At the end it prints the dll's size and hash and says `and in library-win.txt`. Then `pnpm installer` and `pnpm hash`, which should accept, and `pnpm upload`. The sizes to compare: the dll was 48,202,240 bytes and the installer 20,842,016 on 2026-10-12, and neither should move far. The dll's hash is the one number nobody can predict from here, and once it is in the ledger, running `pnpm library` a second time with nothing changed should compile nothing and append nothing, which is the check that the stamps hold on this machine too.

## The audio panel's video moves now

The video region in the audio panel now takes the playing video's shape, along the top for a wide video and down the left for a tall one, with the panel's lines scrolling beside or below it. `window_video_place` in `window.rs` moves and resizes the native video window to the region whenever the panel lays out, and hides it while no video shows; here that is `SetWindowPos` and `ShowWindow` on the child window `window_video_make` makes. It type-checks against this target from the Mac, in a scratch crate without Tauri, and has never run.

Two things only this machine can show. mpv draws in a window of its own inside the one fuji hands it, and resizes it to match through a hook it puts on that window's thread, read in mpv's `video/out/w32_common.c` and not yet seen at work: a video that keeps its first size, or stays in the corner, while the region moves would mean the hook misses a move fuji makes. And at 125 or 150 percent the panel's 10-pixel inset lands on a fraction of a backing pixel, which the Mac's 1 and 2 never do; the page rounds the video's rectangle to whole backing pixels, so a thin line of the page along one edge of the video, or a pixel of the blue frame under it, would be that rounding. Every placement is a line in the log, `audio: video placed at`, with the box in CSS pixels and the rectangle in backing pixels.

To see both, `pnpm local`, press `a`, drop a wide video and then a tall one, and resize the window; the blue frame and the divider are there to show the edges.

## Transparency, through WIC and on both views

On the Mac the native road keeps a picture's alpha, but ImageIO's thumbnail reads a little of the color hidden under fully transparent pixels. Measured on the Mac mini on 2026-10-17: a white disc on transparent pixels hiding bright green came back with green at its edge, up to 24 levels of 255 as it composites, on 130 of the thumbnail's 2,588 edge pixels, though no pixel of the file with any opacity carries green. Most transparent PNGs hide black, so on the Mac that is a faint dark rim. Windows has two steps in `render_com` in `thumbnail.rs` where Microsoft's documentation says nothing about alpha, and both run on a PNG's straight alpha:

- **The Fant scaler.** PNG offers no scaled decode, so Fant shrinks the frame in its own 32bppBGRA. If it averages those colors without weighting them by alpha, the hidden color bleeds into every edge, and more strongly than on the Mac.
- **The color transform.** A PNG carrying an ICC profile goes through `IWICColorTransform` into 32bppBGRA, and whether alpha survives it is undocumented. If it does not, the transparent area comes out as the hidden color.

Two files show both, made with ImageMagick and exiftool, which `winget install --id ImageMagick.ImageMagick -e` and `winget install --id OliverBetz.ExifTool -e` bring if this box lacks them. The first is the white disc with bright green hidden under its transparent pixels and nothing else in the file, and the second adds Windows' own sRGB profile, which changes no color:

```
magick -size 1200x1200 "xc:rgba(0,255,0,0)" -fill white -draw "circle 600,600 600,100" -define png:exclude-chunks=cHRM,gAMA,sRGB,bKGD,tIME,tEXt,zTXt,date PNG32:disc.png
exiftool -q "-ICC_Profile<=C:\Windows\System32\spool\drivers\color\sRGB Color Space Profile.icm" -o disc-profiled.png disc.png
```

Open their folder on the contact sheet. A green rim plain at a glance around either disc means Fant averages straight colors, and a green or black square behind the profiled disc means the transform drops alpha. If either shows, the fix is converting to 32bppPBGRA before the scaler, the format Microsoft recommends for 8-bit WIC pipelines on its Direct2D bitmap source page, and letting the final converter to 32bppRGBA unpremultiply, as the Mac's code already does. A table shows a PNG through the engine on both platforms, so the two files test the sheet alone.

What should show through the transparent and partly transparent parts of a picture is the view's own ground, which the user has decided and nothing yet does. On the Diamond Table that is the dots, which pan with the picture and keep their size as it zooms; today the card's `bg-well`, `--color-well` in `index.css`, sits behind every picture instead, near white in light and near black in dark. On the contact sheet it is a repeating background that stays fixed as the sheet scrolls; the sheet's ground is plain paper today, with no pattern. This box is the harder place to get transparency right, so the correction is made and tested here.

## Ergo, and the three pieces only this machine builds

Since 2026-10-20 the root `package.json` has a dependency, ergo, and every workspace takes ergo 0.1.3 from npm, whose `Data` and `sha256` the pipeline's hashing now goes through. So after pulling, run `pnpm install` at the repository root before any other command: with the old install, `build-log.js` cannot find what it imports, and every script that imports it, `scripts.js` and `win-setup.js` among them, stops before it starts. The pipeline's own code is the same on every machine, and on the Mac that day it built, notarized, hashed and uploaded the dmg and the four Linux packages, each checked by downloading it back; what follows is only what this machine alone runs.

- **blake3, through Microsoft's assembler.** Ergo 0.1.3 brings blake3 into desktop's `Cargo.lock`, with sha1 and sha2 a generation newer than the sha2 in Tauri's tree, so the lockfile holds both. Nothing calls them yet; they compile because the crate is there. When the target is MSVC, blake3's build script assembles its x86-64 SIMD code from `.asm` files with `ml64.exe`, which comes with the Visual Studio Build Tools that give Rust its linker and `win-setup.js` its C compiler. Clang on the Mac and gcc in the containers built it on 2026-10-20, and nothing has built it with MSVC. A failure would show in blake3's build script during `pnpm installer`, and is a conversation with the user, since ergo is the user's own project and the fix may belong there.
- **The Windows half of `memory.rs`.** `installed()` turns the firmware's kilobytes into bytes with ergo's `size::KB`, behind `#[cfg(target_os = "windows")]`, which no machine has compiled. The memory table under the buckets on the contact sheet shows the result, and its This computer has row should read the installed memory it read before.
- **`win-setup.js` and the Windows path of `libmpv.js`.** Both now run an async `main` that ends at `main().catch(...)` with the 🚧 line, and their finished lines in `build-log.txt` carry a hash ergo wrote. On the Mac `win-setup.js` returns at once and `libmpv.js` takes its Mac path, so neither Windows path has run. `pnpm installer` exercises the first, and the exe's finished line should carry the hash `pnpm hash` then prints for `fuji.exe`; the second waits for the recipe's first run here, in the sections above.

## The video window, and how far Windows lets a window go

Since 2026-10-21, v on the contact sheet opens a video window, `VideoWindow.vue`, a native window of its own on top of fuji's other windows, the workspace the video viewer will be built in, which shows only the word VIDEO and a Close for now. `App.vue` picks a window's root as its page mounts, from a note Rust holds for a window a page asked for: the new command `window_new` makes the window with the note, and `window_note` hands the note to the new page. The essay atop `VideoWindow.vue` is the rule, and `window-check.md` at the root describes how every window behaves as the user meets it, platform by platform, which is the background for everything below. All of it was built and smoke tested on the Mac mini, and none of it has run here.

What the video window does, all of which this machine should match:

- It has no title bar, so the page fills it, and it appears at 800 by 600 CSS pixels at a new random place in the work area every time, placed by `rectSheet`, and fuji remembers nothing about it.
- Opening and closing it leaves the main window exactly where and as it was, and every v on the sheet opens another, so several can be open at once.
- A double-click takes it into fuji's own fullscreen, and another brings it back at the same size and place.
- A drag from anywhere on it moves the window, once the pointer has moved 4 CSS pixels with the button down.
- Esc closes it, as its red button would if it had one, and so do v and the Close beside its name. Its title, which the taskbar shows, reads "Video - Fuji".

Four things only this machine can show, each with the reason it might go wrong here:

- **Two windows in one process, which fuji never had here.** Until now every window on this machine was a launch's first, in a process of its own. A video window opened from the sheet is a second window in the main window's process, joining the WebView2 already running there. `window_new` is an async command whose body runs on the blocking pool, because Tauri's documentation of `WebviewWindowBuilder` warns that building a window from a synchronous command or an event handler deadlocks on Windows; that warning is the reason, and it is untested here. Everything Rust keeps per window is keyed by label, the note, the players and the native video windows, and gets a second entry for the first time on this machine. To see it, press v on the sheet: a video window should appear on top within a moment, with nothing hanging. Press v there to close it, and v on the sheet twice for two. Then close the main window with a video window still open, and fuji should keep running until that last window closes, and then be gone from Task Manager. And resize the main window, open a video window, close the main window and then the video window: the new size should be in `fuji.toml`, which fuji writes when the process's last window closes.
- **Fuji's fullscreen from the video window.** Here `isFullscreen` reports fuji's own fullscreen, since tao's simple fullscreen is the ordinary one, where on the Mac it reports only a Space. The video window keeps its own record of fuji's fullscreen and asks about a Space only on the Mac, so a fullscreen video window here is never taken for one, and it leaves fuji's fullscreen through `windowFullscreenLeave`. To see it, double-click the video window: it should fill the screen with no taskbar. Double-click again, and it should be back at its size and place. Double-click into fullscreen once more and press v, and it should close without the main window changing.
- **Snap, on the video window.** The drag is Windows' own: tao's `drag_window` releases the mouse capture and posts the window `WM_NCLBUTTONDOWN` with `HTCAPTION`, read in tao 0.35.3, so Windows runs its move loop as if the title bar had been grabbed, and Snap applies. A drag to the top edge should leave the video window maximized, and a drag to a side or a corner should snap it to a half or a quarter; none of it should touch the main window, and v should close it from any of them. The same move loop is why the drag waits for 4 pixels: once it begins, the release never reaches the page, as the audio panel found, so a drag begun on the press would swallow every double-click. A double-click on the video window that does nothing would mean that wait is not doing its job here.
- **How far a window goes past the edges of the screen.** This is the question the section was written for. The answers shape BigVideoWindow in `video.md`: a window with no title bar, bigger than the screen, that a drag from anywhere on the video carries off any of the four edges.

What is known, from documentation and reports. [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getsystemmetrics) `SM_CXMAXTRACK` and `SM_CYMAXTRACK` as "the default maximum width" and height "of a window that has a caption and sizing borders", which "refers to the entire desktop", and says "the user cannot drag the window frame to a size larger than these dimensions", while a window can override it by processing `WM_GETMINMAXINFO`. One [Windows 11 user reports](https://www.elevenforum.com/t/title-bar-can-no-longer-be-moved-off-screen.23050/) that a recent update stopped windows going above the top edge at all, with nothing official from Microsoft behind it. The Mac's answer, for comparison, is [Apple's documentation](https://developer.apple.com/documentation/appkit/nswindow/constrainframerect(_:to:)): whenever a window with a title bar is placed on screen or its size changes, AppKit moves it so its top edge lies on a screen, and cuts a resizable one to the screen's height, leaving its width and its horizontal place alone.

What the session on the Mac believes and has not seen: Windows lets a window go as far off the left, the right and the bottom as the pointer can take it, so long as the pointer stays off the edge, and the taskbar draws over whatever goes behind it. And since the grab can be anywhere in the video window, more of it can pass the top edge than a grab on the title bar allows, until the pointer itself meets the edge and Snap maximizes it.

The answers wanted, from this box's Windows 10, with the video window grabbed by its middle and let go before the pointer touches an edge: how far it goes off each of the four edges; whether Windows moves it back when the button comes up; whether the taskbar covers it or it covers the taskbar; and whether a drag of its border can make it bigger than the screen, which the metric above says it cannot. Whether fuji can set a frame bigger than the screen itself is BigVideoWindow's own question, and needs code to answer.
