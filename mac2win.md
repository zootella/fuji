# From the Mac to Windows: COM on threads that come and go

Written on the Mac mini, 2026-10-04, alongside the change that moved every waiting command's body onto Tokio's blocking pool. Read this, then talk to the user before changing anything; a letter starts a conversation rather than settling one.

## What changed

**Every command that waits now runs its body through `run_blocking` in `lib.rs`**, which hands it to `spawn_blocking`, Tokio's pool for blocking work. Until now those bodies ran on Tokio's worker threads, one per core, which live as long as the app. The essay above `disk_readdir` in `disk.rs` has the reasons and the costs. One of the costs lands on Windows alone, and one Windows body changed shape along the way.

**The blocking pool's threads come and go.** It starts a thread for each body that waits, up to 512, and retires one after ten idle seconds. The Windows thumbnail initializes COM on whatever thread it runs on, because WIC is a COM library. On the old workers that happened once per thread and never mattered. On threads that are created and retired all session long, an initialize that is never paired with an uninitialize is the thing Microsoft asks a program not to leave behind.

**So each render now pairs them.** In `thumbnail.rs`, `start_com` returns a `Com` guard whose `Drop` calls `CoUninitialize`, and `render` declares it first, as `let _com = start_com();`, so it drops last: every COM object — the factory, the decoder, the frame, and everything `render_com` builds — is released before COM is uninitialized, on every path out, the `?` ones included. A `CoInitializeEx` that answers `S_OK` or `S_FALSE` gets a guard; one that answers `RPC_E_CHANGED_MODE` gets none, since that call owes no uninitialize. Please read that code with a Windows eye before trusting it: the drop order is the whole of its correctness, and it was reasoned about rather than watched.

**Pairing them has a cost of its own.** `CoUninitialize` is documented to unload the DLLs COM loaded for the thread, so when the last render of a burst finishes WIC may be unloaded, and the next burst loads it again. Renders in flight together keep it loaded for each other, so this is per burst rather than per render, and nobody has measured it. Initializing once per thread and uninitializing from a thread-local destructor was considered and set aside: Rust may run those destructors under the loader lock, where Microsoft warns that `CoUninitialize` can deadlock.

**`panel.rs`'s Windows body changed shape.** Its `catch_unwind` closure became a plain `unsafe` block, since `run_blocking` now catches a panic for every command. Nothing else about it changed.

**The Windows render now takes its size from a fit.** Added 2026-10-05. `thumbnail_render` no longer takes a longest side; the page sends a fit's name, the beam, the screen's size and `devicePixelRatio`, and `render` in the Windows body reads the picture's shown size, runs `fit_size` from the new `fit.rs`, and gets an exact width and height in backing pixels from `target`, capped at the picture's own pixels. Its old `fit` function is gone. Two things here were reasoned rather than watched. The cap matters more on Windows than on the Mac, because WIC's Fant scaler will enlarge a picture if asked and ImageIO will not, so a small picture asked for at 150 percent would come back blown up if the cap were wrong. And the size for an EXIF orientation of 5 to 8 is worked out from the shown size and swapped back for the decode, the same as before, but through new code. The render also now sends back the picture's own size, and refuses one whose size WIC will not give.

Both Windows bodies were type-checked on the Mac against `x86_64-pc-windows-msvc`, copied into a scratch crate without Tauri on the same `windows` 0.62.2. Neither has been built with Tauri on Windows, and neither has run.

## What to check

- **A release build.** `pnpm compile` in `desktop`, which is the first time either body is compiled as part of fuji on Windows.
- **Thumbnails across idle gaps.** Open a folder of JPEGs and PNGs on the contact sheet, wait more than ten seconds so the pool retires its threads, then open another folder, a few times over. Every thumbnail should arrive, and the log should hold no `thumbnail:` errors that name COM or `CoCreateInstance`. If a render ever fails on a fresh thread and succeeds on a retry, the initialize is the first suspect. And compare the first thumbnail's `render` time after an idle gap with the ones that follow it, which is where reloading WIC would show; the site's thumbnail page has 65 ms for a 6000 by 4500 JPEG decoded alone, measured before this change.
- **Thumbnails sized by the fit.** A folder of JPEGs and PNGs at 125, 150 and 175 percent should look as it did, with some tiles one CSS pixel different, which is expected. Two things to look for: a small picture, smaller than the beam, staying at its own size rather than enlarged and soft; and the eight orientation JPEGs still upright and the right shape. Changing `fit` under `[thumbnail]` in `fuji.toml` to `RowFit` and back is a quick way to see the fit reaching WIC at all.
- **The panel's resolution.** The List view, `MyList.vue`, shows what `panelResolution()` answers; it should be the display's resolution as before, not `0 × 0`.
- **A table over a filling sheet.** Nothing pauses a bucket any more, so a folder opened while a table is showing fills the sheet behind it. On Windows, BMP, WebP and AVIF take the page route, which draws on the same main thread the table uses. Flip through large pictures while a hidden bucket of those formats fills, and say whether the flips hitch.

## Added 2026-10-06: the parable, the Mac's pool, and COM again

**The user's parable, which is the reason for this section.** Say research and caution find that the totally safe way to use an API is get, release, get, release, get, release. Code that does get, get, get, get, and a moment later lets an automatic release clean up, runs fine — and it is the common pattern. If we code the first way because we could not prove to ourselves that the common way was safe, fuji may run slower, and may fail in situations nobody meets, because it uses an API in a pattern its makers do not expect and do not test. So be careful which side of that line a change is on. The user thought of it when COM began to be initialized and uninitialized around every render, and it is the test both sections below were put to.

**On the Mac it came out on the side of the change, and the change is made.** ImageIO and CoreGraphics are C interfaces, but on macOS 15.7.4 both link Foundation and the Objective-C runtime, so something inside them may autorelease an object, and a blocking-pool thread has no autorelease pool to catch it: the object waits until the thread retires, which a thread kept busy by a long burst never does. Apple's guides say what to do. *Advanced Memory Management*: "If you … detach a thread, you need to create your own autorelease pool block," and a long-lived thread that may autorelease a lot should use pool blocks, "otherwise, autoreleased objects accumulate and your memory footprint grows." *Threading Programming Guide*: "long-lived threads should create additional autorelease pools to free objects more frequently." A pool per unit of work is what AppKit's main thread, `NSOperationQueue` and GCD all do, so it is the common pattern and fuji's bare threads were the unusual one. So `run_blocking` in `lib.rs` now runs every body inside an `objc2::rc::autoreleasepool` on the Mac, one pool per command, with the reasons in the essay above `pooled`; the pools `launch.rs` kept around its own bodies came out, and `panel.rs`, whose Mac body asks CoreGraphics and never had one, is covered with everything else. On Windows and linux `pooled` runs the body as it is. A test run on the Mac was built and set aside, because it would only say what this macOS does with these files; the documentation is the answer. Nothing here touches Windows.

**On Windows the parable points the other way, and that is what to re-evaluate.** Microsoft's convention is that a thread calls `CoInitializeEx` once when it starts and `CoUninitialize` once before it ends. Fuji initializes and uninitializes around every render, which is the get, release, get, release of the parable. The section above names one cost, read from the documentation and never measured: the last `CoUninitialize` may unload the DLLs COM loaded, so WIC may load again at the start of every burst. There may be others nobody has looked for, since this is not how COM is usually driven.

**Please research it the way the Mac side was researched — Microsoft's documentation first, then a measurement only where the documentation leaves a question — and then talk to the user before changing anything.** Three shapes to weigh, none of them checked:

- **Keep it as it is.** Correct as reasoned, its cost per burst unknown. The check above, comparing the first thumbnail after an idle gap with the ones after it, is where that cost would show.
- **Once per thread, from Tokio's own hooks.** Tokio's runtime builder takes `on_thread_start` and `on_thread_stop`, which run on every thread it makes, the blocking pool's included, and Tauri can be handed a runtime fuji builds, through `tauri::async_runtime::set`, before the app starts. Initialize in the one and uninitialize in the other, and each thread does COM's conventional pair once. Unlike the thread-local destructor set aside above, these hooks are ordinary code on the thread, which may keep them clear of the loader lock; that is the thing to confirm. The cost is machinery: a runtime of fuji's own in `lib.rs`, for one platform.
- **Keep the process's MTA alive.** `CoIncrementMTAUsage`, from Windows 8 on, called once at startup, keeps COM's multithreaded apartment alive with no thread holding it. What to confirm in the documentation is whether a thread that never initialized COM may then create and use WIC's objects in that apartment, the implicit MTA; if so, the renders need no initialize at all, and the DLLs are never unloaded between bursts.

Whichever wins, the comment above `Com` in `thumbnail.rs` and the section above in this letter should say why.
