# Scan

Scan is fuji's capability under the hood for asking a file what it is. Given a path, whatever the file's name, it answers what the bytes are, whether the file has a running time, and what size it shows at. Features up top will be built on it: a playlist editor's column of running times, a sheet or a table that places a file at its shape before its pixels arrive, and the overnight scan of a whole drive, which is the hardest of them and the one the design is measured against. This sprint designs the capability full stack, so that it is safe, quick and effective for each new feature that finds a use for it.

The overnight scan: fuji walks a drive of several terabytes, several million files collected over forty years and a dozen folders deep, unattended for about fifty hours, and asks its files whether they have a running time and what shape they show at. Sound and video have a running time; pictures and video have a shape. In the morning the user finds a computer that is not stuck, a fuji that has not crashed, and a machine no crafted file has taken over.

**Three tiers.** The scout, scan and play each read the file: the scout first, scan only for what the scout could not answer, and play whenever the collector watches. The scout is fuji's own reader in Rust, the crate in `scout/`, run on a file's first 64 KiB and at most one more slice: a shortcut that answers most pictures, sound and video from their headers, and whose answer says when it could not. Scan is mpv's player asking with no track selected and FFmpeg's demuxers alone, in a sandboxed process of its own, for the sound and video the scout could not answer; a picture the scout could not answer goes to the web engine instead. Play is mpv drawing the file for the collector, which reads it for itself whatever the tiers before it answered. The code fuji writes to read untrusted bytes is Rust, which no file can make write past its memory, and the C and C++ beneath it, the web engine and FFmpeg, are among the most examined code that reads files anywhere, each behind a wall.

## Decided

- **Scan is the name, in code and in prose,** the plain word rather than a longer form like scanner.
- **The page lists and asks, one file at a time.** It walks the drive and calls down once per file with its path, and the governor sets how many calls are in flight. Moving the listing into Rust, as the contact sheet's pages moved, comes later.
- **Scan is built for any bytes, and in practice asks fewer files.** The scan process is designed as though every file on the drive were handed to it, hostile ones included. What fuji actually hands it is narrower, to keep a night's work to files likely to answer. A file with an extension fuji knows for a picture, a sound or a video goes to the scout first. A file with no extension whose first bytes look binary rather than text, or whose name holds `jpg` or `jpeg` the way `file.jpg.2` or `file.jpg!2` does, is checked for a picture's signature. A file goes to FFmpeg only when its extension is a video or an audio extension on fuji's list. These rules cut the volume and stop FFmpeg reading text files as ANSI art; they are no wall against an attacker, who can name a file anything, which is why the scan process is built for any bytes all the same.
- **Pictures without an easy answer go to the web engine.** The page reads the file and lets the engine load it as an image, which reports its size after its orientation; on the Mac and Windows the engine's decoders run in its sandboxed content process. Every animated picture's running time goes this way, and so do HEIC, AVIF, a camera's raw file and every picture format the scout does not know. The operating system's thumbnailers, ImageIO and WIC, are not used for this, since they run in fuji's own process.
- **Media: mpv's player, asking with no track selected and FFmpeg's demuxers alone.** `media_probe` in `media.rs` makes a player for the one question, started with `track-auto-selection=no`, so the file opens and waits with no decoder started and nothing drawn, and with `demuxer=lavf`, `access-references=no`, `ordered-chapters=no`, `autoload-files=no` and `resume-playback=no`, so mpv's own readers for Matroska, playlists, edit lists, cue sheets and `mf` addresses never see the file and it reaches nothing beside itself. It answers the running time, the format and mpv's track list as JSON, with each video track's `demux-w`, `demux-h`, `demux-par` and `demux-rotation`. A frame is `media_frame`, its own player paused at the time asked, drawing nowhere, decoding in software, and `screenshot-raw` with the `rgba` format, which comes back already turned and with its pixels made square. Measured through the shipped library on the Mac mini on 2026-10-16, a fresh player per question, on 320 by 240 test clips: the probe in 2 to 15 ms and the frame in 2.5 to 11. That the container's headers alone carry the answers for media was measured through FFmpeg directly the same day: with decoders refused, MP4, MOV, Matroska, WebM, both AVIs, WMV, a Video CD's MPEG-1, a DVD's MPEG-2 with its pixels that are not square, an animated GIF, MP3, FLAC, Opus, WAV and AAC all gave the same running time and size as with every decoder; an FLV lost its size, and stills lost theirs, which the picture reader and the web engine answer instead. It was no slower, 0.85 ms a file against 0.88 to 1.03. The library keeps every decoder, for playback's breadth; scan's narrowing is a runtime option, so it changes without touching the recipe.
- **A DVD's shape comes from the scout.** With nothing decoded, mpv's probe of an MPEG-2 program stream has no `demux-par`: a DVD-style clip came back at 720 by 480 with no pixel shape, while its frame came back at 853 by 480, at 16:9. The scout reads the pixel's shape from the sequence header, and its `aspect` for a DVD flagged 16:9 is the frame's 853 by 480, grown by mpv's own rule, so the scout answers what the probe cannot without a decoder.
- **mpv's player, not a C file of fuji's.** Reaching FFmpeg directly needs C of fuji's own, compiled against FFmpeg's headers, since its structs change between versions, which means a change to the recipe and a rebuild on every platform. That C would be new, reviewed only by fuji, and doing what C most often gets wrong, sizing buffers from a width, a height and a stride a hostile file supplied; mpv's layer between the file and FFmpeg is more code, but examined for years by its maintainers, its own fuzzers, OSS-Fuzz and every player built on it, and its options keep its own readers off the file. Both put the same FFmpeg on the file and both go inside the same sandbox, so mpv is the safer of the two, and the simpler and more portable: no recipe change, no C of fuji's, one interface already declared and working on every platform. The speed difference is a millisecond a file at most: measured on the Mac mini on 2026-10-15 through the shipped `libmpv.2.dylib`, against 2,400 files already in memory, 400 media files of twenty kinds and 2,000 files from `node_modules` that are not media, FFmpeg directly took about 0.8 ms a media file, one mpv player reused 1.1, and a fresh player per file 2.5, against 36 to 60 ms a file of a night's disk; the files that are not media cost mpv 3.6 ms, with outliers past a second, and never reach it under the rules above.
- **No file reaches past itself.** `access-references=no`, `ordered-chapters=no` and `autoload-files=no` stop mpv following references, segments in other files and files beside it, and `demuxer=lavf` keeps mpv's playlist and edit-list readers off the file. In the scan process the file arrives through mpv's own `fd://` address as an open file, and the sandbox refuses every other open, so FFmpeg's playlist and concatenation demuxers fail to open their second file too.
- **Scan runs in fuji itself, started in a second role.** The same executable, given an argument, branches at the top of `run()` in `lib.rs`, before the panic hook, `window_launch` and Tauri, so it makes no window and no web view and never counts as a second launch. In that role it applies its sandbox, then loops: it receives an open file, calls the same asking code in `media.rs` that the page's in-process commands call, and writes the answer. That code loads a path today, and in the scan process it loads the `fd://` address of the file fuji handed over; a scan and a click share every line of the code beneath and differ only in the road there. The code only scan has is that loop, a few dozen lines; the supervisor in fuji's main process, which starts, hands over, times, kills, journals and replaces, about two hundred; the hand-over of an open file per platform, about forty each; and the sandbox per platform. The platform question is asked once, where a scan process is made. Fuji's Rust starts the scan process, keeps it and watches it; the page calls one command per path and never learns a process is involved.
- **The scan process is there for two jobs nothing else does.** It survives what fuji could not, and it is the narrow thing a sandbox can wrap. CVE-2026-107678, open against the FFmpeg fuji ships, is an MP4 whose tens of thousands of `pssh` boxes exhaust the stack in the MOV demuxer, which scan runs whatever is decoded; inside fuji that one file ends fuji, since a stack overflow in C is a crash Rust cannot catch, and in a scan process it is one answer. The process alone does not stop code an exploit runs, since an unsandboxed process has the user's rights, and the sandbox is what does.
- **A scan process lives for the night, never one per file.** Starting and stopping a process per file would spend the night on starting and stopping: fuji's own executable takes 28 to 40 ms to reach `main` on the Mac mini, measured on 2026-10-13, since the loader maps WebKit, AppKit and the media library first, against about a millisecond of FFmpeg's work for a file. A pipe round trip to a process already running costs 25 microseconds, measured on the Mac mini on 2026-10-15 over 100,000 requests of a path and a line, so handing it one file at a time costs the wire under three percent of the work.
- **Fuji opens the file and hands it over.** Fuji opens each file without blocking, so a FIFO cannot hold it, refuses anything that is not a regular file, and hands the scan process the open file rather than its path: across a Unix socket pair on the Mac and Linux, since an open file crosses a socket and not a pipe, and by duplicating the handle into the scan process on Windows. The scan process then needs no access to the file system at all. An answer is a line written from numbers, and fuji reads it as numbers and nothing else, since a subverted parser can exit cleanly and lie.
- **A hang and a crash are answers too.** When no answer comes by the deadline the page chose, fuji kills the scan process, answers that the file gave no answer in time, and starts another; a scan process spending processor time at the deadline is stuck on the file, and one waiting on a read is stuck on the drive. When the socket closes, the scan process crashed on that file, and fuji answers so and starts another. Killing a process is the one cancel that ends a demuxer's loop, and a read stuck in the kernel keeps only the dead process, which nothing waits for.
- **A file that hung or crashed a scan process is never asked again.** Fuji writes the path in flight to a journal before it hands the file over, the way GNOME's indexer keeps the path in a descriptor its watchdog holds across restarts, so even a crash of fuji or of the machine is attributed to that file. Never asking again also denies an attacker the many tries that wear down address randomization, and restarts slow down after repeated crashes, the reason launchd slows BlastDoor's.
- **A scan process is replaced every so many files**, about 500, so one subverted without crashing answers for only the files after it, as Immich replaces its ExifTool workers every 500 tasks.
- **A sandbox around the scan process, on every platform.** On the Mac, `sandbox_init` with a profile that denies opening files, writing, the network, starting programs and looking up the system's services, since a process with no network can still ask another program to open an address; Apple does not support custom profiles, and Chromium and Firefox use them. On Linux, Landlock denying the whole file system and a short seccomp filter against new sockets, starting programs and attaching to other processes, and inside the flatpak the portal's sandboxed spawn. On Windows, a job object, with a memory limit, no child processes and death with fuji, and a low integrity token, which stop writes and new programs and not the network, then an AppContainer, which stops the network too.
- **Broken files are the common case, and scan is built for them first.** A drive like this holds far more truncated, corrupted and mislabeled files than hostile ones: the 2 GB video that stops halfway, the download that never finished. Scan names them as it finds them, and the store it fills, paths, hashes and what scan found, records the broken beside the good, so nothing in fuji trips over the same file twice.

## What FFmpeg reports, and where it is wrong

Seen on the Mac mini on 2026-10-15, with Homebrew's `ffprobe`, which is FFmpeg 9.0.2 as the recipe builds it, and with a scratch program against the shipped library.

- **A format, and a confidence out of 100.** FFmpeg accepts a match above 25 and, on its last try, a weaker one, warning "misdetection possible". An extensionless JPEG scored 26 and a Video CD file 26, while sixteen JavaScript files came back as MPEG transport streams at 2, so a floor at FFmpeg's own line separates them, narrowly. For a still the codec is the answer and the format's name is not: a JPEG named `liar.png` reached FFmpeg's image demuxer by its name and was read as JPEG by its bytes.
- **A format that should not count.** FFmpeg's ANSI art demuxer read `LICENSE.txt` as a 640 by 400 picture lasting 0.2 seconds, at confidence 99, so which of FFmpeg's formats count as a picture, a sound or a video is fuji's to decide.
- **A running time a still does not have.** A JPEG came back at 0.04 seconds, one frame at FFmpeg's default 25 a second. PNG, BMP and TIFF came back with none, and an animated GIF with its own 2.0.
- **An estimate.** An mp3 with no Xing header is timed from its bitrate: 60.03 seconds for a 60.00-second file.
- **The shape a file shows at takes three facts beyond its stored pixels.** Pixels that are not square: a DVD-style 720 by 480 video whose pixels are 32 wide to 27 tall shows at 16:9, and Video CDs, DVDs and DV are full of them. A turn on a video: one stored at 320 by 240 with a quarter turn shows at 240 by 320. Both are in the probe. A JPEG's EXIF orientation is not: a quarter turn written into a copy of the test JPEG left the probe at 640 by 480, and FFmpeg reported the turn only after decoding the picture.
- **A truncated file often reports what its header promised.** Copies of the test media cut in half: an MP4 with its index at the end, the usual unfinished download, was refused with "moov atom not found", after FFmpeg had identified it as MP4, so the answer can say an MP4 that will not open rather than not media. An MP4 with its index at the front, a Matroska file and a VBR mp3 with a Xing header each came back at their full running time, 5.0, 5.02 and 60 seconds. An AVI came back at 2.53 seconds, its index rebuilt from what was there, and a CBR mp3 at 30.01, estimated from its size, both right. An MP4 whose second half is zeros, the way a torrent client leaves an unfinished file, came back whole, and a JPEG cut in half came back at 640 by 480. Reading every packet finds all of them, "partial file" from the MP4, "File ended prematurely" from the Matroska file, decoding errors in the zeros, and half the frames the mp3's header claims, but reading every packet is reading the whole file.
- **The cost is the bytes read.** FFmpeg reads 2 KB and doubles until it is confident, up to 1 MB (`PROBE_BUF_MAX` in `libavformat/internal.h`), so a file it cannot identify costs a megabyte, and then up to 5 MB more for the streams' details (`probesize`).

## Open

- **The test panel**, in fuji's interface, writing log files, to run the scout over a real collection on another machine.
- **Whether mpv's probe decodes anything.** mpv's FFmpeg demuxer finds a file's streams with `avformat_find_stream_info`, which can open decoders to fill in what a header leaves out, even with no track selected. A DVD-style MPEG-2 clip came back from the probe with no `demux-par`, which suggests nothing was decoded there, and passing `codec_whitelist` through `demuxer-lavf-o` would make sure; untested.
- **How the governor and the scan processes divide the work, with nothing duplicated.** The governor was written with the call that never ends in mind, and it can grow a deadline: past it, the place in the line is freed and the caller's promise fails. In the page that only stops the waiting, since a promise cannot be killed, while a process can be, by the operating system. Fifty hours over several million files is 36 to 60 ms of wall time a file against about a millisecond of processor time, so the overnight scan waits on the disk and one scan process keeps up; more help only on an SSD or a NAS, and hurt a spinning disk. Proposed and not yet adopted: the governor stays the only scheduler, and scan calls wait in its line under a resource name the way thumbnails do, so it alone decides how many run at once, in what order, and whether the line is paused; Rust keeps one scan process per call in flight, reusing whichever is idle, and never queues or decides how many, so the user's one scan process out at a time is the governor set one wide. The deadline is one number the page chooses, enforced at the lowest layer that can enforce it: for a scan call Rust kills the process and the call settles at the deadline as an ordinary answer, and for work in fuji's own process the governor's future deadline frees the place and stops the waiting. A run of timeouts on one drive says the drive is failing, and pausing that drive's name in the governor stops scan asking a dead disk. Handing a process several files at once waits until the walk itself moves into Rust, the way `find.rs` reads many folders per call.
- **Whether a file with no extension whose first bytes carry a media signature goes to FFmpeg**, by a short list of signatures of scan's own. With no extension to check it against, the scout's answer stands alone. It names a text file that opens with `MAC `, `ID3` or `MThd` as sound, while its text verdict, judged apart from every format, says the bytes are characters, so the answer holds both; a binary file that opens with AC-3's two bytes it names AC-3, with nothing in the answer to say otherwise.
- **An FLV's size with nothing decoded.** The one test file lost its width and height through FFmpeg with its decoders refused, and mpv's probe decodes nothing either. FFmpeg's FLV demuxer can take them from the file's own metadata, which the test file may not have carried; whether real Flash videos of the 2000s answer without a decoder, or FLV's decoder joins an allow-list, is untested.
- **A crashed scan process should leave no trace on screen.** On Windows the job object's flag against unhandled exceptions suppresses the crash dialog; on the Mac whether a windowless process of fuji's own executable that crashes puts up "quit unexpectedly" is untested, and a night of crashes must not leave a stack of them. And a scan process that never starts AppKit's application object should have no icon in the Dock, checked once it is built.
- **The scout in fuji's own process and in the scan process.** It runs in fuji's own process today, through `scout_tip` on the blocking pool, which its memory safety makes safe, and that is where the sheet would ask it to size a tile before the thumbnail arrives; inside the scan process it would gain the deadline a read on a dead disk needs.
- **Windows' order**: whether the job object and the low integrity token ship before the AppContainer, which leaves a subverted scan process the network until the AppContainer lands, and the AppContainer's own questions, the read and execute grant on fuji's install folder and whether an executable that imports user32 and WebView2 starts inside one.
- **What kinds of broken scan's answer names**, beside the scout's two: corrupted, a header breaking its format's rules where the scout needed them, and chopped, a header's length or offset pointing past the file's end. One read at the end a header claims, to tell a file that holds less than its header promises, is untried.
- **The confidence floor, the formats that count, and the probe's limits**, `formatprobesize`, `probesize` and `analyzeduration`.
- **How fuji remembers a file that hung or crashed a scan process**, so it is never asked again. The user's first idea, a durable file of the failed files' hashes, raises three questions: what a file of hashes says about what the user has, whether a hash of part of a file could block a different file, and the cost of hashing every file before asking. Proposed and not yet adopted: no separate file and no hashing. The failure is one more answer in the row the store already keeps for the file, keyed by its path, size and modified time, the key the store uses to know a row still holds. The record says nothing the store does not already say, it lives in fuji's own data folder where it can be cleared, and it costs nothing beyond the listing's own read of the folder. A file that changes is a new file and gets one new try, and a copy at another path gets its own single try, which the slower restarts after repeated crashes still bound.
- **Where the shape the user gives a file is kept**, for a film whose pixel shape is flagged wrong and set right once, so it opens at its right shape the next time; the store scan fills is the likely home.
- **Whether a request names its question as well as its file**, so the same scan process can later make a thumbnail, or a still from a video, inside the same walls.
- **TGA, PICT and PCT, which only ImageIO reads.** Fuji opens all three, the scout names none of them, and no web engine reads them, so while ImageIO stays out of scan, a picture of these kinds has no road to its size. Each is reach 1.
