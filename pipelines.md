Three things, done together because they touch the same files: the map of what runs where, the move of the three shell scripts to Python, and a faster Linux run.

## Bash to Python

`desktop/libmpv/build.sh`, `linux/inside-tauri.sh` and `linux/inside-flatpak.sh` become `build.py`, `inside-tauri.py` and `inside-flatpak.py`. The recipe is the one that gains from it: the sources become a list of records, each package's build a function, every command a child process started with its argument list and its environment as data, the stamp a hash of the function's source and its flags, and the record written by the JSON library instead of a heredoc with quotes escaped by hand. The two container scripts translate line for line. Python is already on every build platform because meson is written in it, and the recipe already runs a short Python program inside itself on Linux; the flatpak image is the one place it has to be added, one line in its Dockerfile.

On Windows the recipe still runs inside MSYS2, where the compiler and the twelve projects' configure scripts live, and `libmpv.js` starts `python3 build.py` under it as it starts bash today. MSYS2 carries two Pythons, meson's, which writes paths as `C:\...`, and the POSIX layer's, which writes them as `/c/...`; the configure scripts want the POSIX form, so the recipe uses that one and is settled on the Windows box, which is out of scope for now, so Windows gets the Python recipe in the same shape and unproven.

`pnpm hash` hashes the recipe file by its path, so `scripts.js` points at `build.py`, and every record's recipe hash moves once. Every library's hash moved once too, and the whole difference is a handful of strings inside each: mpv and FFmpeg each write the configure line and the prefix into the binary, and the shell script spelled the prefix as `desktop/libmpv/../src-tauri` where Python resolves it to `desktop/src-tauri`. Found on the Mac mini on 2026-10-15 by comparing the libraries' strings, the Mac's two against each other and the arm64 one against the library inside that afternoon's deb. The Python recipe lands on its own hashes every time: the Mac's `622f89438d2fca1453b34b3f6234dcbea85e3d6e2165078f97e7b3df660085ed` three times from every package, arm64's `728a02d0775aa7ad182797e9624d9594f53e8e1ed18725ad95444154dcd1659b` and x86-64's `aa15cd4dbe30a7d354cb072734a496a827a658f84326240f104dc80e7c877c81` once each so far, the first entries in their ledgers. So a library's hash names the recipe, the tools, and the folder it was built in; the containers always build at the same path, and the Mac at this checkout's.

The constitution says every script here is Node with no shell or Python beside it, and the recipe has been the argued exception. Python for the build steps that drive other projects' builds is a change to that rule, and the sentence is the user's to write before the code lands.

## A faster Linux run

Today's run is 20 to 22 minutes on the Mac mini: three seconds for the images, about five minutes for the arm64 container, two of them the recipe and two Rust, about seventeen for the emulated x86-64 container, twelve of them the recipe and five Rust, and a minute for the flatpak, which needs the x86-64 deb first.

**Keeping the compiled library between runs** takes the recipe's twelve and two minutes out whenever the recipe is unchanged, which is most runs, since the recipe moves a few times a year and the code every release. Measured on the Mac mini on 2026-10-15: `pnpm library` compiled both libraries in 13 minutes 31 seconds, and the `pnpm build` after it, both containers taking their library from the cache, made the four packages in 8 minutes 46 seconds, against 20 minutes 50 seconds for the run that compiled them earlier the same day. The cache is a gitignored folder, `linux/cache`, mounted into the container as a third mount beside the source and the output, holding each architecture's `libmpv.so.2` and its `libmpv.json`. Before the recipe runs, the container uses them if the record's recipe hash equals the hash of the staged recipe and the library hashes to what the record says; after the recipe runs, it copies the fresh pair in. The key includes the toolchain image, as a hash of its layer digests, which `build.js` reads from docker and hands the container, so a `Dockerfile` that bumps a compiler is a miss; not the image's id, which docker changes on every build even with every layer cached, three ids from three builds of one unchanged Dockerfile on the Mac mini on 2026-10-15, while the layer digests stayed one. Nothing changes in `pnpm hash`, since the record travels with the library either way. A fresh library on demand is deleting the folder by hand. What it costs is one exception, argued by the record, to the rule that nothing survives between container runs.

**Running the two containers at once** is the other half, and the smaller one. The flatpak needs the x86-64 deb, so there are two paths at most, arm64 beside x86-64 with the flatpak after. Each container already uses all eight cores, so overlapping the arm64 leg with the long x86-64 leg saves about the arm64 leg's length against the two of them sharing the cores and the Docker VM's 7.6 GB, where two FFmpeg builds and two Rust release builds together would press on memory: three to five minutes off today's run, and one or two off the cached run. Whether this is done, and whether it is done at all once the cache is in, is open. Both are measured on the Mac mini, the cached run twice, once to fill and once to hit.

## The ledger

The library is compiled a few times a year once the cache is in, so every compile is written down where git keeps it. `pnpm library`, in desktop for the Mac and Windows and in linux for both containers, is the one command that compiles the library, and every run of the recipe that compiles anything appends an entry to one of four tracked files at the root, `library-mac.txt`, `library-win.txt`, `library-amd.txt` and `library-arm.txt`: the moment in UTC, the platform and architecture, the library's name, size and hash, the recipe's hash, the compilers, and one line per source with its hash or commit and its address, hashes whole. A run that compiled nothing appends nothing, and a build that lands on an earlier entry's hash still appends, since two entries with one hash on different days are the reproducibility proof. On the Mac and Windows the recipe appends; inside a container it writes the entry beside the record and `build.js` appends it, since a container never writes into the working tree. `pnpm hash` refuses a package whose library has no entry in its file, and `pnpm build` in linux refuses to run without a library in the cache, so no release carries a library the ledger does not know. The files are empty until the first `pnpm library` on each machine, which is the user's run at the end of this sprint, and the article's provenance section then points at them.

## What remains

Everything above is built, run and measured on the Mac mini, and the five packages the Mac publishes are live with their records in the sidecars: the four Linux packages carrying the Python recipe's libraries, and the notarized dmg carrying the Mac's, released the same evening. The Windows box runs `pnpm library` under the letter `mac2win.md`, which asks it the one question the Mac could not answer, which of MSYS2's two Pythons runs the recipe. The build also checks, before Tauri runs, that every library `libmpv.so.2` needs is declared by the deb's and the rpm's dependency lines, since meson links the distribution's optional libraries whenever the image has their headers and the lines are kept by hand; added on 2026-10-15 after a letter from the sister project, whose bare-image check of its frozen engine is the same principle shaped to a program that can be run. Running the two containers at once is not done: with the cache it would take about a minute off the 8 minutes 46 seconds, against the two cargo builds sharing the Docker VM's memory and the arm64 leg losing its place as the early warning, and the user decides whether that minute is wanted.
