# Steel

Fuji's safe Rust: the compiler forbids unsafe code at this crate's root and clippy denies anything that could panic, and it holds Fuji's own knowledge of the world its files come from, in two parts: the scout, the reader, which knows the formats of the files a collection holds, and the walker, which knows the storage they sit on.

The reader reads a file's first bytes. Given the first 64 KiB of a file and the file's size, it says what format the bytes are and what the common formats keep in their header: the stored size of a picture or a video and the size to show it at, its turn, the running time of a sound or a video, the times the file states and the place it was taken. When the first bytes say where the rest of an answer lies, a phone's video index after its data or an Ogg's last page, it asks for one more 64 KiB slice at that offset and answers again from both: two reads at most, and never a search of the file. It reads no pixels and no samples.

The walker walks a folder tree and names every entry in it with what kind of thing it is: a file, a folder, a link, a pipe, a socket, a device, a cloud file not yet downloaded, a folder on another drive, a folder it has already walked, and on Windows a reparse point it can't see behind and a name Windows' paths can't reach. It looks at everything that's there, hidden names included, and avoids only what would interrupt a walk, what isn't really on the disk, and what's somewhere else, so it never follows a link, never leaves the drive it began on, never enters a folder twice, and never opens anything. `src/walk.rs` carries the account of what each platform puts in a walk's way on the line that handles it, beneath a short essay on the rule.

It is a Rust crate of its own, so it builds and tests here with nothing of Fuji around it. Fuji's Rust depends on it by path, and nothing publishes it.

```
pnpm test    run the scout's tests, pinned to the files in samples/, the walker's and find's on trees they build, the disk's in a folder of their own, the fits' against the numbers fit.js gives, and the reads'
pnpm fuzz    run libFuzzer on the reader, seeded from samples/, until stopped
pnpm fit-table  write fit-table.txt, fitSize from fit.js over a grid of pictures, beams and screens, which the fits' test reads; run it when the arithmetic changes in both files at once
```

`pnpm fuzz -- -max_total_time=60` runs it for a minute. Fuzzing needs the nightly toolchain and cargo-fuzz, `rustup toolchain install nightly` and `cargo install cargo-fuzz`.

## The files


## How Fuji uses it

`desktop/src-tauri/src/scout.rs` is the command the page calls with a path. It reads the start of the file, and the second slice when the reader asks for one, and hands them to the reader here; `desktop/src/scout.js` wraps the command for the page. Nothing in Fuji calls the walker yet.

## The answer

The answer holds only what the scout found. In Rust every field is always there, and a value the file does not give, or the reader did not reach, is 0, false or blank; serialized, each of those is left out, `orientation` at 1 among them, so a missing field means the scout found nothing there and never that it found the file has none. A group, a size, a time, `taken` or `place`, is left out only when every part of it is, so one the scout found is written whole, a stated time's offset of 0 included. Below, a field's 0, false or blank is the value Rust holds, and the field a caller reading the JSON does not see. What the file holds sits at the top of the answer, and how the reading went sits in `reading`. What the scout needs next is no part of the answer: `scout_bytes` hands back the offset of the one more slice it wants beside the answer, or nothing, and the command acts on it, so the page never sees a request. Every key is one word, so the answer is spelled the same in Rust and on the page.

### Findings from the file

- `format` is the scout's own word for the format the first bytes announce, `jpeg`, `mp4`, `mp3` and so on, or blank when they announce none it knows. It names the container rather than the codec, so a WMV and a WMA are both `asf`, and Vorbis, Opus and Theora are all `ogg`. The scout sets it the moment a signature matches, before it checks anything else, and `reading` says how much the reader confirmed: `parsed` with no `trouble` when it walked the format's structure to its answers, `signature only` in `details` for a format the scout names and reads no further into, and `trouble` with its reason when the reading broke off part way. A text file that opens with a signature's letters, `ID3` say, is named as that format, and `text` says what the bytes are.
- `kind` is `image`, `video` or `audio`, or blank for a format that is none of the three, like a zip or a PDF, and for text and unknown bytes. A container's kind comes from its tracks when the reader reaches them, and otherwise from its signature or brand, which can say `video` for a file that holds only sound, or nothing at all.
- `text` and `binary` are two verdicts on the first 64 KiB from the four counts in `reading` alone, apart from every format's reader and signature, so no format's pattern reaches them. `text` says the scout is very certain the bytes are characters: they open with a UTF-16 byte order mark, whose text is half zero bytes, or else hold no zero byte and no more than one control character in a hundred bytes. `binary` says it is very certain they are not: they hold a zero byte and open with no such mark. They are never both true. Both are false for an empty file, and for bytes with no zero byte but too many control characters to be text, which real files rarely are. A format and these two can disagree, and the caller sees both: a text file that opens with `ID3` answers `format` mp3 and `text` true. The rule judges and does not prove, and it sees only the first 64 KiB; UTF-16 with no byte order mark reads as binary, since half its bytes are zero. An SVG is text that draws a picture, `text` true and `format` `svg` together.
- `raster` is the stored pixel count of a picture or a video, `{width, height}`, with its turn applied, so a phone's portrait comes back taller than it is wide. For a video it is the frame's stored pixels as its container writes them, which in an MP4 or a MOV is the sample description rather than the track header's shown size. Both numbers are 0 for sound, for SVG, for HEIC and AVIF, whose size the scout does not read, and wherever the reader stopped before them.
- `aspect` is the size to show a picture or a video at, `{width, height}` in square pixels, turned with `raster`. Where a header the scout reads says the pixels are not square, one side of `raster` grows by the pixel's shape, so a DVD stored at 720 by 480 answers 853 by 480 when it is flagged 16:9 and 720 by 540 when it is flagged 4:3; everywhere else `aspect` equals `raster`, and the answer leaves it out, so a caller shows a file at `aspect` where it is there and at `raster` where it is not. That includes a file whose container states no shape while its codec keeps one inside the stream, as H.264 and MPEG-4 Part 2 can: the scout does not read those codecs' streams, so it answers such a file's `raster`, while mpv, which decodes, draws it at its shape. The growing is mpv's rule: the side the pixel is long on grows, neither side ever shrinks below the stored count, and the fraction is dropped, so wherever the scout read the shape, mpv draws the file at this size unzoomed. A reader records the pixel's shape in whatever form its format writes it, a code, a ratio or a display size, and one step at the end makes `aspect` from it, so two files with the same pixels and the same shape answer the same whichever format wrote them. A picture's `aspect` is its `raster`: the scout does not read the fields a few picture formats keep for a pixel's shape, which rarely say anything but square.
- `orientation` is a finding: the file stores an instruction to turn or flip its picture, in EXIF's numbering, 1 for none through 8. The scout reads it from a JPEG's EXIF, a TIFF's first directory, and an MP4 or MOV track's matrix, where only the three quarter turns a phone records count, 3, 6 and 8; every other file answers 1. The scout has already carried the instruction out on `raster` and `aspect`, so a caller uses those two as they are and ignores `orientation` when it sizes anything, since turning them again would swap them back. It is there for a caller that wants to know the file is one an older program, which ignores the instruction, would show turned.
- `seconds` is the running time of a sound or a video, in seconds and their fractions, to whatever precision the format records, converted from the format's own units: a timescale's ticks, nanoseconds, a 90 kHz clock, samples over a rate. It is 0 for a picture, an animated one included, and where the file does not say or the reader stopped first. Four cases come close rather than exact. An MP3 with no Xing header is timed from its size and its first frame's bit rate, which is exact only at a constant bit rate. An MP3 timed from its frame count includes the encoder's padding, about 45 milliseconds. An MPEG program stream is timed to its last pack's clock, short of its last frame's end. And an FLV with no running time in its metadata is timed by its last tag, which is when its last frame starts.
- `animated` is true when the format's own flag says the picture moves: a GIF's looping extension, an APNG's animation control chunk, an animated WebP's flag, or the sequence brand of an AVIF or a HEIF file. It is false for a still and wherever the reader could not look, and a GIF that plays once, with no looping extension, also reads false.
- `corrupted` is true when the scout found positive evidence of a format, then evidence that the file breaks that format's rules where the reader needed them: a segment shorter than its own length field, a box shorter than its header, a zero width. A broken part the reader steps past without needing it, like a JPEG's EXIF or an AVI's OpenDML header, costs only what it held and is not reported.
- `chopped` is true when the scout found positive evidence of a format, then evidence that the file's end is cut off: a length or an offset the reader met on the way to its answers points past the end, or the file ends inside the structure the reader was walking. Most often it is the reason an answer is missing. Downloads are often chopped, especially from the years when a browser wrote to the final name as it went. It can come with a finished reading, where the reader meets the file's stated total on its way, as the RIFF formats, BMP and an MP4's top-level boxes have it: a WAV whose data chunk claims more than the file holds answers its running time with `chopped` true, and then `seconds` is what the header promised rather than what the file holds. A structure that points at or past the file's end for the rest of its answer is chopped too: an MP4 whose data box ends the file, with no index after it, answers `index at the end` in `details` with `chopped` true.
- False on both means no such evidence: an unknown file, a file the scout did not parse, or one damaged in a way the scout cannot see. The scout never goes looking for a length its answers do not need, so it never says the file is good: an MP4 with its index first, cut in half, answers its full size and running time with both false, since the reader stops at the index, and a Matroska file cut in half answers the same, though its segment states a size the scout does not compare. The two are reasons an answer is missing or may be wrong, and no sort of whole files from broken ones, which a length could not give anyway: a torrent's unfinished file has its full length, with zeros where the rest will go.
- `dates` holds every time the file states, six of them, each as the file wrote it, and the section after this list says what each one is and where every format keeps it.
- `taken` is the one time to show for when the picture or the video was taken, picked from `dates`, and an instant in UTC wherever the file gives enough to make one.
- `place` is where the file says it was taken, `{latitude, longitude, known}`, from the same section.

### Dates and places

The scout reports every time a file states and the place it says it was taken, as the file wrote them. From those times it picks the one that says when the picture or the video was taken, so a caller reads a single answer, the same way whichever format wrote it and wherever in the file the scout found it. Whether a time looks right is left to the caller: telling a camera's clock that was never set from a real day is a judgment, and a date in the future can only be caught by something that knows today's date, which the scout never does.

**The shape.** `dates` holds six times, `original`, `digitized`, `modified`, `gps`, `created` and `apple`, and each one has the same shape, `{stamp, offset, zoned}`. A time the file does not state is 0, 0 and false, and left out of the answer, and `dates` is left out when the file states none.

- `stamp` is milliseconds since 1970, the number JavaScript's `Date.now()` counts, so a page hands it straight to `new Date()`, with whatever finer fraction the file wrote.
- `offset` is the time zone, in minutes east of UTC: -420 for California in summer, 540 for Japan. It is 0 when the file stated no zone, and for a time its format defines as UTC.
- `zoned` says whether `stamp` is an instant. It is true where the file stated a zone or its format defines the time as UTC: then `stamp` is the moment in UTC, and the clock the file wrote is `stamp` plus `offset` minutes. It is false where the file wrote a clock with no zone: then `stamp` is those digits read as if they were UTC, a wall clock in a zone nobody knows, and the clock the file wrote is `stamp` itself.

The sample `taken.jpg` says its shutter fired at 10:21:33.123 on August 12, 2023, at -07:00, so its `original` is `{stamp: 1691860893123, offset: -420, zoned: true}`, which is 17:21:33.123 UTC. Written with no offset tag, the same digits would answer `{stamp: 1691835693123, offset: 0, zoned: false}`, which is 10:21:33.123 in no zone at all.

**The six times.**

- `original` is EXIF's DateTimeOriginal, when the shutter fired, with OffsetTimeOriginal for its zone and SubSecTimeOriginal for its fraction of a second. It is the time a camera or a phone means by when a picture was taken.
- `digitized` is EXIF's DateTimeDigitized, when the picture became data, with OffsetTimeDigitized and SubSecTimeDigitized. For a camera it is the same moment as `original`; for a scanner it is the scan.
- `modified` is EXIF's DateTime, the last change to the picture, with OffsetTime and SubSecTime; and in a movie, the movie header's modification time.
- `gps` is the time of the GPS fix, EXIF's GPSDateStamp and GPSTimeStamp read together, which are UTC by EXIF's rule. It comes from the satellites rather than the camera's own clock, and the fix can be older than the shutter.
- `created` is a movie header's creation time, Windows Media's creation date, or Matroska's DateUTC, which is when the muxer made the file rather than when anything was recorded.
- `apple` is Apple's creation date key, `com.apple.quicktime.creationdate`, which an iPhone writes into a movie beside the header's time, as local digits with their zone.

**Where a zone comes from.** A time is zoned in one of three ways, and every other time is a wall clock.

- From EXIF's three offset tags, which EXIF 2.31 added in 2016 and which are written `+09:00`; the scout also takes `+0900` and `Z`. Cameras and phones from before them write no zone at all, and many since leave the tags out or blank, which reads as no zone.
- From Apple's creation date key, which carries its zone in the string, `2023-08-12T10:21:33-0700`. A key with no zone reads as a wall clock.
- From a format's own rule. EXIF's GPS time, a QuickTime or MP4 movie header, Windows Media's creation date and Matroska's DateUTC are all defined as UTC, so the scout answers them zoned, at offset 0. Apple's documentation for the movie header says to write UTC and that older files commonly hold local time there, and cameras have written their local clock into it since, which `zoned` cannot detect.

**Fractions of a second.** EXIF's sub-second tags are digits after an implied decimal point, so `7` is 0.7 and `123` is 0.123. GPS writes its seconds as a fraction, Matroska counts nanoseconds and Windows Media hundreds of nanoseconds, and all of those keep their fraction in `stamp`. A movie header counts whole seconds, and Apple's key is read to the whole second.

**What reads as no time.** A time reads as none when the file does not have its tag, when it holds the blanks a camera with no clock writes, `    :  :     :  :  `, when it spells a date no calendar has, a thirteenth month or February 30th, when it is the 0 a movie header and Windows Media each use for none, and when it lands exactly at the start of 1970, which FFmpeg writes into Windows Media when it is given no time. Everything else is answered as the file wrote it, a camera's clock that was never set included, since telling that clock from a real day is a judgment.

**The one time to show.** `taken` is the moment the picture or the video was taken: one time picked from `dates`, in the same three fields, with two words more, `{stamp, offset, zoned, from, zone}`. Where `zoned` is true, `stamp` is what `Date.now()` would have answered on the camera at that moment, wherever and however the file wrote it, and a page shows it in whatever zone it chooses. Where `zoned` is false, `Date`'s UTC getters on `stamp` give back the camera's own digits.

- `from` names which of the dates it is, `Original`, `Digitized`, `Apple`, `Created`, `Gps` or `Modified`, and is blank when the file states no time.
- `zone` says how its zone was found: `Stated`, written beside the time in the file; `Rule`, the format's definition of the time as UTC; `Borrowed`, from a second clock in the same file; or blank for none, where `zoned` is false and `stamp` is a wall clock.
- `offset` is the zone the moment was in, where `zone` is `Stated` or `Borrowed`. Where it is `Rule`, the instant is known and the place's zone is not, so the 0 in `offset` is UTC itself and says nothing about where the camera was.

The scout takes the first time the file states, in an order that puts the moment of capture first and an edit last:

- `original` comes first, since it is the shutter's own time.
- `digitized` comes next, the scan's time, or the shutter's again.
- `apple` answers for a movie, its local time with its zone.
- `created` follows, a movie header's time or the moment Windows Media or Matroska made the file.
- `gps` answers for a picture that holds a GPS fix and no camera time.
- `modified` comes last, a picture's last change, which is its shutter's time in a file nothing has edited and an edit's time in one something has; `from` says which time it is, so a caller can decline it.

The time picked keeps its own zone when it has one. A time with no zone borrows one from a second clock in the same file that read the same moment in UTC: the shutter's and the scan's times borrow from the GPS fix, and Apple's key from the movie header. A picture's last change borrows nothing, since nothing else in the file read the moment of the edit. The difference between the two clocks, rounded to the nearest quarter hour, is the zone, when the rounding moved it by no more than two minutes and it lands on an offset some place has kept. Those are 45 offsets from -12:00 to +14:00, the half hours of India and Newfoundland and the quarter hours of Nepal and the Chatham Islands among them: every offset a zone in the IANA time zone database has used since 1990, summers included, read from release 2026c on the Mac mini. The camera's clock keeps the moment and the second clock lends only the zone, since a GPS fix can be older than the shutter. A stale fix lends nothing when it lands more than two minutes off a quarter hour, or on one no place keeps, as a fix fifteen minutes stale does in California, and then the time stays a wall clock. A fix stale by a whole hour still lands on a real zone, and lends one an hour off, which nothing in the file can tell from the right one. The two minutes are a factory value, for a run over a collection to set where real files fall. The scout does not look a zone up from the place, which would need a map of the world's zones and their daylight rules.

A picture with no offset tag and no GPS fix, which is every camera without GPS from before 2016, has no UTC in anything the scout reads, and answers its wall clock with `zoned` false. For the samples, `taken.jpg` answers `{stamp: 1691860893123, offset: -420, zoned: true, from: "Original", zone: "Stated"}`, and the same digits with no offset tag beside its GPS fix at 17:21:30.5 UTC answer the same, `Borrowed`. `taken.mov` answers the same instant from `Apple`, `Stated`, and `located.mov`, which holds no Apple key, from `Created` by `Rule`, at offset 0.

**The place.** `latitude` and `longitude` are in degrees, north and east positive. `known` says whether the file states a place. Exactly 0 and 0, which a writer with no fix fills in, counts as none, though it is a real point in the Gulf of Guinea, and so does an angle past a pole or the date line.

- From EXIF's GPS directory, the scout reads GPSLatitude and GPSLongitude, each three fractions of degrees, minutes and seconds, which phones fill with decimals in whichever of the three they like, and the N, S, E or W of GPSLatitudeRef and GPSLongitudeRef; a missing letter reads as north or east. Coordinates of any other type or count, or past 90 or 180 degrees, read as no place.
- From an ISO 6709 string, the form Apple's location key and the `©xyz` box hold, `+37.3315-122.0304+013.405/`, the scout reads degrees with decimals. The standard's other forms, with minutes and seconds, read as no place.
- The scout does not read the altitude in either form, nor the rest of EXIF's GPS directory: the direction the camera faced, the fix's accuracy and its status.

**Per format.**

- **JPEG.** The scout reads all four EXIF times, `original`, `digitized`, `modified` and `gps`, and the place, from the EXIF segment, the APP1 segment that opens with `Exif`, which comes before the picture's frame header. A directory or a value the first 64 KiB does not reach is read from the second slice. The scout does not read XMP, a second APP1 segment that carries dates of its own; IPTC's date and time created in the Photoshop segment, whose time carries a zone; or a camera's maker note, where Canon and Nikon kept a time zone of their own before EXIF had one.
- **TIFF.** The same tags come from the file's first directory and the EXIF and GPS directories it points at, wherever in the file they sit, with the second slice reaching one past the first 64 KiB. A camera's raw file built on TIFF whose first image is a preview, a DNG among them, still answers its times and its place, though the scout refuses its size. A Canon CR2 is refused before any of it. The scout does not read the XMP tag.
- **PNG.** The same tags as a JPEG come from the eXIf chunk, which PNG gained in 2017 and its third edition places before the picture's data. The scout does not see an eXIf chunk a writer put after the data, since its walk stops at the data. It does not read the tIME chunk, which holds the picture's last change in UTC; text chunks like `Creation Time`, whose value is free text; or XMP.
- **MP4, MOV, M4A and 3GP.** The movie header, `mvhd`, gives `created` and `modified`, in whole seconds since 1904, UTC by the format's rule, where 0 means none. The keyed metadata, a `meta` box with `keys` and `ilst` inside, in the movie box as an iPhone writes it or in the user data box as FFmpeg writes it, gives `apple` from `com.apple.quicktime.creationdate` and the place from `com.apple.quicktime.location.ISO6709`. The user data box's `©xyz` gives the place as an Android phone writes it. When a file holds both places, the one the walk meets last answers. Where a movie keeps its keys and its place after its tracks, as FFmpeg writes them, a movie whose index runs past the second slice holds them out of reach. The header's times come before the tracks and are still answered, and `reading` says `not in the slices`. Measured on the Mac mini with FFmpeg's layout, a 30-frame-a-second movie with sound: the keys were reached at one minute and not at two. The scout does not read each track's own header times, `tkhd` and `mdhd`; `©day` in the user data; the 3GPP `loci` box, where FFmpeg writes an MP4's place; Apple's location accuracy key; or XMP.
- **HEIC and AVIF.** The scout reads no time and no place from them. Their EXIF, where an iPhone's photos keep every time and the place, is an item of its own, named in the item information box and found through the item location box, which the scout does not walk.
- **Matroska and WebM.** The segment information's DateUTC, nanoseconds since 2001 in UTC, answers as `created`. It is when the muxer made the file: mkvmerge writes the time it ran, and FFmpeg writes the creation time it is given, which a remux carries over from its source, and none when it has none. The scout does not read the tags, where `DATE_RECORDED` and its kin live.
- **Windows Media.** The file properties object's creation date, hundreds of nanoseconds since 1601 in UTC, answers as `created`, and nothing answers where the broadcast flag is set, since the flag makes the date invalid.
- **Everything else** answers no time and no place. Several formats keep a time the scout does not read: AVI's `IDIT` chunk, the date a camera wrote as text; the `ICRD` creation date in the INFO list of an AVI or a WAV; Broadcast Wave's origination date and time; an MP3's ID3 recording time; the `DATE` comment of FLAC and Ogg; WebP's EXIF chunk; and Photoshop's EXIF among its image resources. GIF and BMP keep no date at all.

### The scout's report on its reading

- `parsed` is true when the scout has a reader for this format and ran it past the signature. It is false for a format the scout names by its signature alone, for bytes it does not recognize, and for an empty file. It says nothing about trouble: a JPEG cut off at 100 bytes is parsed, with trouble.
- `trouble` is true when the reader stopped before it had every answer it reads for this format. Either it reached its own limit, past its slices, `not in the slices`, in a structure or a variant it does not read, `item properties not read`, or at an answer the file does not keep, `total samples not written`; or the file was at fault, which `corrupted` or `chopped` then names, `no marker where the format puts one` or `past the end of the file`. The walk's ceiling, `more boxes than the walk allows`, is the scout's own limit, since a ceiling is no evidence that the file breaks a rule. `corrupted` always comes with `trouble`; `chopped` can come without it. The findings above hold whatever the reader read before it stopped.
- `details` is a few words on the condition, in the scout's own words: why the reader stopped, or why it did not parse, `signature only` or `empty`. It is blank when the reader parsed with no trouble, and for bytes the scout does not recognize.
- `reads` is how many reads the answer is from, 1 or 2.
- `depth` is the farthest byte of the first 64 KiB the reader looked at, signature probes included, for every file. With `reads`, a run over a collection says whether a smaller first read would have done and how often a second was needed.
- `counts` holds `nul`, `control`, `printable` and `high`: how many bytes of the first 64 KiB are zero; control characters other than text's whitespace and escape; printable ASCII with that whitespace and escape; and bytes past ASCII, which UTF-8 text and every binary file have. `text` and `binary` are judged from them, and since they are in every answer, a caller can judge by a rule of its own.

A listing reads the answer three ways. It shows what came back: `raster`, `aspect` and `seconds` wherever they are not 0. It hands the file on to the next tier for what did not: `trouble` with neither finding, or a format named but not `parsed`. And it reads `corrupted` or `chopped` as the reason an answer is missing or may be wrong, never as a verdict on the file.
