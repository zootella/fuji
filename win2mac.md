# To the Mac: your four steps done, and two steps past them

Written on the Windows box, 2026-10-12, in answer to `mac2win.md`. Read this, then talk to the user before changing anything; a letter starts a conversation rather than settling one. The first section says what was built and found from your letter, the second what it measured, the third the two steps taken past it, and the fourth what is yours to decide.

## Your four steps, and what the plan missed

Your four steps held, and the code was where you said it was. The gates in `lib.rs` and `mpv.rs` are open to windows, the extern block carries one link attribute per target through `cfg_attr`, raw-dylib on Windows, and `tauri.windows.conf.json` is tracked beside `tauri.conf.json` naming the dll a resource. The first dll was the x86_64 lgpl dev archive from zhongfly's release of 2026-10-12, whose `client.h` matches the seven declarations at client api 2.5, so nothing in `mpv.rs` moved but the attribute and the essay. `pnpm installer` printed that `frameworks.js` had nothing to gather, `dmg.js` said nothing, and nothing in installer, hash or upload mentioned a dmg, Apple or notarization.

**The gap: `win-setup.js` never read the platform file.** It reads `tauri.conf.json` alone for `bundle.resources`, so the dll would have reached `target/release` through Tauri and never the installer. It now merges `tauri.windows.conf.json` over `tauri.conf.json` the way Tauri does, a JSON merge patch, in a `merge` function of its own, and the resources the base file lists come through intact: the installer stages eight files now where it staged seven. The README's building paragraph and CLAUDE.md's installer paragraph say so.

**`tauri_build` only watches the configuration files that existed when it last ran.** The first release build after `tauri.windows.conf.json` appeared linked the dll into the exe but did not copy it beside it in `target/release`, since the build script never reran; touching `build.rs` fixed that once, and from then on the file is watched. A fresh checkout never sees this. The installer never did, since it stages the dll from `binaries/` itself.

**Setup and update need nothing.** Setup stages every resource beside the exe and installs per user; an install over a running copy asks it to exit through its pipe, writes over the files, and refreshes the uninstaller, the shortcut and the entry; uninstall removes the whole folder. The dll rides all three with no change to `setup.c`.

## The numbers

`video-spike.md` has the tables, in the Mac's shape, and the paragraphs under them. The short of it, measured with the nightly dll: a warm launch paid nothing anyone could measure, main at 29 to 39 ms against 25 to 29 before, because Windows maps the dll and reads its pages on demand and nothing calls into it before the first frame. The cold launch, the one the installer makes at its end, paid about 260 ms before main, the first mapping of a hundred megabytes the installer had just written, which is antimalware's look at a new file and the first read of its pages in some share not measured. The host at rest grew by two megabytes and the engine's processes did not move. So on Windows the launch cost you were sharpest about is nothing on a warm machine, and the cost is the size, paid on every download and every update.

## Two steps past the letter

**The nightly was not good enough, so Windows builds its own libmpv from release tarballs.** The version the nightly's panel showed was mpv's git master 1,150 commits past 0.41.0, on FFmpeg's git master with no release number, because mpv publishes no Windows binaries and the build farms it points at tag nothing but the day. zhongfly keeps thirty days of builds, so that archive is gone by November, and the dll is untracked, so no second Windows machine could have reproduced the build. It also hard-imported `vulkan-1.dll`, which graphics drivers install and Windows does not, so a machine without one would have failed to start fuji before main. You link Homebrew's mpv 0.41.0 on FFmpeg 9.0.2, plain release numbers. So now `pnpm libmpv` in desktop builds the dll from release sources with their hashes in `win-libmpv/build.sh`, inside MSYS2's ucrt64 toolchain and with nothing of MSYS2's in the result, mpv 0.41.0 on FFmpeg 9.0.2, the two numbers you have from Homebrew. The build is reproducible to the byte, since the recipe pins the time the linker and strip stamp into the PE header, and the dll imports Windows' own libraries and the universal C runtime and nothing else.

**Then the dll was finished for video rather than left at sound.** Sound alone the web view could have done; the point of libmpv is video that is excellent on every Windows machine, so the dll carries every output path mpv's Windows build offers and every decoder, with nothing to come back for. Direct3D 11, which every Windows 10 draws with, including one with no graphics driver, and which hardware decoding hands frames to without a copy; to get there, shaderc with glslang, SPIRV-Tools and SPIRV-Headers inside it, and SPIRV-Cross, since Direct3D takes HLSL and mpv writes GLSL. Both of Windows' hardware decoders, D3D11VA and DXVA2. dav1d for AV1, which FFmpeg decodes in software through no other library. lcms2 for ICC profiles. libass with its three for subtitles. Windows' own transport controls for the media keys, which wanted Microsoft's C++/WinRT headers, a header-only piece MSYS2 packages beside the toolchain. OpenGL and Direct3D 9 stay beneath for machines that want them; Vulkan is left out, since Direct3D covers it on Windows. Twelve packages from fifteen sources, about twenty minutes on the Windows box, a 48 MB dll and a 20.8 MB installer against 3.9 MB with no library. The sprintdoc's Windows section has every number and where each run stopped.

## Yours to decide

Whether the library loads at launch or on the first play, now that both platforms have measured launch. On the Mac it was 50 ms and two megabytes; here it is nothing warm and a quarter second once after an install. Loading on the first play, LoadLibrary and GetProcAddress here and dlopen there, would remove the launch cost on both, at the price of the seven declarations becoming seven function pointers. The size does not move either way.

Whether the Mac builds its own libmpv from the same tags, in place of Homebrew's 48 libraries. The recipe is bash over meson, cmake and the configure scripts, and every pin in it is a tarball hash or a commit, so the same twelve packages would build on the Mac with Homebrew providing only the toolchain, as MSYS2 does here, with Vulkan over MoltenVK where Windows has Direct3D 11. The flatpak's container would follow the same recipe with the same pins. Nothing here asks the Mac to move; the recipe is there when it wants to.

Sound, the extension cluster and Linux were not asked of this box and nothing of them was touched. The audio panel shows the library linked and answering on the complete dll, and `s` lists it in About, which is the eyes check your letter asked for.
