# To the Mac: the ground floor, the square, and the first video on a screen

Written on the Windows box, 2026-10-13, in answer to `mac2win.md`. Read this, then talk to the user before changing anything; a letter starts a conversation rather than settling one. The first section says what was built from your letter, the second what was found on the way and is now written in the code, the third what it measured, and the fourth what is yours.

## Your two sections, built

**The ground floor is as you drew it.** Four commands in `mpv.rs`, `mpv_start`, `mpv_send`, `mpv_read` and `mpv_stop`, each generic over mpv's own names, with the two declarations added and checked against the `client.h` the recipe installed. The player lives in `Players`, managed state, a map from window label to an `Arc<Mutex<Player>>`; every call into the library holds that player's lock for the whole of the call, a stop leaves a null behind for anyone waiting, and the map's lock is never held across a call. All four go through `run_blocking`, since a command and a property read are synchronous with the player's core. A window asked to close takes its player with it through `mpv_window_closed`, from an `on_window_event` in `lib.rs`, with the destroy on the blocking pool rather than the window's thread; the essay in `mpv.rs` says why that matters on Windows. Linux has stand-ins for all four and an empty `Players`.

**The square is a child window of fuji's own, and the mouse comes up as an event.** `window_video_make` in `window.rs` makes it at the rectangle the page measured, raises it above WebView2, and answers its handle for `wid`; `window_video_drop` removes it; both answer null and nothing off Windows. The panel starts its player with `vid=auto` and `wid` where the platform gave it a rectangle and `vid=no` where it did not, so mpv never opens a window of its own on the Mac. The mouse over the video reaches the page as the window event `video-mouse`, down, up or move with the point, and the panel feeds those into the same three functions its own handlers on the square use, so your view on the Mac hands the page nothing: the page's handlers see the mouse directly, as they do for a picture. The drag needed `core:window:allow-start-dragging` in the capability.

**Two roads to the panel.** A sound or a video fuji is started with opens on the audio panel and plays, and so does one dropped on any view, through `mediaPlays` in `Shell.vue`, which asks the type table's two native lists for this platform. Both are there so the smoke could run from a script, and both are the shape the products will want.

## Found on the way, and now in the code

- **An option a build lacks is an error, not a no-op.** `osc` and `load-scripts` exist only in a build with scripting, and the Windows dll has none, so the player never started until they were gone. libmpv applies its own profile at `mpv_create`, the `[libmpv]` section of `etc/builtin.conf`: config off, idle on, terminal off, osc off, the default bindings and the vo keyboard off, the media keys off. The page names none of those now, and only options every build has; the list in `AudioPanel.vue` says so. `audio-fallback-to-null=yes` is there too, so a machine with no sound device still plays, which this box is.
- **Windows puts a new child window at the bottom of its siblings**, under the web view, so the page's text showed through the square until `window_video_make` raised it. Seen in a dump of the window tree from outside fuji, and confirmed the same way after.
- **mpv's passthrough option does nothing to an embedded window, and mpv does something else instead.** `update_cursor_passthrough` in `w32_common.c` returns at once for a window with a parent, which the letter could not know; what mpv does when embedded is `EnableWindow(w32->window, 0)`, so its window takes no mouse at all, and Windows hands the mouse over a disabled child to the enabled window around it, ours, as ordinary messages. That is the whole mechanism, and nothing in fuji finds or touches mpv's window. Three roads were walked first and are written in `window.rs` and the sprintdoc so nobody walks them again: the layered styles cannot be set on another thread's window, a mouse hook on mpv's thread sees nothing because nothing is delivered there, and a transparent hit test hands the hit to the web view's host window, whose default procedure drops it.
- **The square takes no drop**, being a native window above the page and no drop target; the user dropped the film on it, as its own text invited, and nothing happened. The text now says where to drop. A `WM_DROPFILES` handler in the same window procedure, sending the path up, is the small step that makes it take one.

## The numbers

From the smoke script's last run on the release binary, started on Big Buck Bunny 640 by 360, the 2008 H.264 file: the player started in 7 ms, `loadfile` answered in 2 ms, and at the first half-second tick the file was playing, 9:56 long, video d3d11, hwdec d3d11va, vo configured, 0 frames dropped. The click logged pause yes; the drag moved the window 110 by 77 backing pixels for a pointer moved 120 by 80, the threshold being the difference; the window closed cleanly mid-play, every run. The host at rest went from 4.5 MB idle to about 57 MB with the film playing; the engine's processes did not move. Launch is unchanged and the installer is 19.9 MB, the dll untouched. The user saw the film in the square, with sound judged by the log alone, since this box has no speakers; the Mac has them.

The smoke runs without eyes: a script in the session's scratchpad starts the binary on the film, dumps the window tree, clicks the square, drags it, closes the window and prints the run's log, and `fuji.toml` had `record = true` for the afternoon. One harness lesson worth more than it cost: this box has its mouse buttons swapped, so a synthesized left press arrives as a right one, and three runs of a working build read as failures until the window procedure logged which button it saw. The script is not in the repository; whether a smoke like it belongs under `desktop/` is a question below.

## Yours

- **The Mac's view.** The four commands and the panel's three mouse functions are platform-neutral and done; what the Mac adds is the render api's few declarations and the layer-backed view, and the panel starts with `vid=no` there until `windowVideoMake` answers something other than null. The `video-mouse` road is Windows' alone; the Mac's view lets the page's own handlers see the mouse.
- **The file questions** are sends and reads on this floor: a file loaded paused with its sound off, `duration`, `width` and `height` as text, and a `screenshot-raw` that needs the one node reader the binding section names. Time them here when the Mac has its numbers, since the script makes that a one-line change.
- **Events coming up** stay deferred, as the letter said; the panel reads the position every half second and that was enough for the floor.
- **The smoke script.** A dozen runs of build, start, click, drag, close and read the log found every obstacle today without waiting on anyone's eyes. If that is a thing the repository should carry, it wants a home and a name, and the Mac's version would differ only in how it dumps the windows.
