Components: what is on the shelf

The search for existing list, tree and grid components, done 2026-10-11 from the Mac mini by fetching documentation, repositories and the npm registry. Nothing was run in a webview. The long report this came from is not kept; this page is the record. It is a sprintdoc: it shrinks as decisions become code.

The decision

Write FujiList and FujiTree ourselves, borrow their behavior models from the sources below. Across roughly ninety packages for Vue, React, web components and plain JavaScript, no single component meets the need: a columned list and a folder tree with a keyboard focus separate from the selection, Ctrl and Shift clicks, type-ahead, inline rename, an instant filter, ten thousand rows kept light, a flat platform-neutral look, under MIT, maintained, for Vue 3 or plain JavaScript.

The expectation that what exists is React-specific, heavyweight, or built to another use case held outright for the list. The only Vue components with a complete desktop selection model are PrimeVue's DataTable, which left MIT with version 5.0 in July 2026 and now requires a license key, and AG Grid Community, a 21.6 MB styled grid whose tree is an Enterprise feature at $999 per developer.

It failed in one narrow place, and the record says so rather than pretending otherwise. The tree's behavior layer exists for Vue: Zag's tree-view machine, through @zag-js/vue or Ark UI, has focus apart from selection, Ctrl-click toggle, Shift-click range, Shift with the arrows, type-ahead, F2 rename and lazy children, under MIT, at 1.19 million weekly downloads. It is declined for a stated reason: adopting it would give the tree a different interaction codebase from the list. Since the list's model has to be written anyway, and a tree drawn as rows is a flat list of visible rows with an indent and a twistie, the tree costs the project four keys and an async children contract on top of the list, and nothing else.

Two parts of the look cannot come from CSS in any engine fuji ships on. No browser hands a page the user's highlight or accent color, and WebView2 draws Chromium's two-tone focus ring rather than Windows' dotted rectangle. The section on the browsers has the engine-by-engine facts.

On portability the evidence points one way: the cores that crossed frameworks in this survey are the ones with no framework in them. So the traits, the click rules, the keyboard and the type-ahead buffer live in plain modules, and the Vue component is the thin layer that binds them to a template. That answers the open question about shipping the components as plain JavaScript.

The pattern is the same across the table: the behavior exists in pieces, and the pieces come with a framework, a look or a license. The two that have everything, VS Code's widgets and PrimeVue's DataTable, cannot be installed under fuji's terms.

What to borrow, and from where

Three traits: focus, selection, anchor

The model is VS Code's. Its list widget keeps three separate traits: focus is where the keyboard is, selection is the rows chosen, and the anchor is the reference point for a Shift-click or a Shift-arrow range. The tree keeps the same traits at the tree level, because collapsed nodes are not known to the list, and restores them as rows are rendered, since a selected row may be collapsed away. Wunderbaum reaches the same shape as focused, active and selected, where setting focus "only draws a dotted border" (keyboard tutorial); Headless Tree and Zag keep the focused item and the selected items as sibling state. The ARIA authoring guide says why: focus is a pointer, there is only one point of focus at any time, and the selected state must be visually distinct from the focus indicator. VS Code puts one tab stop on the list root.

The click rules, in five lines

Headless Tree states the mouse model in the smallest form found: with Shift, select up to the row from the anchor, keeping the existing selection when Ctrl or Cmd is also down; with Ctrl or Cmd alone, toggle the row; otherwise replace the selection with the row (reference). VS Code adds the edges: the toggle modifier is Cmd on the Mac and Ctrl elsewhere, switchable to Alt; a Shift-click selects the range from the anchor to the row, merges it with the existing selection, moves focus to the row and leaves the anchor where it was; a right-click sets focus only; a plain click sets focus, anchor and selection (listWidget.ts, listService.ts). React Aria's selection guide is the best prose statement of the same thing, under the name "replace" behavior. The vendors say it in fewer words: Finder's Command-click and Shift-click, and Explorer's Shift-click for contiguous and Ctrl-click for non-adjacent, with no toggle on a plain click.

Keyboard tables

Four documents give a table that copies nearly as is. The ARIA Tree View pattern is the base, with its recommended multi-select model of Space to toggle, Shift+Arrow to move and toggle, Shift+Space for a run, Ctrl+Shift+Home and End, and Ctrl+A. MUI's tree accessibility page restates it cleanly. PrimeVue's 4.x DataTable accessibility document is the list equivalent, header keys included. VS Code's listCommands.ts is the production table with its conditions, and its Explorer file actions settle two platform differences: rename is F2 on Windows and Linux and Enter on the Mac, and trash is Delete on Windows and Cmd+Backspace on the Mac. Ignite UI's tree navigation is a compact reference implementation of the modifier-plus-arrow focus move.

Type-ahead is not the filter

Two mechanisms. Type-ahead is Win32's incremental search string: each typed character appends, the control finds and selects the match, and a time-out resets the string. VS Code's type navigation in listWidget.ts is the implementation to copy: printable keys accumulate, the search starts after the focus and wraps, a prefix match wins, a fuzzy match counts only when it is the single result, and the buffer resets after 800 ms. The filter is a different widget. VS Code's find control toggles between highlighting and filtering (user interface docs). The rule fuji wants for a tree filter is react-arborist's: only matching nodes show, a matching child shows all its parents, and internal nodes open while filtering; Wunderbaum offers both dim and hide modes with matches wrapped in <mark>.

Rename

Zag's flow is the most complete written down: F2 starts it only when renaming is allowed, Enter or blur submits, Escape cancels, empty names are rejected, IME composition is handled, and there are hooks before and after (Zag tree-view). Wunderbaum names the triggers as a list, ["clickActive", "F2", "macEnter"], which expresses the Windows-and-Mac difference as data rather than branches (edit tutorial). Apple's guidelines add the mouse rule for a file list: single-click a name to edit it, double-click to open the file (outline views).

Folders as a predicate, children as a promise

Whether a node can expand is a property of the node, not a count of its children. VS Code's AsyncDataTree sets collapsible from hasChildren, takes getChildren as a promise, and after 800 ms marks a slow load so the twistie shows a spinner. Headless Tree takes an isItemFolder predicate; Zag takes loadChildren with a count. Vaadin's data provider is the most fully specified contract: page, page size, parent item, and a size the callback reports. The libraries that get it wrong show the trap: Reka's leaves must return undefined rather than an empty array, and Element Plus's TreeV2 has no lazy path, so an empty folder would need a placeholder child. Fuji's find.rs already answers many folders per call, so the page decides collapsibility from the entry's kind and asks Rust for children on expand. Apple's guidelines ask that expansion choices be retained, and Microsoft's that they persist, so fuji.toml is where they go.

The row's DOM

Two light shapes to copy. VS Code's tree row is one row element holding an indent, a twistie and a contents element, with indent computed from depth and a default of 8 pixels clamped between 4 and 40 (abstractTree.ts); the list row carries its role, index, set size and position. Wunderbaum's tree-grid row is one row element with a node column holding indent, expander, icon and title, plus one element per extra column with an inline left and width (render tutorial), the one place in the survey where a tree and columns share a row. Reka's single li with data attributes for indent, selected and expanded shows how little a row needs. The floor fuji is avoiding: Naive UI's node is about thirteen elements at depth three, Vuetify's eight or more, and every per-item web component adds a shadow root per node that page CSS cannot reach except through ::part(). For headers, Microsoft's list view guide says the first click sorts ascending, the second descending, with the previous column as the secondary key, numbers right-aligned and text left; Apple's lists and tables says a click on an already sorted column reverses it, and in an outline view sorting happens at each level.

A settings vocabulary

VS Code's list settings are a ready-made list of the switches a portable component exposes: the multi-select modifier (Ctrl or Cmd by default, Alt as the alternative), open on single or double click, expand on single or double click, type navigation automatic or on a trigger, the default find mode highlight or filter, fuzzy or contiguous matching, the tree indent, indent guides none or on hover or always, scroll by page, smooth scrolling, and sticky scroll with a maximum item count. The widget itself binds none of Space, Shift+Arrow or Left and Right; the workbench binds them with conditions, which is the design rule: expose the switches, do not hard-code them.

What the browsers give for free, and what they do not

The system colors a page can rely on are the neutral pairs, not the highlight. CSS Color 4 defines Canvas and CanvasText, Field and FieldText, ButtonFace and ButtonText, GrayText, Highlight and HighlightText, SelectedItem and SelectedItemText, AccentColor and AccentColorText, and promises contrast only within a pair. Every engine treats the two colors fuji wants as fingerprinting surfaces. The CSS working group resolved on 2026-08-06 that user agents should return a fixed color for AccentColor, and browser-compat data records a fixed blue in Chrome, Firefox and Safari. What is inferred rather than read

Nothing was run in a webview; compatibility with WKWebView, WebView2 and WebKitGTK is inferred from each library's stated Safari and Chrome support and the APIs it touches. Every per-row element count was read from templates and source, not measured in a browser. Zag's README lists Shift+Arrow ranges as to do while its source implements them; the source is taken as the behavior.
