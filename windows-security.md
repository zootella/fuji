# The sandbox process on Windows: what can go wrong, the walls, the recovery paths, and what was measured

Notes for the second half of the Security article, written on the Windows box on 2026-10-26, the day the Windows walls landed. security.md holds the research and the article's outline; scan.md holds the decided and open items; the essays atop `copper/src/sandbox.rs` and `copper/src/inventory.rs` are the code's own account. This document is the Windows half in one place: the mishaps and attacks the design anticipates, what each wall stops and what it does not, how each recovery path was exercised, and the numbers, so the article can state facts and this file can say where they came from. Everything measured was measured on the Windows 10 box, Windows 10 Pro 22H2 build 19045, on 2026-10-25 and 2026-10-26, unless a line says otherwise; Windows 11 is by sight alone until the test box exists.

## What can go wrong in the sandbox process

The sandbox process is a second copy of fuji's own executable, started by the main process for one inventory with `--inventory-sandbox`, running the copper and steel crates and nothing of Tauri. It walks the folder, reads every file's first bytes through steel's scout, hashes whole files when asked, and hands every file the type table or the scout calls video to FFmpeg through libmpv's probe. The probe is where the untrusted bytes meet C: a demuxer parses the container, and a demuxer has, over twenty years, been where the bugs in the history drafted in `site/docs/security.md` lived. The design anticipates six endings for that process, four of them things a hostile file could choose and two of them ordinary life.

- **A fault.** An access violation or a stack overflow in FFmpeg, from a bug a crafted file reached, or in fuji's own Rust where it calls C. Exit code 0xC0000005 or 0xC00000FD.
- **An abort, which on Windows is a fast fail.** Rust's abort, which an allocation failure or a panic across an FFI boundary ends in, and the C runtime's `abort()`, which FFmpeg's `av_assert0` calls when a demuxer's own invariant breaks. Both compile to the `int 0x29` fast fail and exit with 0xC0000409. A fast fail is not an exception: it never reaches `UnhandledExceptionFilter`, which is where a process's own crash handling and the job object's crash flag both live, so anything that counts on the exception path misses it.
- **A hang.** A demuxer's loop that never ends on a crafted length, or a read the kernel never finishes, on a dropped network share or a dying disk. The process is alive, its counts stop moving, and nothing inside it can be asked to stop, since a read stuck in the kernel is not interruptible from user mode and a loop in C has no stop flag.
- **Memory exhausted.** A file whose headers make a demuxer allocate without bound, as CVE-2026-107678's tens of thousands of `pssh` boxes do against the FFmpeg fuji ships. Left alone this takes the machine's memory and then the machine's attention.
- **A takeover.** The bug that lets the file choose what the process does next. Code running then has what the process has: it runs as the user, and on Windows that means the user's files to read and write, the user's half of the registry, programs to start, the network, the clipboard, the other windows on the desktop, and the other processes of the user's, the main process among them. The walls exist for this ending, and the question for each wall is which of those reaches it closes.
- **The two ordinary endings.** The inventory finishes, or the user presses Stop or closes the window. The design has to make those as clean as the bad endings, and make the bad endings as quiet as these.

Two mishaps that are not endings of the sandbox process also shaped the Windows work. The main process can die first, by a crash of its own or by Task Manager, and the sandbox process must not outlive it as an orphan still writing the inventory. And the system's own crash handling can speak up on the sandbox process's behalf: Windows Error Reporting collects a report, writes it to disk, logs two events, and by its documented default asks the user whether to send it, which is a dialog in the user's face for a process the main process already picked up the pieces of.

## The walls Windows offers a process, and the ones fuji uses

A process on Windows can wall itself in without any privilege, and the sandbox process does so once, between reading its request and opening its first file, in the Windows arm of `enter`. What the loader mapped before `main`, fuji's own executable and the media library beside it, came from the program and not from a file, so it is fine that those are already in memory when the walls go up. The order matters and is this.

- **The error mode, first.** `SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX)`. The middle flag is documented as keeping the Windows Error Reporting dialog away, and measured it does more: the system does not invoke the reporter's collection at all for a fault, and for a fast fail starts it for a tenth of a second and writes nothing. It is the one wall that works for every ending, because the error mode is read before the exception path that a fast fail skips. It goes first so that a crash in the walls themselves is quiet too.
- **A job object, second.** The process makes an unnamed job, sets its limits, and assigns itself. The limits: `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` with a count of one, so `CreateProcess` from inside fails with error 1816, "not enough quota"; `JOB_OBJECT_LIMIT_PROCESS_MEMORY` at 1 GiB of committed memory, past which allocation fails, which Rust turns into an abort and FFmpeg's `av_malloc` into a null the demuxer has to handle; `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`, which is belt to the error mode's braces; and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, so the job and the process end together. The job's basic UI restrictions are the eight Chromium's sandbox sets at its lockdown level: no reading or writing the clipboard, no USER handles of processes outside the job, so no window of another process can be found or sent to, no global atoms, no display settings, no system parameters, no desktop made or switched to, and no `ExitWindows`. The handle to the job stays open for the life of the process, since closing the last handle to a kill-on-close job would end it. Nested jobs are allowed since Windows 8, so a main process that was itself started inside a job, by a launcher or an installer, does not break this.
- **The integrity level, last.** The process opens its own token with `TOKEN_ADJUST_DEFAULT` and sets `TokenIntegrityLevel` to the Untrusted label, `S-1-16-0`, in place. Mandatory Integrity Control then judges every open from here by that level against the object's label, and the user's files, folders and registry keys all carry Medium with no-write-up, so a write to any of them is refused with access denied, and processes carry no-read-up and no-write-up, so another process's memory is refused. What the process already had open stays open, which is why its three standard streams still work, and which is why the walls judge an open and not a handle. Untrusted is the level Chromium's renderers run at; Low, the level Internet Explorer's protected mode ran at, differs in leaving the `LocalLow` folder under the user's profile writable, and the inventory wrote the same file at Untrusted on every walk, so there was no reason to stop at Low.

The main process builds two walls of its own when it starts the sandbox process, in the Windows arm of `start`.

- **A handle list.** Rust's `std::process::Command` on Windows asks `CreateProcessW` to inherit handles and names none, so the new process receives every handle the main process holds marked inheritable, which WebView2 and the system mark some of without asking. A file already open arrives past the walls, since the walls judge opens. The main process therefore calls `CreateProcessW` itself with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` naming the three streams, which is the only way Windows has to say which handles cross; the three are marked inheritable for that one call and unmarked after. A `Command` started on another thread of the main process in those microseconds would inherit them, which nothing in fuji does during an inventory; the code says so where it happens.
- **A default error mode and a bare environment.** `CREATE_DEFAULT_ERROR_MODE`, so the sandbox process's error mode is its own and not the main process's, which matters below; `CREATE_UNICODE_ENVIRONMENT` with an environment of `SystemRoot`, `TEMP` and `TMP` only, since without `SystemRoot` the system's own libraries fail to load through side-by-side, and the temporary folder is there so the check tries the real one. Nothing else of the main process's environment crosses.

## What fuji does not use on Windows, and why

- **AppContainer**, which is what would close the network. An AppContainer's process cannot open the user's folder by path; it reads only what its capability SIDs grant or what a broker hands it open. Fuji's inventory walks and opens by path, so the AppContainer waits on the open question in scan.md of how a sandbox process under one would read the folder, and the network stays open on Windows until it is answered.
- **A restricted token** with the user's SID made deny-only, Chromium's other half. It would stop reads of the user's other files, and it would stop reads of the folder too, for the same reason as the AppContainer.
- **The job's crash flag alone.** It silences a fault and not a fast fail, measured, so the error mode carries that wall and the flag is kept only as a second line.
- **`WerSetFlags`** with `WER_FAULT_REPORTING_NO_UI`. Reports were still written to the archive with it set; it changes the dialog, not the collection.
- **The Windows Filtering Platform or a firewall rule** against the network, which need administrator rights fuji does not have and should not ask for.
- **A crash handler inside the sandbox process.** A thread that overflows its stack, as one of mpv's can on a hostile file, leaves a handler no stack to run on, the same reason the Mac answers crashes from the main process; on Windows the error mode does the job without a handler.

## The recovery paths, and how each was tried

Each ending above has a path back to the main process, and each path was driven on this box by `pnpm walk` in copper, which runs `fuji --inventory` and `fuji --sandbox-check` against a built fuji and prints what it saw, and by a scratch program that crashes on purpose behind each candidate wall. The product code carries two test-only request options for the walk, `crash` and `hang`, which the panel never sends.

- **A crash.** The request's `crash` option makes the sandbox process write to address 8 a second into the walk, a fault on any platform. The main process reads the exit code from the process handle, keeps the counts the sandbox process had reported up stderr, and ends the inventory with an error naming the file in hand and the code: "the sandbox process ended without finishing, reading …, exit code: 0xc0000005", in 1.13 s, with no sandbox process left. The walk counts fuji's reports under both WER folders before and after: 0 and 0.
- **A hang.** The request's `hang` option holds the loop at its first progress report past one second, on the loop's own thread, with the stdin watcher still running, which is the shape of a read the kernel never finishes. Nothing inside the sandbox process can end it, and the main process's watcher thread does, with `TerminateProcess` the moment Stop is set: the walk sends Stop two seconds in and the sandbox process is gone 0.09 s later, the error naming the file it stuck on. Today Stop and the window closing are the two ways a hang ends; the deadline, after which the main process would kill on its own when the counts stop moving, is a decided item in scan.md not yet built, and so is what the main process does next, resume past the file or stop and say so.
- **Stop in the ordinary case.** The same kill against a sandbox process that is working: gone 0.06 s after Stop on a main-process inventory and 0.08 s on a sandbox one.
- **The main process dies first.** The sandbox process keeps stdin open after its one line of request and ends the moment stdin closes, which happens when the main process ends however it ends. The walk kills the main process with no warning two seconds in: the sandbox process is gone 0.03 s later, and none is left half a second after.
- **Memory.** The check asks for twice the job's limit through the heap and is refused: "memory allocation failed because the memory allocator returned an error". A demuxer that asked for the same would get a null from `av_malloc`; a Rust allocation would abort, which is a fast fail, which is quiet.
- **The walls, from inside.** `fuji --sandbox-check <folder> <file outside>` puts the walls on itself and tries each reach, printing ok or NO beside what full walls would answer. After the Windows walls it prints, refused: write a file in the folder, write a file in the temporary folder, start a program, set a value under the user's registry, read or write the memory of the process that started it, take more memory than the limit, report a crash to Windows Error Reporting. Allowed, and so printed NO: read a file outside the folder, list the folder above it, connect to this machine, and end the process that started it. The first three are the walls Windows offers no process on its own; the fourth is new knowledge from this check, below.
- **The same file.** Inside the walls the inventory wrote the same file as the main process, line for line with the accessed times aside: 72 lines on steel's samples, which hold video and so drive the probe, 12,094 lines under `node_modules/.pnpm`, and 72 again on the samples named through a junction, which Windows resolves by the name.

## What was measured

**The crash spike.** A scratch Rust program with no dependencies, driven by a PowerShell script, crashing four ways behind each wall, 44 runs on 2026-10-25, counting WER reports naming it under `C:\ProgramData\Microsoft\Windows\WER` and the user's `%LOCALAPPDATA%` folders, polling for `WerFault.exe` and the just-in-time debugger, reading the exit code, and reading the Application log for events 1000 and 1001.

| wall | access violation | stack overflow | Rust abort | C abort() |
|---|---|---|---|---|
| none | WerFault 1 to 1.4 s, a report, events 1000 and 1001 | the same | the same | the same |
| error mode, SEM_NOGPFAULTERRORBOX | dies in 0.02 to 0.05 s, no WerFault, nothing written | the same | WerFault for 0.1 s, nothing written | the same |
| job, DIE_ON_UNHANDLED_EXCEPTION alone | quiet | quiet | a report | a report |
| WerSetFlags NO_UI | a report | a report | a report | a report |
| error mode at Low or Untrusted integrity | quiet | quiet | quiet | quiet |

The exit code reached the parent in every row. No dialog appeared in any run, because this box has `DefaultConsent` set to 4 under HKLM, send everything without asking; the documented default is 1, always ask, so a user's machine without the walls would show the dialog this box does not. The just-in-time debugger registered here, `vsjitdebugger.exe`, never launched, since it has no `Auto` value.

**Error modes are inherited, and node's hides crashes.** A new process inherits its parent's error mode unless started with `CREATE_DEFAULT_ERROR_MODE`. Measured at the start of a child process: 0x8003 under node, whose libuv sets `SEM_NOGPFAULTERRORBOX` in every child, 0x8001 under PowerShell, 0x3 under cmd and bash. The walk's crash step, which runs under node, counted zero reports on 2026-10-25 before any wall existed, a pass nothing had earned; the sandbox process is now started with its own default mode and sets 0x8003 itself, so the step's zero on 2026-10-26 is a real one.

**The integrity level, by itself.** The same scratch program lowering its own token and trying reaches. At Low: a write to the temporary folder refused, error 5; a write under `LocalLow` allowed; a read of the user's own file allowed; listing the profile allowed; `LoadLibrary` of a system library allowed; a connection to this machine allowed; starting a program allowed; a value set under HKCU refused. Low with the job's one-process limit: starting a program refused, error 1816. Untrusted: as Low, and the write under `LocalLow` refused too; reads, library loads, the connection and the program still allowed without the job. Lowering a token in place with `SetTokenInformation` worked for both labels with no privilege.

**Ending the parent.** The check opens the process that started it for `PROCESS_TERMINATE`, as the unix check sends signal 0 to its parent, and at Untrusted the open succeeded, while an open for `PROCESS_VM_READ | PROCESS_VM_WRITE | PROCESS_VM_OPERATION` was refused. The likeliest reason is that terminate sits in a process object's execute mapping, which the default label policy of no-read-up and no-write-up does not cover. A subverted sandbox process could therefore end fuji, a denial and not an escape, where on the Mac and Linux it cannot signal the main process at all. The thing to try is the main process labeling its own process object no-execute-up at startup, after which the check's line would say whether the open is refused; it is an open item in scan.md.

**The walk, whole, on the debug build of 2026-10-26**, the lines as printed, trimmed:

| step | saw |
|---|---|
| check | 7 refused as they should be, 2 allowed as they should be, 4 allowed that fuller walls would refuse |
| same, samples | 0.75 s main, 0.45 s sandbox, 72 lines each, identical |
| same, .pnpm | 149 s main cold, 26 s sandbox warm, 12,094 lines each, identical |
| link | 72 lines each through a junction, identical |
| stop | ended 0.06 s and 0.08 s after Stop, 0 sandbox processes left |
| crash | exit 1 in 1.13 s, 914 lines, exit code 0xc0000005 named with the file, 0 reports before and after |
| hang | 977 lines, ended 0.09 s after Stop, the file it stuck on named, 0 left |
| kill | ended 0.03 s after the main process was killed, 0 left half a second after |

**Builds.** The debug build with the new windows crate features took 1m11s; the release build 1m43s, and the installer, 20 MB, 23.6 s. The Mac letter's belief that a release build has no console for `fuji --inventory` to answer on is wrong on Windows: the GUI-subsystem executable answers through pipes the same as the console one, so `FUJI=` can point the walk at the installed copy.

**Copper's tests on Windows.** 21 of 22 pass. The one failure predates this work and is not in the sandbox: the thumbnailer's test of a header claiming more than the machine holds writes a hundred-byte TIFF whose directory claims a square past half the machine's memory, and WIC answers "The component cannot be found" (0x88982F50) rather than reading the size and refusing; either the test's TIFF or the wall's Windows half wants a look.

## What stays open on Windows

- **Reads outside the folder and the network.** Both are allowed, and together they are the leak: a subverted sandbox process can read what the user can read and send it out. The job and the integrity level wall persistence, no write, no program, no registry, no autostart, and not confidentiality. The AppContainer is the answer to the network and waits on the folder question; a per-folder read wall has no Windows mechanism a process can put on itself.
- **Ending the main process**, above, with no-execute-up to try.
- **The deadline**, and what the main process does once the sandbox process is gone mid-run, both platform-independent and both decided in scan.md.
- **Windows 11 by sight.** Everything here is Windows 10 22H2. The calls are all Windows 8 era or older, the job's nesting included, and Windows 11's WER, error mode and integrity mechanism are the same; the test box will say.
- **The handle-list race**, microseconds wide, documented in the code and real only if the main process spawned a `Command` on another thread during the start.
- **The thumbnailer's test**, above.

## Facts for the article

Stated the way a site page states them, without the rig or the trail, for the second half's Windows paragraphs.

- On Windows the sandbox process runs at the Untrusted integrity level inside a job object that allows it no other process, a gigabyte of memory, and none of the desktop: no clipboard, no window of another program's, no display settings. It cannot write a file or a registry value the user owns, start a program, or read or write another process's memory. It can read what the user can read, and it can reach the network.
- A crash of the sandbox process, a fault or an abort, ends that process alone. Fuji names the file that was being read and the code it ended with, and Windows shows no dialog and writes no report, because the sandbox process turns the system's reporter off for itself before it reads a byte.
- A file that stalls the sandbox process is ended by Stop at once, whatever it was doing, and fuji names the file it stalled on.
- If fuji itself ends while the sandbox process is running, the sandbox process ends with it within a few hundredths of a second.
- The sandbox process is started holding its three streams and nothing else of fuji's, with an environment of three names.
- These are the walls Chromium puts around a renderer on Windows, less the AppContainer that would close the network.
