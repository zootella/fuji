# Inventory

What is still to build around the main process's orchestration of the sandbox process, so that every look at a file ends in one of its outcomes: a quick answer, a fast error that says what went wrong, a crash, which should not happen and may be malice, or a hang the main process ends.

## The sandbox process timeout

- **What it is.** The main process's answer to a file that never finishes. When the sandbox process's counts stop moving for the timeout's length, the sandbox process has timed out; the time starts over whenever the counts move, so an hour hashing a large file never times out and a read stuck in the kernel does.
- **What it is for.** An overnight run nobody watches. A problem that belongs to the file moves the inventory on past the file; a problem that belongs to the drive or the computer stops it, rather than hammering a failing disk.
- **Telling the two apart.** When the sandbox process times out, its processor time over the stall says which: climbing, it is working on the file and getting nowhere, a demuxer's loop; flat, it is waiting in the kernel on a read that does not return, a dying disk retrying a sector, a dropped share, a drive asleep. A crash is the file's. The main process reads the sandbox process's processor time with `proc_pid_rusage` on the Mac, from `/proc/<pid>/stat` on Linux, and with `GetProcessTimes` on Windows.
- **The probe's own wait muddies that.** Inside the sandbox process the probe gives up after its own ten seconds and leaves mpv's player thread spinning, and such a thread keeps the processor time climbing through a later stall on the drive. The stall is judged clean only when the probe in the sandbox process waits longer than the timeout, so the main process's kill ends every stall, spinners included.
- **Past a file.** The main process kills the sandbox process, writes the file's line itself, saying the file hung or crashed it, and starts a new sandbox process that resumes after that file, the output reopened for appending. The walk lists a tree in the same order every run, so resuming is skipping to the name after the file.
- **Stopping.** The main process kills the sandbox process and ends the inventory saying the drive stopped answering, and which file it was reading.
- **The timeout's length.** A hash reports every megabyte and the probe's own wait is ten seconds, so a healthy file reports far inside thirty seconds.
- **The walk's steps.** The crash step goes on past the crashed file; the hang option becomes two, a busy hang the walk expects skipped and an idle one it expects to stop the run.
- **A deadlock.** Two of mpv's threads waiting on each other sit idle, look like the drive, and stop a run that could have gone on.
- **Why a kill, and nothing gentler.** FFmpeg checks its interrupt callback before each protocol read, at each turn of `find_stream_info` and in an HLS playlist's waits, and never inside `open()`, a decoder, a demuxer's loop bound by the processor, a recursive free or a probe function, read from FFmpeg 9.0.2's source ([avio.h](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/avio.h)), so it bounds waiting on input and nothing else.
- **A memory ceiling, on the Mac and Linux.** Windows' job caps the sandbox process at a gigabyte. The Mac ignores `RLIMIT_AS`: a 2 GB allocation succeeded after a 512 MB limit was asked for, on the Mac mini, so a ceiling there is the main process watching the sandbox process's memory and killing it. Linux takes `RLIMIT_AS` ([setrlimit(2)](https://man7.org/linux/man-pages/man2/setrlimit.2.html)). A 17-byte file once made FFmpeg's IAMF demuxer allocate gigabytes while probing ([CVE-2026-66037](https://www.cve.org/CVERecord?id=CVE-2026-66037), fixed in 9.0.2).
- **Prior art for the timeout.** Tracker gives each file five seconds and then ends its extractor ([tracker-extract.c](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract.c)). Windows Search forcibly ends a filter that stops answering ([Microsoft](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/incomplete-search-results-occur-if-pdf-ifilter-installed)). Jellyfin starts an `ffprobe` per file with no timeout on it ([MediaEncoder.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs)), as Immich and Nextcloud do, and users report scans stuck at 95% on a probe that never finishes (reported). Immich replaces each ExifTool worker after 500 tasks or five minutes ([batch-cluster](https://raw.githubusercontent.com/photostructure/batch-cluster.js/main/src/BatchClusterOptions.ts)).
- **Windows' clock.** Whether the clock Rust's `Instant` reads on Windows counts through sleep, which would make a laptop that slept mid-run wake to a stopped inventory; on the Mac and Linux it does not count sleep.

## Further safeguards

- **Remembering a file that hung or crashed the sandbox process across runs**, so it is never asked again. The user's first idea, a durable file of the failed files' hashes, raises three questions: what a file of hashes says about what the user has, whether a hash of part of a file could block a different file, and the cost of hashing every file before asking. Proposed and not adopted: the failure is one more answer in the row a store of answers keeps for the file, keyed by its path, size and modified time, a file that changes being a new file with one new try.
- **Prior art for remembering.** Tracker writes the path before each file to a descriptor its [watchdog](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/miners/fs/tracker-extract-watchdog.c) keeps across restarts, so the next extractor logs "failed in previous execution, ignoring" and [marks the file](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract-decorator.c) never to be read again. The freedesktop [thumbnail specification](https://specifications.freedesktop.org/thumbnail/latest/failures.html) remembers a failure as an empty PNG in a fail folder, carrying the file's address and modified time. KDE's Baloo [halves a failed batch](https://invent.kde.org/frameworks/baloo/-/raw/master/src/file/filecontentindexer.cpp) until one file is left and marks it, and with no timeout [a corrupt file still hangs it](https://bugs.kde.org/show_bug.cgi?id=375131). Windows Search ends a stuck filter without remembering the item, which once meant [indexing the same file over and over](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/incomplete-search-results-occur-if-pdf-ifilter-installed). Writing the path down before handing a file over attributes even a crash of fuji, or of the machine, to that file.
- **Copper's own binary** as the sandbox process, linking the media library and the standard library; the entry, the pipe, the counts and the kill are the same code in either binary. It would leave WebKit and Tauri unloaded, and not AppKit or CoreFoundation, which the media library links itself.
- **Keeping decoders out of the probe.** FFmpeg's search for a file's streams can open decoders to fill in what a header leaves out, even with no track selected: `avformat_find_stream_info` "tries to read and decode a few frames to find missing information", in [FFmpeg's documentation](https://ffmpeg.org/doxygen/trunk/group__lavf__decoding.html). A DVD-style MPEG-2 clip came back with no `demux-par`, which suggests nothing was decoded there, and passing `codec_whitelist` through `demuxer-lavf-o` would make sure, keeping every decoder out of the probe's reach.
- **A fresh sandbox process every so many files.** One sandbox process takes a whole inventory, so code a file ran inside it stays for every later file and can write any answer for them. Starting a new one every few hundred files, as Immich replaces each ExifTool worker after 500 tasks, would limit how far one file's code reaches.
- **Handing the sandbox process files rather than a folder.** Windows Search, Android's media extractor and Chrome hand their parsing process bytes or an open file and never a path, so its wall can refuse every open; fuji's sandbox process opens files itself, inside a wall around the folder. Handing it each open descriptor instead, over a Unix socket as `SCM_RIGHTS` on the Mac and Linux and by `DuplicateHandle` with read access on Windows, would narrow the wall from the folder to the file in hand, and FFmpeg reads either through an `AVIOContext` with read and seek callbacks ([avio.h](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/avio.h)).
- **Which process reads a picture the tip scan cannot answer.** A feature that asks a file its shape can ask the web engine, which reads it in its sandboxed content process, rather than the operating system's thumbnailers, which read it in the main process.
