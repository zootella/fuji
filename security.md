# Security

Fuji's threat model, where it parses bytes nobody vouches for, the walls it has, the walls it is building, and the research behind each, which is the raw material for the security article in Craftsmanship. Every claim about fuji's code was read from the source on the Mac mini between 2026-10-15 and 2026-10-18, and every claim about the world is in a research section below with its source.

## The threat model

**Every file is untrusted, and fuji parses files nobody chose.** A collection holds files of unknown origin whose names need not describe their contents, and fuji opens them in bulk with no one choosing each: the contact sheet thumbnails a whole folder the moment it opens, and scan reads a whole drive overnight. That is the property every precedent in the research shares. Stagefright was reached through MMS, Chris Evans's exploits through a file manager's thumbnailer and the Tracker indexer, FORCEDENTRY and BLASTPASS through iMessage attachments. A parser reached without a choice is one an attacker reaches by putting a file where it will be looked at: a download folder, a USB drive, a share.

**A file's name bounds nothing.** Every parser fuji uses chooses its decoder from the bytes: ImageIO, WIC, both web engines and FFmpeg. Evans's NSF music file was named `.mp3` and his SNES one `.flac`, and NSO's PDF was named `.gif`. So no check on a name or an extension limits what code a file reaches. What limits it is which parsers are compiled in and allowed to run, and which process they run in.

**Broken files are common, hostile files are rare, and the design meets both.** A drive of downloads holds truncated, corrupted and mislabeled files by the thousand, and fuji meets them every day, so they decide most of the design: a truncated MP4 whose header still claims its full running time is a wrong answer that looks right. Hostile files are rare and the stakes are the machine. No public report documents an FFmpeg bug exploited in the wild, and CISA's catalog of exploited vulnerabilities lists none; it lists FreeType twice, and the image parsers behind FORCEDENTRY and BLASTPASS. FFmpeg's record is a large volume of memory-safety bugs found by fuzzing, over three thousand fixes citing OSS-Fuzz since 2017, which says such bugs are found often and fixed fast, and that more remain in a build with every demuxer and decoder.

**An attacker wins what the parsing process can do.** Code running in a process can do whatever that process may: read the user's files, write to them and to the places programs start from, open network connections, start programs. Fuji's main process runs with the user's full rights, so code that takes it over has all of them. Chromium's Rule of 2 names the combination to avoid: untrustworthy input, a parser in an unsafe language, and a process with high privilege, of which any two are acceptable and all three are not.

**The storage is untrusted in a different way.** A share that drops, a disk that sleeps, a failing disc that retries a sector for minutes, a cloud placeholder that downloads on read, and a FIFO that blocks whoever opens it: a call into any of them may never return.

**Out of scope:** a compromised operating system, a kernel bug, which no sandbox stops, and anyone with the machine in hand.

## Three outcomes

Every call that reaches past code fuji controls, a read, a decode, a probe, ends one of three ways: it succeeds, it fails, or it never returns. Failure has layers: an error the far side reports; a failure by another channel, a panic or a crash; a wrong answer that looks right; and malice, input built to make the far side do what its authors never meant. Fuji's rule at every call out is to turn each of these into a value the caller can reason about. The third outcome is the one ordinary testing never meets, because every disk a developer tests on answers in milliseconds.

## Where fuji parses untrusted bytes

| parser | what it reads | process | sandbox |
| --- | --- | --- | --- |
| the scout, fuji's own reader in Rust | a file's format, a picture's or a video's stored size and the size to show it at, and a sound's or a video's running time, from its first 64 KiB and one more slice where the header points | fuji's own today, on the blocking pool; a scan process to come | memory safety, and the scan process's sandbox to come |
| the web engine's image decoders | the tables' pictures where the engine reads the kind, the page route's thumbnails, GIF and SVG tiles, and the size of every picture scan's reader cannot answer | the web engine's content process | on the Mac and Windows; WebKitGTK's on Linux unchecked |
| ImageIO on the Mac, WIC on Windows | the native route's thumbnails, and the tables' pictures of the kinds only these read, a TIFF on Windows and a Photoshop file, a Targa, a PICT or a camera raw on the Mac | fuji's own | none |
| libmpv: FFmpeg's demuxers and decoders, libass, FreeType, HarfBuzz, FriBidi, libplacebo, lcms2 | a file the user plays | fuji's own | none |
| mpv's player with FFmpeg's demuxers alone and no track selected, planned | the running time and size of a file with a video or audio extension, and a frame from a video | a scan process | planned |

Two rows hold all three of the Rule of 2's properties today. The native road is reached with no choice: its thumbnails when a folder opens, and a whole picture when a table comes within reach of one. Playback is reached by choosing a file, a narrower door, though wider than it looks: when a Matroska file's subtitle track starts, mpv hands every font attachment to libass, which loads each through FreeType before any glyph is drawn and whether or not a subtitle uses it (read from mpv 0.41.0's `sd_ass.c` and libass 0.17.5's `ass_fontselect.c`).

**The web engine's sandbox does not protect fuji as things stand.** Code that takes over the content process can call every command the page can, and `disk_read`, `disk_write`, `disk_copy` and `process_open` take any path, so a compromised renderer reaches the user's files and can start a program, one step from the unsandboxed processes. The path scope below is the wall for that.

## Walls fuji has

- **Libraries chosen for the scrutiny they get, and built from their own releases.** Every parser fuji ships is free software among the most examined code that reads media: FFmpeg has been fuzzed by Google since before 2014 and by OSS-Fuzz since 2017, with more than three thousand fixes, and mpv, FreeType, HarfBuzz, libass, dav1d, zlib and lcms2 are all in OSS-Fuzz; libplacebo, the renderer, is not, and reads pixels and settings rather than a file's structure. Their bugs are found and fixed in public. The web engines that draw fuji's page, WebKit and Chromium's in WebView2, are among the most attacked and most defended code there is. The operating system's own imaging libraries, ImageIO and WIC, are the exception, closed source and patched by Apple and Microsoft, and fuji uses them for the native route's thumbnails, for the tables' pictures of the kinds only they read, and nowhere in scan.
- **Provenance a reader can check.** The recipe builds every library from each project's own release, pinned by SHA-256 or by git commit, never from someone else's build; it writes a record of each library it makes, the library's hash, the recipe's own hash, the tools and every source; the ledger in git dates every build; each release's sidecar carries its library's record; `pnpm hash` refuses a library the recipe did not build; and the Mac's library comes out the same to the byte from every build.
- **The full breadth, narrowed where it is used.** The library keeps every demuxer and decoder, since the formats of forty years of collecting are the mission, and each use narrows what runs at run time, scan asking with no track selected and FFmpeg's demuxers alone, so the posture changes without rebuilding the library.
- **The recipe builds whole classes out.** FFmpeg is built with no network and `file` as its only protocol, which removes `concat:`, `subfile:`, `data:`, `pipe:`, `fd:` and HTTP, the protocols the playlist attacks of 2016 and 2017 used to read local files and send them out. It is built without libxml2, so its DASH demuxer is not in the library. mpv is built without Lua, JavaScript and ytdl, so no script runs, and CVE-2018-6360's road through `ytdl_hook.lua` is not there.
- **Versions past the known bugs, with two open.** dav1d 1.5.4, zlib 1.3.2, lcms2 2.19, FreeType 2.15.0, HarfBuzz 14.6.0 and FriBidi 1.0.17 are past every CVE the research found, and FFmpeg 9.0.2 carries the fixes for PixelSmash, the IAMF probe's runaway allocation and the VobSub demuxer's overflow. Open against what fuji ships: CVE-2026-107678, an MP4 with tens of thousands of `pssh` boxes that exhausts the stack and burns quadratic time in the MOV demuxer, its fix still a pull request; and CVE-2026-95127, signed overflow in libass 0.17.5 that wraps to garbage coordinates. A pinned release receives a fix only through the recipe, one hash line per package.
- **A ceiling before a decode allocates.** `thumbnail_render` and `thumbnail_natural` refuse a header claiming a raster larger than half the machine's memory: the decompression bomb, which needs no bug.
- **The page's own walls.** The content security policy allows only fuji's scripts, its IPC, and blob and data images. A file's name or a path reaches the page only through Vue's escaping interpolation, so it never becomes script. An SVG is shown only in an img, where its scripts never run. No plugin is granted to the page, so its whole reach below is the handler list in `lib.rs`.
- **Failure as a value.** Every command returns a result, and a panic in a command that waits comes back as an error through `run_blocking`; a panic in a command on the window's thread ends the process. The store remembers a failed read or decode on its entry, and the views leave a failed file out, count it and move on.

## Walls fuji is building

**Scan: fuji's own reader in Rust first, the most examined C beneath it, all of it in a sandboxed process of its own.** Every picture exploit in the research was in a decoder written in C or C++: GDI+'s JPEG, the Windows Metafile engine, ImageIO's JBIG2, libwebp, GStreamer's music decoders, FFmpeg's MagicYUV. The code fuji writes to read untrusted bytes is Rust, which no file can make read or write past its memory, and what it hands on goes to the web engine and to FFmpeg, among the most examined code that reads files anywhere, each behind a wall. Each part answers a finding in the research.

- **The scout, fuji's own reader, short and memory-safe.** It names the formats a collection holds most of from a file's first 64 KiB, reads the stored size and the size to show it at, the turn, the running time and whether a picture animates from their headers, asks for one more 64 KiB slice where a header points past the tip, and hands everything else on: no frames, no pixels, no samples. Every read goes through a helper that answers nothing outside the two slices, every offset sum is checked for overflow, every loop moves forward or stops, and no number from the file sizes an allocation. Under those rules, the worst a hostile header can do is make the reader answer nothing, or a wrong size or running time. It cannot run code. A wrong answer lasts only until the web engine, the thumbnailer or mpv reads the file, and finds the right one or refuses the file. Tests against sample files pin its answers, fuzzing examines it, and it is short enough to audit line by line.
- **The web engine for every picture the reader cannot answer**, BMP, anything animated, AVIF, TIFF and the rest: the page loads the file as an image, and on the Mac and Windows the engine's decoders run in its sandboxed content process. The operating system's thumbnailers are not asked, since they run in fuji's own process.
- **mpv's player, asking rather than playing.** Scan asks mpv's player for a running time and a size with no track selected, so no decoder starts, and with `demuxer=lavf`, so mpv's own readers never see the file and FFmpeg's demuxers alone parse it; its headers carry the answers, which FFmpeg with every decoder refused confirmed for sixteen kinds of test media on the Mac mini on 2026-10-16. A frame decodes, from its own player, paused and drawing nowhere. mpv rather than C of fuji's own calling FFmpeg directly, since that C would be new and reviewed only by fuji while mpv's layer has been examined for years, and the two put the same FFmpeg on the file.
- **No file reaches past itself.** `access-references=no`, `ordered-chapters=no` and `autoload-files=no` stop mpv following references, segments in other files and files beside it; in the scan process the file arrives as an open file through mpv's `fd://` address, and the sandbox refuses every other open, so the playlist and concatenation demuxers that open other files fail whatever the file is named.
- **Fewer files asked, which is no wall.** Scan reads pictures with extensions fuji knows, files with no extension whose first bytes look binary, and names holding `jpg` or `jpeg`; it hands FFmpeg only files with a video or audio extension on fuji's list. That keeps a night's work to files likely to answer and keeps FFmpeg off text files it would read as ANSI art. An attacker can name a file anything, so every wall above and below is built for any bytes.
- **A separate process** turns a crash into an answer and makes a hang killable, and gives the sandbox one narrow thing to wrap; by itself it does not stop code an exploit runs, since an unsandboxed process has the user's rights, and the sandbox is what does. A process is all fuji can stop mid-work: FFmpeg checks its interrupt callback before reads and between packets, and never inside `open()`, a decoder, a probe function or a loop bound by the processor, and a thread in fuji's own process runs until it returns.
- **A deadline per file**, past which fuji kills the scan process and starts another, as GNOME's indexer does at five seconds.
- **The path in flight recorded before each request**, and a file that crashed or hung a scan process never asked again. GNOME's indexer works this way, and Windows Search and Baloo before its fix did not, and retried the same file forever. Refusing a second try also denies an attacker the repeated crashes that wear down address randomization, which is why launchd slows BlastDoor's restarts.
- **Brokered files.** Fuji opens each file, after checking it is a regular file, since opening a FIFO blocks, and hands the scan process the open descriptor or handle. The scan process then needs no access to the file system, so its sandbox refuses every open, and the playlist and concatenation demuxers that open other files fail with everything else. Every system the research found that sandboxes its parser hands it an open file or the bytes, never a path.
- **The sandbox itself.** On the Mac, `sandbox_init` with a profile denying opens, writes, the network, new processes and lookups of the system's services, since a process with no network can still ask another program to open an address: unsupported by Apple, used by Chromium and Firefox, and measured working on macOS 15.7.4. On Windows, a job object and a low integrity token first, which stop writes and new programs and leave the network, then an AppContainer fed brokered handles, which stops the network too. On Linux, Landlock and a short seccomp filter, and inside the flatpak the portal's sandboxed spawn.
- **Answers read strictly.** Fuji reads the scan process's line as numbers and nothing else, since a subverted parser can exit cleanly and lie: PixelSmash corrupted Emby's heap and its process exited 0.
- **A scan process replaced every so many files**, about 500, so one subverted without crashing answers for only the files after it, and restarts that slow down after repeated crashes.

**Keeping the library current.** A pinned release starts aging the day it is pinned: NVD matches 42 CVEs to FFmpeg in 2026 and undercounts, two were open against what fuji shipped within days, and a published fix publishes its bug, since the commit shows what was wrong. FFmpeg backports fixes to its release branches, so following the 9.0 branch's point releases brings them with no change to fuji's code, and the recipe makes a bump one line per package. Most FFmpeg bugs are crashes and hangs found by fuzzers, and none is documented as exploited in the wild, so this is maintenance on a cadence rather than an emergency, with a prompt bump for a fix in code fuji reaches.

**A path scope in Rust, for every command that touches the disk.** A registry of the folders the user has shown fuji, kept on the Rust side, with every disk command refusing a path outside them, so a compromised renderer reaches only what the user already chose. `disk.rs` plans it for the delete family, and it belongs to every disk command. Not built.

**The same walls for thumbnails and playback, open.** The native route decodes in fuji's own process and is reached without a choice; a sandboxed process built for scan could take that work too. Playback is harder, since mpv draws into fuji's own window through the render API on the Mac and Linux. Its narrower door is mpv's own options against a file pulling in others from its folder and against its font attachments, a question for Fuji Video.

**A top gate for the page.** The page has no `unhandledrejection` or `error` listener, so a rejection that escapes every gate lands in the web inspector's console, which nobody reads. One listener writing to the log is the page's top gate. Not built.

**A limit on a read.** `disk_read` reads a whole file into memory, and the page holds it more than once on the way to a blob. Nothing compares a read with the file's size, which the listing already knows, so a disk image of gigabytes renamed `.jpg` is read whole the moment a table asks for it.

## Forever

**Almost no call in fuji has a timeout.** No invoke, read or decode is ever abandoned for taking too long; the one exception is `launch_set`, which waits ten seconds for the Mac's answer.

**Where a call that never ends does its damage:**
- **The diamond table stops.** Every flip and every drop goes through one queue, one at a time, and the queue moves only when the work at its head settles, so one load that never settles freezes the table until fuji restarts.
- **A governor's line stops.** Every governor lets four calls through at a time, so four calls that never settle hold all four places, and everything behind them in that line waits for good. The store reads under one name, `disk`, for every view.
- **Threads pile up, by the hundreds.** A command that waits runs on Tokio's blocking pool, a thread each, so a read stuck on a dead share holds one thread nothing else needs; the pool stops at 512, and the governors' widths keep fuji far below it.

**A timeout in the page ends the waiting, never the work.** A read blocked in the kernel cannot be cancelled from Rust, let alone from the page, and a decoder on a pool thread runs until it returns. So the answer for work in fuji's own process is containment: the governor grows a deadline, past which it frees the place and fails the caller's promise, and the view treats the call as failed and moves on while the stuck work finishes or does not on a thread nothing waits for. Scan's work is the exception, because a process can be killed. A run of timeouts on one drive says the drive is failing rather than the files, and pausing that drive's name in the governor stops every caller asking it.

**Forever cannot be tested on the disks fuji is developed on**, so it needs a way to reproduce it on demand: a share pulled out from under fuji, a file system made to answer slowly, a FIFO in a folder.

## What fuji thinks a file is

**Fuji names a file by its extension, and every parser beneath names it again by its bytes.** `fileTypes.js` decides what the listing keeps, how the sheet routes a tile, and what fuji declares to each operating system; ImageIO, WIC, the web engines and FFmpeg each decide from the bytes. A file with a wrong name shows if the parser its route reaches can read it and is left out and counted if not, and no file is tried on a second route.

**A file with no extension is never shown.** The listing keeps only files whose extension fuji knows, so a JPEG saved as `image` is dropped before anything asks what it is, and File → Open… lists every file, so choosing one lands on some other picture in its folder. The scout and scan answer this, since both name a file by its bytes, a JPEG called `image` a 640 by 480 JPEG among them, and a store of what they found names each file once.

**A damaged file is refused whole.** A truncated JPEG fails its decode and is counted. Whether a partial decode should show the part that arrived, the way a browser does, is undecided.

**A name that is not valid UTF-8 is lost in transit.** `disk_readdir` hands names to the page as text, so a name that is not valid UTF-8, which Linux allows and old collections hold, is replaced character by character and can no longer be opened by what came back. A backslash in a Mac or Linux name survives, since `forwardize` turns backslashes into slashes only in a path that starts with a Windows drive letter.

## The article's second half

The history half of the security article is drafted on the site; this half says how fuji is built, from the walls above, as the parts of one strategy, and then what no design can do.

- **The code fuji writes to read untrusted bytes is Rust.** Every exploit in the history was in a decoder written in C or C++, and fuji's own reader, the scout, is short, memory-safe, audited line by line by the user and by an AI review, pinned by tests and fuzzed.
- **The C beneath it is the most examined there is.** WebKit, Chromium's engine and FFmpeg, free software whose bugs are found and fixed in public, rather than commercial, proprietary or closed-source parsers; built from each project's own releases, with a record anyone can check, and kept current.
- **As little of it runs as the job needs.** Scan asks through mpv with no track selected and FFmpeg's demuxers alone; the library is built with no network, no protocol but files, no encoders and no scripting; no file can make FFmpeg open another; and scan asks fewer files, which is volume rather than a wall.
- **It runs behind walls.** A separate scan process, sandboxed on every platform and handed open files and nothing else, and the web engine's own sandboxed process for every picture fuji's reader hands on.
- **When something goes wrong, fuji survives and moves on.** A deadline and a kill for a hang, one try per file for a crash, a scan process replaced every few hundred files, slower restarts after repeated crashes, answers read as numbers and nothing else, and broken files named and remembered rather than tripped over.
- **The page's own walls**, the content security policy, Vue's escaping, SVG only in an img and no plugins, the ceiling on a decode, and the path scope to come.
- **What no design can do.** It cannot make FFmpeg free of bugs or stop an exploit of the operating system's kernel; a subverted scan process can still lie in its answer and read the files it is handed until it is replaced; the Mac's sandbox rests on an interface Apple does not support; Windows has no network wall until the AppContainer; and thumbnails and playback still parse in fuji's own process until they move.

## Research: parsers attacked through files nobody opened

Gathered on 2026-10-15 for the history that opens the security article, every source fetched that day unless marked reported. The article checks each claim again before it publishes.

**Linux, 2016.** Chris Evans took over Ubuntu 12.04.5 with a crafted NES music file through GStreamer 0.10's NSF decoder "without the user opening the exploit file -- they only have to navigate to the folder", because the file manager's thumbnailer parses it, and he named it `.mp3`, since GStreamer "will ignore a file's suffix and use file format auto detection" ([2016-11-14](https://scarybeastsecurity.blogspot.com/2016/11/0day-exploit-compromising-linux-desktop.html)). The next day a web page in Chrome on Fedora 24 dropped a file into Downloads, which Tracker "will auto crawl", and crashed an unconfined `tracker-extract` through a VMnc integer overflow, CVE-2016-9445; he argued that media parsing needs "no writable filesystem access, no network access, no other process access" ([2016-11-15](https://scarybeastsecurity.blogspot.com/2016/11/0day-poc-risky-design-decisions-in.html)). A FLIC file reached Rhythmbox's metadata scanner ([2016-11-21](https://scarybeastsecurity.blogspot.com/2016/11/0day-exploit-advancing-exploitation.html)): "Code that automatically indexes or thumbnails media files really needs to be sandboxed in this day and age." A SNES music file named `.flac` reached tracker-extract on Fedora 25, with a reliable exploit running inside it, and the video thumbnailer on Ubuntu 16.04, through Game Music Emu ([2016-12-13](https://scarybeastsecurity.blogspot.com/2016/12/redux-compromising-linux-using-snes.html)).

**GNOME's answer.** A bug asking whether every thumbnailer could be sandboxed with bubblewrap was opened the day after the first exploit ([774497](https://bugzilla.gnome.org/show_bug.cgi?id=774497)), and Bastien Nocera landed it in gnome-desktop 3.25.90, GNOME 3.26, on 2017-07-21 ([changelog](https://download.gnome.org/sources/gnome-desktop/3.25/gnome-desktop-3.25.90.changes), [his post](https://www.hadess.net/2017/07/security-for-security-gods-sandboxing.html)): `/usr` read-only, no network, the file's name hidden, then seccomp from Flatpak's code. The [current code](https://gitlab.gnome.org/GNOME/gnome-desktop/-/raw/master/libgnome-desktop/gnome-desktop-thumbnail-script.c) starts a new process for each thumbnail with no timeout and no resource limit, and Nocera [measured](https://gitlab.gnome.org/GNOME/gnome-desktop/-/issues/69) MP3s on a Samba share at 2.3 seconds without the sandbox and 3.3 with it. [CVE-2019-11460](https://cveawg.mitre.org/api/cve/CVE-2019-11460) escaped it through the `TIOCSTI` ioctl. The freedesktop [thumbnail specification](https://specifications.freedesktop.org/thumbnail/latest/failures.html) remembers a failure as an empty PNG under a fail folder, carrying the file's address and modified time. Tracker sandboxed its extractor's threads with seccomp on 2016-12-08 ([1.11.2](https://download.gnome.org/sources/tracker/1.11/tracker-1.11.2.changes)), turned the filter to fail every call not allowed by 2023 ([Carlos Garnacho](https://blogs.gnome.org/carlosg/?p=7504)), and added Landlock in 3.7 ([MR 499](https://gitlab.gnome.org/GNOME/localsearch/-/merge_requests/499)). Its design is the closest precedent to scan's: one long-lived extractor started by a [watchdog](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/miners/fs/tracker-extract-watchdog.c) over a socket pair, a deadline of five seconds a file after which the [extractor](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract.c) exits, and the path written before each file to a descriptor the watchdog keeps across restarts, so the next extractor finds it, logs "failed in previous execution, ignoring", and [marks the file](https://gitlab.gnome.org/GNOME/tracker-miners/-/raw/master/src/tracker-extract/tracker-extract-decorator.c) so it is never extracted again. KDE's Baloo keeps a long-lived [extractor](https://invent.kde.org/frameworks/baloo/-/raw/master/src/file/extractorprocess.cpp) fed batches and, when it fails, [halves the batch](https://invent.kde.org/frameworks/baloo/-/raw/master/src/file/filecontentindexer.cpp) until one file is left and marks it failed; it has no sandbox and no timeout, and [a corrupt file hangs it](https://bugs.kde.org/show_bug.cgi?id=375131).

**Windows.** Windows Search ran its filters in `SearchFilterHost.exe` with reduced privileges from the start, which "cannot even read the filesystem", citing a WMF vulnerability Google Desktop Search exposed by indexing without one ([Brandon Paddock, 2007-06-20](https://brandonlive.com/2007/06/20/faq-why-does-wds-windows-vista-use-so-many-processes/)); a job object forbids child processes and caps the working set at 100 MB ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/search/-search-ifilter-about)), and a filter that stops answering is forcibly terminated without the item being remembered, which in one case meant [reindexing over and over](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/incomplete-search-results-occur-if-pdf-ifilter-installed). Explorer runs thumbnail extractors in the COM Surrogate because "Explorer has learned not to trust thumbnail extractors" ([Raymond Chen, 2009-02-12](https://devblogs.microsoft.com/oldnewthing/20090212-00/?p=19173)), and asks them to [take a stream rather than a path](https://learn.microsoft.com/en-us/windows/win32/shell/building-thumbnail-providers). Three bulletins ran code from a folder being looked at: [MS10-046](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2010/ms10-046), a shortcut's icon displayed, which [Stuxnet](https://www.cisa.gov/news-events/ics-advisories/icsa-10-201-01c) spread through from USB drives; [MS11-006](https://learn.microsoft.com/en-us/security-updates/securitybulletins/2011/ms11-006), a thumbnail viewed; and [ADV200006](https://api.msrc.microsoft.com/sug/v2.0/en-US/vulnerability?$filter=cveNumber%20eq%20%27ADV200006%27) in 2020, fonts in the Preview Pane, where on Windows 10 an attack "could only result in code execution within an AppContainer sandbox context", so Microsoft advised against the workarounds there.

**The Mac and the iPhone.** Spotlight's `mds` starts "a heavily sandboxed task called mdworker", whose importers are "not even permitted to read or write any file other than the one being scanned" ([Microsoft, 2025-07-28](https://www.microsoft.com/en-us/security/blog/2025/07/28/sploitlight-analyzing-a-spotlight-based-macos-tcc-vulnerability)), and which spawn, parse some files and die ([Doyensec, 2017](https://blog.doyensec.com/2017/11/15/osx-spotlight.html)). QuickLook's thumbnails moved to sandboxed app extensions in 10.15, and Sequoia dropped the old plug-ins (reported, [Eclectic Light](https://eclecticlight.co/2024/10/31/how-sequoia-has-changed-quicklook-and-its-thumbnails/)). iOS 14's BlastDoor parses almost all untrusted data in iMessage in a tightly sandboxed Swift service, and launchd doubles the wait before restarting it after each crash, up to about twenty minutes, which defeats attacks that need many tries ([Samuel Groß, 2021-01-28](https://projectzero.google/2021/01/a-look-at-imessage-in-ios-14.html)). NSO's FORCEDENTRY then sent a `.gif` that a service outside BlastDoor handed to ImageIO, which parsed it "completely ignoring the file extension" among "over 20 image codecs" and reached JBIG2 inside a PDF, CVE-2021-30860; Apple restricted the formats that service accepts and moved GIF into BlastDoor ([Ian Beer and Samuel Groß, 2021-12-15](https://projectzero.google/2021/12/a-deep-dive-into-nso-zero-click.html)). In 2023 Citizen Lab caught BLASTPASS, PassKit attachments carrying malicious images, CVE-2023-41064 ([Citizen Lab, 2023-09-07](https://citizenlab.ca/2023/09/blastpass-nso-group-iphone-zero-click-zero-day-exploit-captured-in-the-wild/)), and Chrome fixed libwebp's CVE-2023-4863, reported by Apple and Citizen Lab, with an exploit in the wild ([Chrome releases, 2023-09-11](https://chromereleases.googleblog.com/2023/09/stable-channel-update-for-desktop_11.html)); that the two are one bug is reported.

**Android.** Stagefright, 2015: bugs in Android's MP4 and 3GPP parsing, among them CVE-2015-1538, reached through MMS, which fetched and parsed attachments with no one touching them, "the worst of which requires no user-interaction", on an estimated 950 million devices ([Zimperium](https://zimperium.com/blog/experts-found-a-unicorn-in-the-heart-of-android), [CERT VU#924951](https://kb.cert.org/vuls/id/924951)). Android 7 split `mediaserver`, since "media parsers do not require access to most of the privileged permissions held by mediaserver", into processes with no camera, microphone, network or dynamic code, under seccomp ([2016-05-05](https://android-developers.googleblog.com/2016/05/hardening-media-stack.html)); the extractor receives bytes over Binder and never a descriptor ([framework hardening](https://source.android.com/docs/core/media/framework-hardening)). Android 10 moved software codecs into a process of their own, since about 80% of 2018's critical and high media bugs were in them ([2019-05-09](https://security.googleblog.com/2019/05/queue-hardening-enhancements.html)).

**Media servers.** Jellyfin starts an `ffprobe` per file with no timeout on the probe ([MediaEncoder.cs](https://raw.githubusercontent.com/jellyfin/jellyfin/master/MediaBrowser.MediaEncoding/Encoder/MediaEncoder.cs)), as do Immich and Nextcloud, and users report library scans stuck at 95% on an ffprobe that never finishes (reported). Immich runs ExifTool as long-lived workers, each replaced after 500 tasks or five minutes ([batch-cluster](https://raw.githubusercontent.com/photostructure/batch-cluster.js/main/src/BatchClusterOptions.ts)). PixelSmash, CVE-2026-8461, an out-of-bounds write in FFmpeg's MagicYUV decoder, ran code through Jellyfin's library scan with address randomization turned off, and crashed it reliably with randomization on; Emby's heap was corrupted silently and its process exited 0; mpv, Immich and PhotoPrism crashed; and Plex was spared because it builds FFmpeg with decoders disabled and a minimal allow-list ([JFrog, 2026-06-22](https://jfrog.com/blog/pixelsmash-critical-ffmpeg-vulnerability-turns-media-files-into-weapons/), [BleepingComputer](https://bleepingcomputer.com/news/security/ffmpeg-fixes-pixelsmash-flaw-in-widely-used-video-decoder)). ExifTool's DjVu parsing, [CVE-2021-22204](https://cveawg.mitre.org/api/cve/CVE-2021-22204), became GitLab's remote code execution through uploaded images, [CVE-2021-22205](https://cveawg.mitre.org/api/cve/CVE-2021-22205).

**Browsers.** Firefox's RDD process runs media decoders in a sandboxed process of their own, starting with AV1 ([process model](https://firefox-source-docs.mozilla.org/dom/ipc/process_model.html)), and Chrome's media metadata parser receives blob data from the browser process rather than opening files ([media_gallery_util](https://chromium.googlesource.com/chromium/src/+/main/chrome/services/media_gallery_util/)).

**What recurs.** Every system moved parsing into a separate process, and most added a sandbox only after an exploit; Windows Search had both from 2007. The worker receives bytes or an open file, never a path to go and open. A hang is met by a deadline per file that ends the whole worker. A file that crashed or hung the worker is remembered and not asked again, and the systems that skipped this retried the same file forever. Indexers keep one long-lived worker, and thumbnailers and media servers start a process per file. Watching for a crash is not enough, since a subverted parser can exit cleanly. Filtering by extension bounds nothing, since parsers choose by the contents, and the fix that worked was an allow-list of codecs. And sandboxes have holes of their own.

## Research: the libraries fuji ships

Gathered on 2026-10-15, every source fetched that day unless marked reported; CVE records read through the CVE Services API and FFmpeg read at the tag `n9.0.2`. The counts come from matching keywords in commit messages and are approximate.

**FFmpeg's record.** NVD matches 333 CVEs to FFmpeg published from 2015 through 2026, by year 29, 21, 47, 29, 11, 4, 65, 29, 6, 37, 13 and 42; about 211 are memory corruption and 67 denial of service by the weakness NVD assigns, and recent years are undercounted, since a keyword search finds 67 mentioning FFmpeg from July to mid-October 2026 alone ([NVD](https://services.nvd.nist.gov/rest/json/cves/2.0?virtualMatchString=cpe:2.3:a:ffmpeg:ffmpeg&resultsPerPage=2000)). FFmpeg's history holds 3,073 commits citing an OSS-Fuzz test case from February 2017 to October 2026: about 1,270 integer overflow or undefined behavior, 680 timeouts, 370 out-of-bounds reads or writes, 95 leaks, 93 uninitialized memory, 80 out of memory, and 7 use after free or double free. 668 came from the demuxer fuzz target, which opens a file, finds its streams and reads packets, the road scan takes ([target_dem_fuzzer.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/tools/target_dem_fuzzer.c)). Before OSS-Fuzz, Google's own fuzzing produced 1,120 fixes, and Google advised people to "refrain from using either of the two projects to process untrusted media files" ([2014-01-10](https://security.googleblog.com/2014/01/ffmpeg-and-thousand-fixes.html)); OSS-Fuzz counted 17 FFmpeg vulnerabilities in its first five months ([2017-05-08](https://security.googleblog.com/2017/05/oss-fuzz-five-months-later-and.html)).

**What scan's two calls run.** `avformat_open_input` runs the probe function of every demuxer compiled in over up to 1 MiB of the file, then the chosen demuxer's header parser. `avformat_find_stream_info` reads up to 5,000,000 bytes or five seconds of media, runs the parsers, and opens decoders until each stream's parameters are known, which for video takes a pixel format, so the first frames of most video streams are decoded ([demux.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/demux.c), [format.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/format.c), and FFmpeg's documentation: it "tries to read and decode a few frames to find missing information", [lavf decoding](https://ffmpeg.org/doxygen/trunk/group__lavf__decoding.html)).

**Recent bugs, against 9.0.2.** PixelSmash, above, is fixed in 8.1.2 and 9.0, and JFrog does not say whether finding a file's streams alone reaches it. [CVE-2026-66037](https://www.cve.org/CVERecord?id=CVE-2026-66037): a 17-byte file makes the IAMF demuxer allocate gigabytes "during format probing", fixed in 9.0.2. [CVE-2026-64830](https://www.cve.org/CVERecord?id=CVE-2026-64830): a heap overflow in the VobSub demuxer, scored 8.8, fixed in 9.0.2. [CVE-2026-107678](https://www.cve.org/CVERecord?id=CVE-2026-107678), published 2026-10-08 and open against 9.0.2: an MP4 with tens of thousands of `pssh` boxes exhausts the stack through a recursive free and burns quadratic time in the MOV demuxer, its fix [still a pull request](https://code.ffmpeg.org/FFmpeg/FFmpeg/pulls/24593). The other CVEs naming 9.0.2 concern remuxing, the DASH demuxer, which needs the libxml2 fuji's build leaves out, or network handlers fuji does not build. Three uninitialized-memory disclosures, in TIFF, RSCC and LCL, are fixed in 9.0.

**Big Sleep.** FFmpeg's commits credit Google's Big Sleep twelve times between July and September 2025, in its EXR, SANM, DHAV and DASH code, among them [CVE-2025-59733](https://www.cve.org/CVERecord?id=CVE-2025-59733), a heap overflow in OpenEXR's DWAA and DWAB decompression, and [CVE-2025-59734](https://www.cve.org/CVERecord?id=CVE-2025-59734), a use-after-free write in SANM, the LucasArts Smush decoder, both fixed in 8.0. In a public dispute FFmpeg called the Smush report, a bug in "the first 10-20 frames of Rebel Assault 2", "CVE slop" ([It's FOSS, 2025-11-14](https://itsfoss.com/news/ffmpeg-google-fiasco/), [The New Stack](https://thenewstack.io/ffmpeg-to-google-fund-us-or-stop-sending-bugs/); the posts themselves reported), and its [security page](https://ffmpeg.org/security.html) now says "Automated submissions are not accepted." The obscure codec's bug was a real use-after-free write, in a decoder a build with every decoder carries.

**In the wild.** CISA's Known Exploited Vulnerabilities catalog of 2026-10-15, 1,746 entries, lists no FFmpeg bug, and its one FFmpeg mention is a trojanized `ffmpeg.exe` inside another vendor's installer, CVE-2024-4978 ([KEV](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)). The research found no public report of an FFmpeg parsing bug exploited in the wild.

**Files that make FFmpeg open other files.** Maxim Andreev reported in 2016 that an HLS playlist hidden in a file "with any extension: avi/mov" used `concat:` and `file://` to send the first line of a local file to a web server, "when file manager tries to generate thumbnail" ([oss-security, 2016-01-13](https://seclists.org/oss-sec/2016/q1/85); [CVE-2016-1897](https://www.cve.org/CVERecord?id=CVE-2016-1897), [CVE-2016-1898](https://www.cve.org/CVERecord?id=CVE-2016-1898)), and FFmpeg added `protocol_whitelist` and made the concat demuxer safe by default. In 2017 Emil Lerner and Pavel Cheremushkin hid a playlist in an AVI's GAB2 subtitle that read a local file and drew it into the output through the XBIN decoder ([CVE-2017-9993](https://www.cve.org/CVERecord?id=CVE-2017-9993), [proof of concept](https://github.com/neex/ffmpeg-avi-m3u-xbin)), and FFmpeg's fix admitted leaks remain possible "from files and symlinks ending in common multimedia extensions" ([189ff4219](https://github.com/FFmpeg/FFmpeg/commit/189ff4219)). Hardening continued: HLS probing refuses files not named `.m3u8` or `.m3u` since 2023, `extension_picky` since 2025, and two playlist bypasses fixed in 9.0.2. With `file` as the only protocol, what remains in 9.0.2: an HLS playlist named `.m3u8` or `.m3u` opens local paths with allowed extensions, and a live one reloads up to 1,000 times; an ffconcat file, detected by its content under any name, opens relative paths below its own folder, symlinks included; image2 is chosen by a name holding `%d`, `*`, `?` or `{`; MOV's external references are off by default ([hls.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/hls.c), [concatdec.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/concatdec.c), [img2dec.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/img2dec.c)). FFmpeg opens a file with a blocking `open()` and checks its interrupt callback only before reads, so a FIFO, met directly or as a playlist's segment named `.ts`, blocks until something writes to it ([file.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/file.c), [avio.c](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/avio.c)).

**mpv.** [CVE-2021-30145](https://www.cve.org/CVERecord?id=CVE-2021-30145), fixed in 0.33.1: a format string in `demux_mf`, carried by an `mf://` address an m3u playlist can deliver ([fix](https://github.com/mpv-player/mpv/commit/d0c530919d8cd4d7a774e38ab064e0fabdae34e6)). [CVE-2018-6360](https://www.cve.org/CVERecord?id=CVE-2018-6360): `ytdl_hook.lua` accepted addresses that led to `dlopen`. mpv's [manual](https://mpv.io/manual/stable/) says playlists get safety checks since 0.31.0, calls `--access-references=no` "helpful if the file is automatically scanned (e.g. thumbnail generation)", says `--ordered-chapters`, on by default, makes mpv "load and search for video segments from other files" in the folder, and warns that `--use-filedir-conf` "May be dangerous if playing from untrusted media". mpv is in OSS-Fuzz.

**Subtitles and fonts.** Check Point's "Hacked in Translation" took over VLC, Kodi, Popcorn Time and Stremio, about 200 million installs, through subtitle files ([2017-05-23](https://research.checkpoint.com/2017/hacked-in-translation/)); VLC's were heap bugs in its subtitle decoder, [CVE-2017-8310](https://www.cve.org/CVERecord?id=CVE-2017-8310) to 8313, and Kodi's a path traversal through a zip as subtitles, [CVE-2017-8314](https://www.cve.org/CVERecord?id=CVE-2017-8314). libass: [CVE-2020-24994](https://www.cve.org/CVERecord?id=CVE-2020-24994), a stack overflow in `parse_tag`; [CVE-2020-36430](https://www.cve.org/CVERecord?id=CVE-2020-36430), a heap overflow decoding fonts embedded in scripts, found by OSS-Fuzz; and [CVE-2026-95127](https://www.cve.org/CVERecord?id=CVE-2026-95127), published 2026-10-13 against 0.17.5, signed overflow from extreme numbers in a subtitle that in a normal build "silently wraps to garbage coordinates", its fix [a pull request](https://github.com/libass/libass/pull/955) ([issue](https://github.com/libass/libass/issues/947)). FreeType's [CVE-2025-27363](https://www.cve.org/CVERecord?id=CVE-2025-27363), an out-of-bounds write in variable-font subglyphs up to 2.13.0, "may have been exploited in the wild" by [Facebook's advisory](https://www.facebook.com/security/advisories/cve-2025-27363), with "limited, targeted exploitation" by [Android's bulletin](https://source.android.com/docs/security/bulletin/2025-05-01), and entered the catalog on 2025-05-06; who exploited it and how is not public. CVE-2020-15999, FreeType's bug in PNG images inside fonts, was used in a Chrome exploit chain and is in the catalog. Font attachments reach FreeType in playback ([sd_ass.c](https://github.com/mpv-player/mpv/blob/v0.41.0/sub/sd_ass.c), [ass_fontselect.c](https://github.com/libass/libass/blob/0.17.5/libass/ass_fontselect.c)), and never in scan, since libavformat carries attachments as bytes and fuji's FFmpeg is built without libfreetype.

**The rest of the library.** dav1d's [CVE-2024-1580](https://www.cve.org/CVERecord?id=CVE-2024-1580), an integer overflow on large frames, is fixed in 1.4.0; zlib's [CVE-2022-37434](https://www.cve.org/CVERecord?id=CVE-2022-37434) is reachable only through `inflateGetHeader` and is fixed after 1.2.12; lcms2's integer overflows are fixed by 2.19, and mpv hands a file's embedded ICC profile to lcms2 only when a display profile is in use. libplacebo has no CVE in NVD and, alone among the library's parts, no OSS-Fuzz project.

**Denial of service.** Timeouts are the second-largest class of OSS-Fuzz fixes, about 680 of 3,073 and 103 of the demuxer target's 668, where timeout means past the fuzzer's limit rather than necessarily endless. The interrupt callback aborts a blocking operation when it returns 1 ([avio.h](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/avio.h)), and FFmpeg checks it before every protocol read, at each `find_stream_info` iteration and in HLS reload waits, and never inside `open()`, inside a decoder, in a demuxer's loops bound by the processor, in a recursive free or in a probe function, so it bounds waiting on input and nothing else (read from the 9.0.2 source). The limits that bound work, from [options_table.h](https://github.com/FFmpeg/FFmpeg/blob/n9.0.2/libavformat/options_table.h): `probesize` 5,000,000 bytes, `formatprobesize` 1 MiB, `analyzeduration` five seconds, `max_probe_packets` 2,500, `max_streams` 1,000, `max_ts_probe` 50 and `duration_probesize`, with libavcodec's `max_pixels` and `max_samples` passed through `find_stream_info`'s options.

## Research: walls around a worker

Gathered on 2026-10-15 for the security article and for scan's design, every source fetched that day unless marked reported. The article checks each claim again before it publishes.

**The principle.** Chromium's [Rule of 2](https://chromium.googlesource.com/chromium/src/+/main/docs/security/rule-of-2.md): of untrustworthy inputs, an unsafe implementation language and high privilege, pick no more than two. The page calls a process running as the person's own account high privilege and a sandboxed utility process low, and its approved designs are to parse in a sandboxed process and validate what it returns, or to write the parser in a memory-safe language. A separate process with no sandbox buys a crash that can be noticed and a hang that can be killed, and nothing against an exploit: Chromium's [multi-process architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/) credits only the operating system's limits on files and network with containing a compromised renderer, and its [sandbox FAQ](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox_faq.md) says sandboxed code cannot install persistent malware because writing to the filesystem is banned, and that no sandbox stops a kernel bug. A long-lived worker, once exploited, stays exploited for every later file and can falsify those answers, which restarting it every so many files limits.

**Brokered files, the strongest form, on every platform.** The main process opens each file and hands the worker the open descriptor or handle, so the worker's sandbox can refuse every open by path. A descriptor crosses a Unix socket as SCM_RIGHTS on the Mac and Linux ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)); a handle crosses by [`DuplicateHandle`](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) on Windows, asked for with read access rather than the same access, which can come out larger. FFmpeg reads either through a custom `AVIOContext` with read and seek callbacks ([avio.h](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/avio.h)), which needs no protocol; the recipe builds FFmpeg with `file` as its only protocol, so the `fd` and `pipe` protocols are not in the library, and FFmpeg's own Windows [`handle` protocol](https://github.com/FFmpeg/FFmpeg/commit/1ae485ba98381cbb2505e75a0666c40c77f3d8de) reached its main branch on 2026-10-10 and is in no release. Chromium brokers this way on Windows and the Mac, and Android's media extractor goes further, [receiving bytes over Binder and never a descriptor](https://source.android.com/devices/media/framework-hardening).

**The Mac.** `sandbox_init` with a custom profile string, called by the worker on itself before its first request. It is deprecated since 10.8 and outside what Apple supports, "We don't support custom sandboxes at all", in [Apple's developer forums in March 2024](https://developer.apple.com/forums/thread/747880), and Chromium ([seatbelt.cc](https://chromium.googlesource.com/chromium/src/+/main/sandbox/mac/seatbelt.cc)) and Firefox ([Sandbox.mm](https://github.com/mozilla-firefox/firefox/blob/main/security/sandbox/mac/Sandbox.mm)) both call it. Measured on the Mac mini under macOS 15.7.4 on 2026-10-15: a forked process applied a profile in 5 ms, then failed with EPERM to open a user file by path, to connect over TCP and to start a process, and read a descriptor it received over a Unix socket after the sandbox was on. Xcode 27's manual page, quoted on the [OpenSSH list in August 2026](https://lists.mindrot.org/pipermail/openssh-unix-dev/2026-August/042690.html), says processes using the named `kSBXProfile` profiles against SDK 27 will be killed, and nothing found says the custom-profile road is affected. Chromium's [V2 design](https://chromium.googlesource.com/chromium/src/+/af7f13600046b6fa4c007577e7fe6b24e1038903/sandbox/mac/seatbelt_sandbox_design.md) applies its profile from a helper that links only libSystem, before any framework loads, with every profile starting from deny. Fuji's one executable links AppKit, WebKit and the media library, whose initializers run before the lock, which holds as long as no untrusted byte arrives until after it. Apple's supported road is a helper or XPC service with the App Sandbox entitlement and without `com.apple.security.inherit`, which [kills a child of an unsandboxed parent](https://developer.apple.com/forums/thread/706390), and it needs an executable of its own.

**Windows.** Chromium's [model](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md): a restricted token at Untrusted integrity, a job object allowing one process, an alternate desktop, AppContainer mainly to deny the network, and handles brokered from the browser. A plain Win32 program can adopt it in two steps. First a job object with a memory limit, one process, kill on close and no crash dialog ([JOBOBJECT_BASIC_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)), and a [low integrity token](https://learn.microsoft.com/en-us/previous-versions/dotnet/articles/bb625960(v=msdn.10)), which stops writes to most of the profile and HKCU and still [reads the user's files](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control) and opens sockets. Then an [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) with no capabilities, which cannot reach the network or open the user's files by path, fed brokered handles. The AppContainer needs read and execute on its own executable and dlls, which Chrome's installer grants ([configure_app_container_sandbox.cc](https://chromium.googlesource.com/chromium/src/+/main/chrome/installer/setup/configure_app_container_sandbox.cc)) and fuji's per-user install folder would need too; whether an executable that imports user32 and WebView2 starts inside one is untested. No mature Rust crate does this, so it is a few hundred lines against the `windows` crate.

**Linux.** [Landlock](https://docs.kernel.org/userspace-api/landlock.html) for files, after `no_new_privs`, with every filesystem right handled and none allowed; files opened before it stay usable, so brokered descriptors work. Debian 12's 6.1 kernel reaches Landlock ABI 1, files only, and Ubuntu 24.04's 6.8 reaches ABI 4, which adds TCP ([the landlock crate's ABI table](https://docs.rs/landlock/latest/landlock/enum.ABI.html)), so the network needs a seccomp filter on older kernels; the kernel's own page says ["System call filtering isn't a sandbox"](https://docs.kernel.org/userspace-api/seccomp_filter.html). Namespaces are out, since Ubuntu 24.04 grants no capabilities in an unprivileged user namespace ([release notes](https://documentation.ubuntu.com/release-notes/24.04/)). Inside the flatpak, nested bubblewrap is blocked by [flatpak's seccomp list](https://github.com/flatpak/flatpak/blob/main/common/flatpak-run.c), Landlock and a further seccomp filter are not on it (untested), and the [portal's Spawn](https://github.com/flatpak/flatpak/blob/main/data/org.freedesktop.portal.Flatpak.xml) starts a new instance of the application in a tighter sandbox with no network, taking descriptors. Of the crates, `landlock` is active, `seccompiler` moved into rust-vmm's mono-repo, and `extrasafe`, `birdcage` and `gaol` are stale or archived.

**What it costs.** A profile took 5 ms to apply on the Mac, once per worker. Fifty hours over several million files is 36 to 60 ms of wall time a file against about a millisecond of processor time, so the overnight scan waits on the disk and one worker keeps up; more help only on storage that serves reads in parallel, an SSD or a NAS, and hurt a spinning disk.

**Memory-safe parsers instead.** Rust crates read some containers' headers, Mozilla's `mp4parse`, `symphonia`, `matroska`, `imagesize` and `nom-exif`, and none reaches AVI, MPEG program and transport streams, ASF, RealMedia, FLV or DV. Firefox's [RLBox](https://hacks.mozilla.org/2021/12/webassembly-and-back-again-fine-grained-sandboxing-in-firefox-95/) sandboxes C libraries as WebAssembly in the same process, Graphite, Hunspell and Ogg since Firefox 95 and Expat and Woff2 since 96, and runs FFmpeg's decoding in a separate process instead (reported, [bug 1595994](https://bugzilla.mozilla.org/show_bug.cgi?id=1595994)).

**Supervising the worker.** Linux bounds memory with `RLIMIT_AS` ([setrlimit(2)](https://man7.org/linux/man-pages/man2/setrlimit.2.html)); the Mac does not, measured on the Mac mini when a 2 GB allocation succeeded after a 512 MB limit was asked for, so the parent watches the worker's memory and kills it, which `memory.rs` already measures; Windows bounds it with the job object. FFmpeg bounds itself with `probesize`, `max_streams`, `duration_probesize` and `av_max_alloc`, and `format_whitelist` and `protocol_whitelist` say which demuxers and protocols may run. At a deadline, the worker's processor time against the wall clock tells a parser spinning on the file from a read stalled on the drive. Writing the path in flight to a journal before sending it attributes even a crash of fuji, or of the machine, to that file.

## Additional Notes (moved in from another sprintdoc)

- **Keeping the library current**, proposed: follow FFmpeg's point releases on the 9.0 branch with each fuji release, since FFmpeg backports its fixes there and a point release keeps the same interface; bump promptly for a fix in code fuji reaches, a demuxer scan runs or a decoder with a public exploit, the first being the fixes for CVE-2026-107678 in the MOV demuxer and CVE-2026-95127 in libass once they are released; and take the larger moves, FFmpeg's next major version or mpv 0.42, after a look at what they change. A bump is one version and hash line per package and `pnpm library` on each platform, about 3 minutes on the Mac, 20 on the Windows box and 13 for both Linux libraries, then the ledger entries and a normal release.
- **Checking each project's signature at a bump**, proposed: a pinned hash proves the bytes have not changed since they were pinned, not that the pinned bytes were the maintainers'. FFmpeg publishes a signature beside each release tarball, and some of the others do too; checking it once when a hash line changes, and saying so in the record, closes that. mpv, SPIRV-Cross and shaderc come as archives GitHub generates from a tag, with nothing signed, and their record says the tag and the hash are all there is.
- **Checking the ledger against advisories**, proposed: the ledger names every source and version, so a small script could ask a vulnerability database, OSV or NVD, what is known against each, and turn the ledger into an alarm. Not tried.
