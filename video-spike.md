# Video spike

libmpv in fuji the right way, as to stability, provenance and performance, on the Mac and Windows, and built for Linux with choices that leave it no surprises, though Linux is not tested in this spike. Sound and video playing on top of the web page in Tauri, with nothing drawn over the video, where a click anywhere on it toggles play and pause and a drag moves the whole window. And the library's answers about a file, its running time and its dimensions from a path, and a still frame rendered from a time in it, through calls that are safe and fast, for the part of fuji that will walk a collection overnight. Built so far: the library linked, carried and measured on both machines, and nothing plays yet.

The same six with the library inside is the measurement. The dll alone is tens of megabytes against an installer under four, but the installer compresses what it carries, so the installer is the number and not the dll. **Startup and memory.** The log's first two lines, written by the shell at every launch: the launch timed whole from the operating system starting the process, through the loader, main and the page, to the first frame; and the footprint of each of fuji's processes two seconds later, before anything is opened. The spike measures whichever it builds and says which, and if the first costs something a collector who never plays a video would notice, tries the second.

## One recipe

Homebrew's part on the Mac today is the library itself. `brew install mpv` puts mpv the player and the 47 libraries it was built against under `/opt/homebrew`, and `frameworks.js` walks that tree, copies all 48, rewrites each to find its siblings inside the bundle, signs each and hands Tauri the list. It works, the numbers above are from it, and it is the wrong shape for shipping. The tree is whatever Homebrew's formula wanted for the player on the day of the last `brew upgrade`, LuaJIT, libarchive and libbluray among it, pinned to nothing, so two Macs build two different Fujis and the same Mac builds a third next month. It is 48 binaries to sign and to notarize where Windows signs none and carries one. And it is a provenance Windows no longer has, since Windows builds its dll from twelve release sources with their hashes in the repository and gets the same bytes every time.

The uniform construction is the Windows recipe run on the Mac. `win-libmpv/build.sh` is bash over meson, cmake and the configure scripts, and every pin in it is a tarball hash or a commit, so the same packages build on the Mac with Homebrew providing the tools alone, meson, ninja, cmake, nasm and pkg-config, the way MSYS2 does on Windows, and nothing of Homebrew's in the result: one `libmpv.2.dylib` with FFmpeg, libplacebo, libass, dav1d and lcms2 static inside it and Apple's own frameworks beneath, VideoToolbox for the hardware decoder and OpenGL for the output, which is the output mpv's own Mac window draws through and the one the render API offers. The Mac's section of the recipe is smaller than Windows', since OpenGL takes shaders as mpv writes them and wants no compiler; Vulkan over MoltenVK, which would want one, is left out until a reason appears. Then `frameworks.js` has one file to copy and sign and no tree to walk, the dmg carries one library, the panel shows the recipe's numbers and not the day's, and the recipe moves out from under its Windows name. The same recipe runs in the flatpak's container, which has no mpv to depend on anyway, and for the same uniformity in the deb and rpm containers too, so no package depends on whichever libmpv a distribution ships, 0.35 on Debian 12 and 0.37 on Ubuntu 24.04, and every one of the six carries the same bytes. The cost is scaffolding: a Mac section and a Linux section in the recipe, the tools installed once per machine, and ten or twenty minutes of building when the library changes, which is rarely. Proposed here, in answer to the question the Windows letter left to the Mac, and not yet decided.

## The ground floor

A view that plays sound, and then a square on it that plays video, from the same four commands, which are the floor Fuji Audio and Fuji Video are both built on: a player started for the window with the options the page chooses; one command that sends it one mpv command with its arguments; one that reads one property as text; and one that stops it. The handle lives in Rust keyed by the window's label, so Windows runs the map with one entry and nothing branches. Two declarations join the seven for it, setting an option and sending a command. The page owns what it shows and what plays when, with play and stop and nothing more: no pause control, no seek bar, no keys past `a`. Audio output is mpv's on every platform and nothing to build. Events coming back up wait, and the view reads the position itself while it shows.

For the spike the view is `AudioPanel.vue` in the shell, reached by `a` from the sheet and from the settings and left by `a`, and it shows the library's version today, which is how the link was proven. Next it plays: a dropped file loaded and played with the video switched off, which on Big Buck Bunny proves the demuxer and both decoders on a real video file with no pixels. Then the square: a fixed rectangle on the panel, no resize, where the video draws on top of the page, sized to the video's aspect or stretched to fill, whichever is easiest, since the test is pixels and not fit. Fuji Video, when it ships, always sizes its window to the video and never crops, letterboxes or stretches, and that is a sprint of its own; so is Fuji Audio's shape, its keys, whether it is a window, and how it opens from the sheet, the table or a file the operating system hands over.

Two things happen on the video, and neither draws on it. A click anywhere on it, at any time, toggles play and pause; a drag on it moves the whole window. Both are the page's: the native view ignores the mouse, so a click and a drag over the video reach the page under it as they reach a picture, and the page toggles the player or asks the window to follow the pointer. On Windows mpv makes a window of its own inside the one it is handed, and `input-cursor-passthrough` is the option that lets pointer events through it, to verify there.

## What the library says about a file

The part of fuji not started yet walks a collection overnight, for hours and over terabytes, into a small SQLite database of what each file is, and three of its questions are the library's. From a path: the running time, and the dimensions, which give the aspect, the figures a collector understands, with the codec kept as the way to find them and not the thing to show. And a still frame from a time in the file, rendered to an image, fast, reliable and safe, for a contact sheet of a video, or a row of stills that flips as the pointer moves across it. For pictures the same walk matches the bytes to the extension, so a file named `image` with none is known for the JPEG it is, and reads the raster's dimensions; whether that goes through the library or through the headers in Rust, which know a JPEG from its first bytes, is a question the walk's own sprint answers.

mpv has all three through the client API, with no view and no pixels on screen. A file loaded paused with its sound off hands `duration`, `width` and `height` as properties, from the container before any frame is decoded, and `screenshot-raw` after a seek returns the frame as a bitmap in memory, a map of width, height, stride and bytes, which crosses to the page the way a thumbnail does. The spike builds those as commands of the same shape as the player's, no new library and no second binding, and times them on both machines against the size of the file and the distance of the seek: a seek lands on a keyframe and decodes forward to the time asked, so the cost is the distance to the last keyframe, and the number says whether a row of stills is a flip or a wait. Safe is the one word the library cannot promise, since it is FFmpeg parsing an untrusted file inside fuji's process; the walk is hours long and already a process of its own, and whether these answers come from a process fuji can lose without losing a window is decided when the walk is designed, not here. FFmpeg declared directly stays the fallback if mpv's road proves slow.

## The binding

Settled: declarations written by hand in `mpv.rs` against mpv's client header, seven today, with no crate and no bindgen, since fuji calls a handful of functions whose signatures the API's second major version fixed. Two more join for the player, one more for a command that returns a node, which the still needs, and the render API's few on the Mac and Linux, declared against `render.h` and `render_gl.h`, which Homebrew ships beside `client.h` and the recipe would too.

## Windows

Built on the Windows box on 2026-10-12, from the Mac's letter in `mac2win.md`. The link was the easiest of the three, as expected: the gates in `lib.rs` and `mpv.rs` opened to windows, and the extern block there carries `#[link(name = "libmpv-2", kind = "raw-dylib")]`, so the linker writes the imports from the seven declarations and no import library is made or kept. The library is zhongfly's mpv-winbuild lgpl dev archive of the same day, the plain x86_64 one, whose `client.h` matches the seven declarations at client api 2.5; its `libmpv-2.dll` sits untracked in `src-tauri/binaries/`, and is 101,207,552 bytes, a hundred megabytes rather than tens. Shipping is a tracked `tauri.windows.conf.json` naming the dll a resource, which Tauri merges on Windows alone and copies beside the executable in both profiles, and which `win-setup.js` now merges the same way, since it read `tauri.conf.json` alone before and would have made an installer without the dll in it. Two things found on the way. `tauri_build` watches only the configuration files that existed when it last ran, so the first build after the platform file appears does not copy the dll into `target/release` until `build.rs` or `tauri.conf.json` changes; a fresh checkout never sees this. And the dll hard-imports `vulkan-1.dll`, which graphics drivers install and Windows does not, so on a machine without one the loader fails before main and fuji never starts; loading on the first play would remove that along with the launch cost.

## Linux

Not tested in this spike, and built so that nothing waits on a test to be a surprise. The gate in `lib.rs` opens; the recipe builds the library in the containers if it is adopted, and `libmpv-dev` goes in the images with a dependency line in the deb and the rpm if it is not. The square is the Mac's: every target fuji ships to runs Wayland, Ubuntu 24.04 and the Pi's own desktop among them, where mpv cannot be handed a window, so the view is the render API over WebKitGTK, which is the view the Mac builds. The flatpak's sandbox has to be allowed to make sound, which is a line in its manifest and the one thing here only a test can prove. The spike ends on Linux with the four packages built in the containers with no errors, as they built on 2026-10-12 with the stand-in; installing them on the Linux desktop and the Raspberry Pi is the sprint after.
